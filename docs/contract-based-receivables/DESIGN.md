# 合同主应收与收款分配设计

## 目标

将“登记收款”改为以合同为业务依据，同时保留订单级查询和项目执行链路。合同是客户应收主体，Payment 是实际到账事实，payment_allocations 是收款在合同及订单之间的不可变归属事实。

## 当前问题

- Payment 仅关联 business_documents（实际为订单），登记表单也只能选择订单。
- 合同已收金额通过合同关联订单的收款间接汇总；订单换绑合同可能改变历史合同统计。
- 应收页面按合同展示，但写入动作按订单执行，合同金额与订单金额不一致时缺少安全边界。

## 本阶段边界

1. 新增 payment_allocations 表，支持合同级和订单级分配。
2. 新登记收款必须选择合同；旧 order_id 输入仅用于兼容，并自动解析唯一合同。
3. 未指定订单时，按合同关联订单的创建顺序自动分配，剩余金额保留为合同级分配。
4. 指定订单时，仅分配到该合同下的订单，并校验订单未收余额。
5. 合同、框架合同项目和订单的已收/未收均从分配事实核算；收款作废不删除记录，但分配不计入余额。
6. 历史收款只在迁移中回填明确唯一的合同关系；无法唯一判断的记录保留原状，后续人工处理。

## 非目标

- 本阶段不增加合同付款期次、发票、退款和自动催收。
- 不删除旧 Payment 字段、旧 API 别名或历史收款。
- 不修改设计、制作、安装任务状态和权限。
- 不在本阶段对生产数据库执行人工数据修复。

## 核心流程

```text
合同 → 登记收款单 → 收款分配
                  ├─ 合同
                  ├─ 订单
                  └─ 合同未分配余额

订单 → 设计 / 制作 / 安装任务（执行链路不变）
```

## 一致性规则

- 收款客户必须等于合同客户。
- 合同已收不得超过合同总额；订单分配不得超过订单未收额。
- 同一收款单的分配总额不得超过收款金额。
- 新收款不能跨客户、跨合同订单分配。
- 作废操作保留 Payment 和 allocation 审计事实，余额从有效收款分配重新计算。
- 金额计算在服务层使用 Decimal；数据库约束保证分配金额为正数。
