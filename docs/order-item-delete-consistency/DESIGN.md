# 订单明细删除与设计/制作/安装任务一致性设计方案

## 1. 任务分类、风险和目标

- 类型：订单明细生命周期、三阶段任务关联、任务进度聚合、回收站联动和关联数据清理。
- 模式：STRICT。
- 风险：高。删除动作会同时影响订单明细、设计/制作/安装任务、外协、验收、成本、任务看板、完成统计和回收站恢复；如果只改前端或只删除一张关联表，容易造成任务进度虚高、订单无法恢复或财务历史丢失。

本次目标：

1. 删除订单明细时，立即从设计、制作、安装三类任务的当前有效范围移除；该明细不再可选择、不可推进，也不再参与任务进度分母。
2. 三类受影响任务重新计算明细数量、状态、进度和看板可见性；一个任务内其他明细的状态、执行人、进度不被重置。
3. 一次删除后，如果订单已经没有任何有效明细，订单自动进入回收站。
4. 删除前展示该明细实际关联的任务、外协、验收、成本等内容，用户确认后才提交；提交采用已有的预检凭证、版本校验和原子事务。
5. 保留必要的操作审计和财务事实，避免把“业务关联删除”错误实现成不可恢复的物理删除。

## 2. 对用户需求的具体理解

### 2.1 “删除任务历史关联”的业务含义

本方案将“删除任务历史关联”分成两层：

| 层级 | 删除后的表现 | 是否物理删除 |
|---|---|---:|
| 当前业务关联 | 该订单明细不再出现在设计/制作/安装任务的有效明细、可选项、进度分母、看板和正常任务摘要中 | 否，标记为已移除 |
| 审计历史 | 保留原任务编号、明细编号、原状态、进度、执行人、删除人、删除时间和原因，用于追溯 | 否 |

不建议物理删除 `task_order_item_links` 或 `task_item_status_logs`：物理删除会破坏幂等、回收站恢复、历史统计解释和问题排查；而且订单明细当前本身已经采用 `lifecycle_status='voided'` 的逻辑作废方式。用户界面上仍然会达到“任务历史关联已删除”的效果，历史页只在有权限时显示“明细已从订单删除”的记录。

### 2.2 “如果任务内所有明细都被删除”的边界

这里区分两个场景：

1. 某一个设计、制作或安装任务没有有效明细了，但订单还有其他有效明细：只关闭/隐藏这个空任务，不回收整个订单。
2. 本次删除事务完成后，订单的有效明细数量为 0：订单状态改为订单级 `cancelled`，写入 `deleted_at`，自动进入订单回收站。

这样不会因为一个设计任务的明细被删掉，就误把同一订单中仍在制作或安装的其他明细一并回收。

### 2.3 新增明细和重新录入的边界

删除后重新新增同名明细会产生新的明细 ID，不继承原明细的任务状态、执行人、进度、附件关联和成本归属。只有回收站中的“恢复本次删除”才恢复原明细 ID 和可恢复的任务快照。

## 3. 当前系统审计结论

当前实现已经有部分安全基础，但删除链路尚未闭合：

| 位置/对象 | 当前行为 | 本次需要解决的问题 |
|---|---|---|
| `BusinessDocumentItem.lifecycle_status` | 普通订单明细删除被标记为 `voided`，没有直接物理删除 | 这是正确的保留历史基础，但需要把所有下游当前关联同步标记为无效 |
| `TaskOrderItemLink` | 保存任务、订单明细、明细状态、进度和明细执行人 | 没有单独的关联生命周期字段；订单明细软删除不会自动触发 FK cascade |
| 三张任务表的 `order_item_id` | 旧版单明细兼容字段，采用 `SET NULL` | 删除明细后可能继续留下陈旧的直接引用，需要清空或迁移到统一关联模型 |
| `task_service` 的任务聚合 | 主要按 link 的 `item_status` 聚合，`cancelled/rolled_back` 才会被排除 | 没有排除订单明细 `lifecycle_status='voided'` 的统一规则，可能造成进度和摘要不一致 |
| `BusinessDocumentService._apply_order_item_refresh` | 已处理部分验收和外协刷新 | 当前没有统一清理三类任务明细 link 并重算所有受影响任务 |
| `_build_order_item_mutation_context` | 删除最后一条明细时以 `LAST_ITEM` 阻止提交 | 与“全部明细删除后订单进回收站”新规则冲突，需改为允许并触发自动回收 |
| `Attachment` / 订单阶段资料 | 资料以 `order_id + stage` 为订单/阶段级源头，不绑定单条订单明细 | 删除某一条明细不能安全删除整组设计资料、制作资料或安装现场照片视频，应保留 |
| `ProjectCost` | 支持单条或多条订单明细成本归属，金额本身是成本事实 | 删除明细时只能解除/转为订单级解释，不能静默删除真实成本金额 |
| `TaskItemStatusLog` | 追加式明细状态历史，完成统计查询当前有效订单明细 | 保留历史事件；当前统计继续通过有效明细过滤，不把已删除明细算进当前结果 |

当前最重要的逻辑缺口是：订单明细被软删除后，任务 link 仍可能参与 `_task_item_state_map`、任务聚合和任务摘要。这会使“明细已经删除”与“任务仍显示制作中/已完成”同时存在。

## 4. 目标数据模型

### 4.1 订单明细生命周期

继续使用 `BusinessDocumentItem.lifecycle_status`：

```text
active  ->  voided
```

删除时记录：

- `voided_at`：删除生效时间；
- `void_reason`：用户填写的删除原因；
- `BusinessDocumentVersion`：完整的删除前后快照及受影响关联；
- `OperationLog`：操作人、订单、动作、客户端地址和结果。

不增加第二套订单明细删除字段，避免 `deleted_at`、`voided`、`cancelled` 三套语义并存。

### 4.2 任务明细关联生命周期

在 `TaskOrderItemLink` 增加独立的关联生命周期，而不复用 `item_status`：

```text
link_status: active | removed
removed_at: datetime | null
removed_by: users.id | null
removed_reason: text | null
```

推荐增加索引：

```text
(task_type, task_id, link_status)
(order_item_id, link_status)
```

字段语义：

- `item_status` 仍只表示该明细在当前阶段的业务状态，例如设计中、制作中、安装中、已完成；
- `link_status='removed'` 表示这条任务关联不再是当前工作范围，不代表该明细曾经的阶段状态被改成了已完成或取消；
- 所有正常任务查询、明细选项、状态动作、进度聚合和下游阶段判断默认只取 `link_status='active'` 且订单明细仍为 `active` 的记录；
- 管理员历史查询可以带 `include_removed=true`，显示“订单明细已删除”，但不能继续操作。

### 4.3 任务范围状态

为了避免把“任务工作范围为空”和“任务业务已经完成/取消”混在一个 `status` 字段里，三张任务表增加：

```text
scope_status: active | empty_after_item_delete
scope_closed_at: datetime | null
scope_closed_reason: text | null
```

规则：

- 有至少一条有效任务明细时，`scope_status='active'`；
- 任务没有有效明细但仍保留任务历史时，`scope_status='empty_after_item_delete'`；
- 空任务从未完成任务看板和可操作列表隐藏，历史任务仍可由有权限用户查看；
- `task.status` 保留最后一个真实工作流状态，不能为了隐藏空任务把已完成事实改写成“已取消”；
- 当前任务响应额外返回 `effective_item_count`、`scope_status` 和 `scope_closed_reason`，前端用它们判断当前是否可操作。

如果实施时为了兼容旧数据库暂时不增加任务范围字段，备选方案是把空任务写成 `cancelled`；但这会污染完成/取消统计、历史语义和回收恢复，因此不采用作为正式方案。

## 5. 删除影响分类

删除确认框不显示模糊的“关联数据若干条”，而是显示精确的关联清单和处理动作。

| 关联类型 | 识别方式 | 确认后的处理 | 默认是否阻断 |
|---|---|---|---:|
| 设计/制作/安装任务明细 | `TaskOrderItemLink.order_item_id` 或旧任务的 `order_item_id` | 当前 link 标记 `removed`；清空旧直接引用；保存原状态/进度/执行人快照；任务重算 | 否 |
| 任务状态历史 | `TaskItemStatusLog.order_item_id` | 保留追加式历史，当前统计按有效订单明细过滤 | 否 |
| 未开始外协 | `OutsourceTask.order_item_id` 且状态 `pending/draft`、无付款 | 外协任务软取消，记录“订单明细删除”原因；从外协阻塞集合移除 | 否 |
| 外协进行中、已付款、已完成或已结算 | 同上 | 不静默删除事实；确认框列出任务编号、状态和金额 | 是，需先处理外协或使用后续高风险流程 |
| 草稿/待处理验收行 | `AcceptanceItem.document_item_id` | 解除明细引用，验收草稿保留 | 否 |
| 已验收/有条件验收事实 | `AcceptanceItem.document_item_id` | 保留验收事实并标记待复核 | 是，避免删除交付证据 |
| 单条明细成本 | `ProjectCost.document_item_id` 或 `ProjectCostItemLink.document_item_id` | 解除该明细归属；成本记录和金额保留，必要时转为订单级成本解释；不做金额分摊 | 否，若有已结算事实则提示复核 |
| 订单阶段资料 | `Attachment.order_id + stage` | 保留整组订单资料，不按文件名猜测属于哪条明细 | 否 |
| 收款、合同、库存、对账、用车等订单级数据 | `document_id/related_order_id` | 保留事实，只在预览中提示“不会随单条明细删除” | 付款金额可能导致删除后总额低于已收款时阻断 |

“确认后删除”只对可以稳定映射且属于计划状态的数据执行；已付款、已验收、已结算等事实不物理删除，避免把业务删除误变成财务冲销。

## 6. 用户操作流程

### 6.1 删除前预检

订单详情点击某条明细的“删除”后：

1. 前端调用现有订单明细删除预检接口；
2. 服务端锁定前读取订单有效明细、目标明细和所有三阶段任务关联；
3. 生成删除影响清单：关联任务编号、阶段、原状态、原进度、执行人、外协/验收/成本记录及处理动作；
4. 计算删除后的订单有效明细数、订单金额、已收/未收金额和是否自动进入回收站；
5. 返回签名 `preview_id / plan_hash / preview_expires_at`，前端只展示结果，不在浏览器自行推断关联。

### 6.2 确认框建议

标题：`确认删除订单明细`。

内容结构：

```text
将删除：公示栏（新做）
删除原因：________________

将从当前任务中移除：
设计任务 Dxxxx：设计中，执行人：张三，进度：50%
制作任务 Pxxxx：制作中，执行人：李四，进度：50%
安装任务 Ixxxx：未关联

将自动处理：
未开始外协 1 条、草稿验收行 1 条、明细成本归属 1 条

将保留历史：
订单阶段资料、收款、已完成任务记录、成本金额和操作日志

删除后订单有效明细：0 条
删除后订单将自动移入回收站
```

确认按钮文案：

- 有有效明细：`确认删除明细`；
- 删除后无有效明细：`确认删除并移入回收站`；
- 存在阻断关联：禁用提交并显示具体处理建议；
- 预检过期或订单版本变化：要求重新预检，不允许沿用旧确认。

### 6.3 提交后的反馈

成功返回：

- 已删除的订单明细 ID；
- 三类受影响任务及重算前后明细数/状态/进度；
- 外协、验收、成本的实际处理结果；
- 是否自动回收订单；
- 变更批次号，供订单版本/操作日志追踪。

前端刷新订单详情、项目看板、三个任务列表和成本列表；如果订单进入回收站，跳转到订单列表并提示“订单已无有效明细，已移入回收站”。

## 7. 统一事务处理顺序

订单明细删除、三类任务关联清理和重算必须由一个服务方法统一完成，不能由订单 API、任务 API、外协 API 分别各做一半。

```text
锁定订单和明细
      |
      v
重新验证预检凭证、订单版本、权限和阻断条件
      |
      v
收集设计/制作/安装当前 link + 旧 order_item_id 兼容引用
      |
      v
订单明细 active -> voided
      |
      v
任务 link active -> removed，记录移除快照和操作审计
      |
      v
处理可自动处理的外协/验收/成本明细关联
      |
      v
按受影响任务逐个重算明细数、状态、进度、范围状态
      |
      v
重算订单金额、收款差额、利润及必要的剩余明细阶段
      |
      +---- 有效明细 > 0：保持订单活跃，刷新看板
      |
      +---- 有效明细 = 0：订单 status=cancelled、写 deleted_at、进入回收站
      |
      v
写 BusinessDocumentVersion + OperationLog
      |
      v
同一数据库事务提交；任何一步失败全部回滚
```

### 7.1 任务重算公式

对每个受影响任务：

1. 有效工作集合 = `link_status='active'`、订单明细 `lifecycle_status='active'`、且 link 状态不是 `cancelled/rolled_back` 的明细；
2. 有效集合为空：`scope_status='empty_after_item_delete'`、`progress_pct=0`，不把空集合当作 100%；
3. 有效集合不为空：保留每条未删除明细的状态、进度、执行人，只对有效集合聚合；
4. 全部有效明细完成时，任务才可以为设计 `confirmed` 或制作/安装 `completed`；
5. 混合状态时，使用现有阶段状态优先级和明细进度平均规则，不能把被删除明细计入分母；
6. 任务重算只作用于该任务的受影响 link，不重置同订单其他任务的独立明细。

### 7.2 订单状态和金额重算

- 订单金额继续由剩余 `active` 订单明细小计求和；
- 已收款、未收款、成本和毛利按现有公式重新计算；
- 若删除后总额低于已收款，提交前阻断，提示“订单已有收款，删除后订单金额不能低于已收款金额，请先处理收款”；
- 若仍有有效明细，订单不能因为被删除的明细历史状态而变成完成；必要时调用现有项目阶段解析器，保证剩余明细未完成时不会保留错误的 `completed`；
- 若有效明细为 0 且付款约束通过：订单状态写为 `cancelled`，设置 `deleted_at`，写状态日志原因“订单明细全部删除，系统自动移入回收站”。

## 8. 回收站和恢复规则

自动回收必须有可用的恢复路径，否则会出现“订单在回收站，但恢复后没有任何有效明细”的空订单。

### 8.1 自动回收快照

进入回收站时，在同一个变更批次中保存：

- 本次导致回收的所有订单明细 ID；
- 这些明细删除前的完整字段快照；
- 三类任务 link 的状态、进度、执行人和位置；
- 订单原状态、金额和任务范围状态；
- 不能自动恢复的外协/验收/成本事实说明。

### 8.2 恢复动作

对于“因订单明细全部删除自动回收”的订单，回收站按钮显示：`恢复订单并恢复删除明细`。

恢复事务：

1. 恢复订单 `deleted_at=NULL`；
2. 根据自动回收快照恢复导致回收的订单明细为 `active`；
3. 仅恢复快照中仍可恢复的三阶段任务 link，已被后续人工处理的记录不强行覆盖；
4. 重新计算三类任务和订单金额/阶段；
5. 若恢复后仍无有效明细，保持在回收站并提示“没有可恢复的有效明细”；
6. 记录恢复操作日志。

订单级人工取消的原有恢复逻辑保持不变，不套用明细删除的恢复快照。

## 9. 三类任务统一规则

设计、制作、安装必须共用同一套“按明细删除关联 + 重算”的服务函数和查询过滤器，只通过 `task_type` 配置差异化状态集合：

| 阶段 | 当前有效关联 | 删除后的任务效果 | 是否影响订单回收 |
|---|---|---|---:|
| 设计 | active link + active order item | 移除设计 link，任务空则关闭范围并隐藏 | 只有订单整体没有有效明细时影响 |
| 制作 | active link + active order item | 移除制作 link，外协进行中按阻断规则处理 | 同上 |
| 安装 | active link + active order item | 移除安装 link，现场资料保留 | 同上 |

禁止分别在三个 API 中复制一套删除逻辑；后续新增阶段时只注册阶段模型、状态集合和显示文案。

## 10. 权限、安全和并发

- 删除订单明细继续使用订单明细编辑权限；设计/制作/安装任务权限不能推导出订单删除权限；
- 预检、确认和实际提交都在服务层重新校验，前端隐藏按钮不算安全边界；
- 操作人必须填写删除原因；高风险关联的提示不能被普通确认绕过；
- 使用订单 `updated_at` 乐观锁和数据库行锁，防止两个用户同时删除/修改同一明细；
- 预检签名必须包含订单 ID、明细 ID、操作、删除原因、关联目录和订单版本；目录变化后必须重新预检；
- 重复提交同一 `preview_id` 返回幂等结果，不重复删除关联、不重复回收订单、不重复写业务变更；
- 上传文件只保留，不在删除订单明细时删除整个订单阶段目录；
- 不新增第三方依赖，不通过模糊的项目名称、客户名称或文件名猜测明细关联。

## 11. 非目标和暂不处理

- 不把订单级“取消订单”改成明细删除；两者仍是不同操作；
- 不物理删除订单明细、任务状态日志、成本、付款、验收事实或订单阶段附件；
- 不通过删除明细自动删除整个任务的所有附件；当前附件是订单/阶段级源头；
- 不允许普通用户强制删除已付款、已验收、已结算或外协进行中的明细；
- 不在本轮增加跨订单批量删除、删除后选择性恢复单条明细或财务退款/冲销流程；
- 不顺手删除三张任务表的旧 `assigned_to/order_item_id` 字段，先完成兼容迁移和数据验证。

## 12. 主要风险和控制措施

| 风险 | 控制措施 |
|---|---|
| 只删除订单明细，任务 link 仍参与聚合 | 集中使用 `link_status + order item lifecycle` 过滤器，三类任务统一重算 |
| 被删除明细把任务推到 100% | 空集合进度固定为 0；只用剩余有效明细计算分母 |
| 删除一条明细重置同任务其他明细 | 只按受影响 `order_item_id` 更新 link，其他行原样保留 |
| 删除最后一条明细后订单金额与已收款矛盾 | 维持现有“总额不能低于已收款”阻断；退款/冲销另立流程 |
| 回收站恢复成空订单 | 自动回收保存删除前快照，恢复按钮同时恢复本次删除明细 |
| 已付款/已验收事实被误删 | 关联分类为阻断或保留历史，不执行物理删除 |
| 旧任务直接字段留下悬空引用 | 删除事务内清空/兼容迁移旧 `order_item_id`，并做孤儿检查 |
| 新旧查询过滤不一致 | 提取单一有效任务明细查询服务，任务列表、详情、统计、看板全部复用 |
