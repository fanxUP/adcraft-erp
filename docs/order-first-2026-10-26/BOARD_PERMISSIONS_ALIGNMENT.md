# 订单看板与权限衔接实施记录

日期：2026-10-26。基线：master e501fa4，叠加工作区已有的历史报价档案移除改动。
状态：本地实施及验证完成；未提交、推送或部署，未修改生产数据和实际角色授权。

## 实现结果

- 工作台、独立项目看板复用 `ProjectBoard`，按授权显示待确认/待安排、设计、制作、安装、已完成项目。待确认订单不进入执行队列，同一订单各阶段任务保持独立进度。
- 各列独立分页、显示服务端总数，任务和完成项目在 SQL 中过滤、计数和分页，任务上下文按页批量加载。订单队列支持多状态查询；取消第一页200条的展示限制。
- 列内滚动，分页控件保持可见。加载失败单独提示并提供重试；不会用“暂无记录”代替接口异常。统计明确区分本页可见订单与已加载任务，不叠加重复订单金额。
- 卡片展示订单变更待复核、追加/补做、外协、对应任务待处理事项，以及当前需求、本任务计划量、已完成量、明细执行人。历史未知实际量显示“未记录”，不根据百分比估算。追加来源存入已有范围快照，不新增数据库字段。
- 完成详情将原“数量”改为“当前需求量”，各阶段单独列出历史各批任务完成量、任务编号、原明细名称和单位。需求改为8个时，历史10个与2个仍各自保留。
- 看板进入权与可读取来源一致。工作台无驾驶舱权限时不请求驾驶舱数据。窗口重新聚焦、页面恢复、权限更新和手动刷新会重新读取看板。
- 完整订单创建/编辑要求订单读取、订单金额及明细价格读取。确认订单单独使用状态变更权；删除单独使用删除与金额读取权。详情页编辑按钮同时判断权限与业务可编辑状态。
- 登录资料新增服务端核验的 `effective_permissions`；前端以有效权限判断菜单、路由和操作，保留原始权限列表兼容既有客户端。缺少前置能力、多角色冲突时，前端与服务端保持一致。
- 变更事项按关联模块检查读取、处理及既有员工可见范围，并返回 `can_resolve` 和原因。项目成本复用实际存在的 `expense:read/update`，财务处理不再要求 `order:update`。未完成超收款退款/转预收时仍不可关闭事项；已关闭事项不可覆盖改写。
- 财务可通过订单回收站查看取消订单并处理有权限的资金事项；列表需订单读取及收付款读取或删除权，恢复接口和恢复按钮仍要求删除权。
- 报价写入权限从新角色默认配置中退役，两个初始化入口均保持 deprecated。现有授权保留供审计，旧报价读取、定价规则、客户协议、图纸采集和AI相关能力保留。角色页面只列出现有报价授权，服务端禁止新增退役授权。
- 修正项目看板路由的页面上下文与业务指引。

## 数据与发布边界

没有新增依赖、数据表、迁移、后台进程，没有清理业务或财务数据。历史无可靠快照的实际数量不补猜；历史重复完成记录不自动合并删除。

生产实际角色和多角色组合尚未盘点。发布前可在生产部署惯用环境中运行：

```bash
umask 077
python scripts/audit_order_permissions.py > /tmp/order-permission-inventory.json
```

脚本显式使用只读事务，输出角色授权、在用账号权限并集、缺失依赖/冲突及退役授权，不输出凭据，不自动调整授权。应逐项核对自定义角色的编辑前置权限；不能通过批量增加删除、价格、资金或全量查看权修复缺项。应用与前端应一同发布，使有效权限和页面行为同时更新。回退可恢复原应用版本；本次没有需要回退的数据库结构变更。
