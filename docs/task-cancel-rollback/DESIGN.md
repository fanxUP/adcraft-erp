# 任务取消改为跨阶段回退：设计方案

## 1. 目标与边界

### 1.1 目标

将设计、制作、安装任务中的“取消明细”改为明确的“退回上一阶段”，避免把一条明细写成取消后被阶段汇总误判为完成或导致任务链断裂。

目标流程如下：

```text
订单确认/设计前一级
        |
        v
      设计  <------ 制作明细回退
        |
        v
      制作  <------ 安装明细回退
        |
        v
      安装
        |
        v
      完成
```

### 1.2 推荐解释

本方案将“起始位置为设计”解释为：业务人员在项目看板和任务处理上看到的首个执行阶段是设计。订单的“待确认/已确认”仍作为订单前置生命周期状态保留，用于订单确认、权限校验和审计，不直接暴露为任务阶段。

设计任务被整体删除时，订单回到设计前一级的“已确认”状态，并可重新创建设计任务；默认不退回“待确认”，避免要求业务人员重新确认已经确认过的订单。

如果“回退到设计前一级”实际是指所有任务（包括制作、安装）都直接跳回订单确认前，而不是按阶段逐级回退，这属于另一套业务规则，需要在实施前单独确认；本方案不采用这种跳跃式回退。

### 1.3 非目标

- 不删除订单级“取消订单”、回收站和恢复订单功能；订单取消与任务回退是两个不同层级的操作。
- 不改动外协任务的取消规则；外协进行中仍按现有阻塞和权限规则处理。
- 不把已完成订单重新打开作为普通员工操作；完成后的跨阶段回退必须走高权限、强确认和审计。
- 不批量改写历史数据中的 `cancelled` 状态；生产/安装历史取消明细仅允许有权限用户通过单条“恢复到上一阶段”显式恢复，未恢复前仍按历史记录处理。
- 不把设计明细做成“取消后仍可在设计任务中继续操作”的半有效状态。

## 2. 当前实现审计

当前代码的关键现状：

| 位置 | 当前行为 | 风险 |
| --- | --- | --- |
| `backend/app/domain/workflow_registry.py` | 设计、制作、安装的工作流都允许流转到 `cancelled` | “取消”既像业务放弃，又被任务汇总当成终态 |
| `backend/app/services/task_service.py` | 明细动作由服务端生成，取消动作会写入明细状态并参与任务汇总 | 可能把未完成明细计入全部终态，触发下游任务或整单完成 |
| `TaskOrderItemLink.item_status` | 当前阶段状态和取消状态共用一个字段 | 无法区分“当前阶段状态”和“已退出当前阶段” |
| `TaskItemStatusLog` | 主要记录状态前后值，缺少明确的跨阶段操作语义 | 回退、取消、任务删除的历史含义不够清晰 |
| 设计/制作/安装详情页 | 前端工作流和操作按钮均可能出现“取消” | 与新的逐级回退规则不一致 |
| 整单任务删除 | 已有按整张任务卡删除并重建前置阶段的逻辑 | 设计任务删除规则需要明确为唯一的设计阶段撤销入口 |

当前截图中的“制作中”明细，如果需要撤回，应显示“退回设计”，只影响这一条明细；不应再显示“取消制作”，也不应把其他明细一起变更。

## 3. 目标业务规则

### 3.1 操作名称

| 原操作 | 新操作 | 作用范围 |
| --- | --- | --- |
| 取消设计 | 移除 | 设计明细不提供取消/回退按钮 |
| 取消制作 | 退回设计 | 当前选中的制作明细，逐条生效 |
| 取消安装 | 退回制作 | 当前选中的安装明细，逐条生效 |
| 删除设计任务 | 删除设计任务并退回设计前一级 | 整张设计任务，仅限任务删除权限 |
| 删除制作/安装任务 | 删除任务并退回上一阶段 | 保留为高权限的整卡应急操作，范围与现有权限一致 |

界面文案不再使用容易混淆的“取消任务”。订单级操作仍使用“取消订单”。

### 3.2 明细回退矩阵

| 当前执行阶段 | 可回退目标 | 普通员工 | 经理/管理员 | 结果 |
| --- | --- | --- | --- | --- |
| 设计 | 无 | 不可取消明细 | 不可取消明细 | 只能删除整张设计任务 |
| 制作 | 设计 | 按现有任务操作权限 | 可以 | 只回退已操作的明细 |
| 安装 | 制作 | 按现有任务操作权限 | 可以 | 只回退已操作的明细 |
| 已完成明细 | 上一阶段 | 默认禁止 | 需要专门的高权限和二次确认 | 防止已交付结果被普通回退破坏 |
| 已取消历史明细 | 设计：无；制作：设计；安装：制作 | 只读 | 制作/安装可显式恢复 | 保留历史，不自动批量迁移；恢复只作用于当前明细 |

默认情况下，回退只允许未完成的当前阶段明细。对已完成明细的回退不作为第一版普通流程；如确有需要，经理/管理员通过单独的“回退已完成明细”权限操作，并强制填写原因。

### 3.3 起始位置

订单确认后自动进入设计执行链：

1. 订单确认校验仍然保留。
2. 确认成功后创建或复用设计任务，并把可执行明细置于设计阶段。
3. 项目看板任务列从设计开始展示；“已确认”只作为设计前置状态。
4. 不允许用“取消设计明细”来删除一部分设计工作；若整张设计任务不再需要，由有权限的人删除整张任务。

## 4. 跨阶段回退的技术模型

### 4.1 回退必须是独立命令

不能把回退实现成普通的 `change_status(to_status="pending")`。`pending` 属于当前任务的待分配状态，直接写入会让制作明细留在制作卡片里，并不能真正回到设计。

建议新增明确的服务命令和接口，例如：

```http
POST /api/v1/production-tasks/{task_id}/rollback-items
POST /api/v1/installation-tasks/{task_id}/rollback-items
```

请求体：

```json
{
  "order_item_ids": ["..."],
  "reason": "尺寸需要重新确认"
}
```

接口只接受当前页面选中的明细 ID；不再接受“整单”“整卡默认全部明细”语义。

### 4.2 明细级原子事务

一次回退必须在一个数据库事务中完成：

1. 校验登录用户、岗位权限、明细归属和当前状态。
2. 校验外协阻塞、执行人和已完成限制。
3. 仅处理请求中的 `order_item_ids`。
4. 将源阶段明细标记为“已退回上一级”，从源阶段可执行集合移除。
5. 在上一级任务中复用现有任务或创建任务，只恢复这几条明细。
6. 清理这几条明细在下游阶段的未完成关联，不能清理其他明细。
7. 重算源任务、目标任务和订单的状态/进度。
8. 写入回退操作日志；任一步失败则全部回滚。

### 4.3 明细关联状态

建议不删除 `TaskOrderItemLink`，也不把 `cancelled` 伪装成回退。沿用现有字符串状态字段增加内部历史状态 `rolled_back`，并在服务层单独定义：

- `rolled_back` 不是可执行阶段状态。
- `rolled_back` 不计入完成数量、不触发下游创建、不满足当前阶段“全部完成”。
- 源任务中的该行显示“已退回设计/已退回制作”，只读。
- 目标阶段重新建立或复用可执行关联。
- 回退日志通过现有 `TaskItemStatusLog.source="rollback"` 标明来源；若后续审计要求增强，再增加结构化 `event_type`，不与本次功能混做。

这样可以保留完整历史，又避免硬删除关联后无法解释“这条明细为什么从制作回到了设计”。

### 4.4 任务卡汇总规则

- 源任务只对可执行关联和已完成关联计算当前任务进度。
- `rolled_back` 关联不作为完成分母，也不将任务进度推到 100%。
- 若源任务仍有未完成或已完成明细，保留任务卡并显示剩余执行内容。
- 若源任务只剩 `rolled_back` 历史关联，没有可执行/已完成明细，则任务卡标记为历史“已回退”，从未完成看板隐藏。
- 目标任务仅增加本次回退的明细，不重置目标任务内其他明细的状态、执行人和进度。

## 5. 各阶段具体处理

### 5.1 设计任务

- 设计明细动作中删除“取消设计”。
- 设计明细只能执行设计流程本身，不能用明细取消表达“不要做这条”。
- 设计任务整卡删除按钮仅对 `design_task:delete` 权限开放，前端隐藏不能替代后端鉴权。
- 删除前显示影响范围：设计任务、该任务关联、未完成的制作/安装下游任务及其明细关联。
- 删除成功后订单回到“已确认”（设计前一级），下游未完成任务只恢复/清理受影响明细；写入任务删除日志。
- 删除是整卡操作，不提供“删除设计明细”。

### 5.2 制作任务

- 制作明细不再显示“取消制作”，改为“退回设计”。
- 只对当前点击的单条明细执行；不读取其他勾选项作为隐式批量范围。
- 回退后该明细在设计任务中恢复为可执行状态，制作任务中保留只读回退记录。
- 当前制作任务还有其他明细时，其他明细状态、执行人、进度完全不变。
- 有外协任务进行中的明细不得直接回退，提示“该明细有外协任务进行中，请先完成或处理外协任务”。

### 5.3 安装任务

- 安装明细不再显示“取消安装”，改为“退回制作”。
- 只影响当前点击的单条安装明细。
- 回退后该明细在制作任务中恢复为可执行状态；安装任务中的原行保留“已退回制作”历史。
- 其他安装明细不能被重置，安装任务进度按剩余有效明细重算。
- 外协进行中、已完成交付或存在验收锁定时，按权限和阻塞规则拒绝普通回退。

### 5.4 整张制作/安装任务删除

保留现有高权限应急入口，但统一文案和行为：

- 制作任务删除：回到设计阶段。
- 安装任务删除：回到制作阶段。
- 只处理该任务及其受影响的下游，不重置同一订单中其他独立明细。
- 前端只显示有删除权限的按钮，后端再次校验。

## 6. 权限与可见性

权限沿用现有阶段权限，避免为了一个动作新增角色种子和授权兼容面；“回退”是对应阶段状态操作权限下的受控子动作：

| 权限 | 用途 |
| --- | --- |
| `design_task:view` | 查看设计任务及本人可见范围明细 |
| `design_task:change_status` | 推进设计明细，不包含删除任务 |
| `design_task:delete` | 删除整张设计任务 |
| `production_task:change_status` | 推进制作明细，也可执行未完成明细退回设计 |
| `installation_task:change_status` | 推进安装明细，也可执行未完成明细退回制作 |
| `*_task:rollback_completed` | 后续独立权限：经理/管理员回退已完成明细，默认关闭 |

第一版不新增 `production_task:rollback`、`installation_task:rollback` 权限码；服务端仍按对应阶段的
`change_status` 权限、岗位范围、明细执行人和外协阻塞规则逐项校验。后续若需要把“推进”和“回退”
授权拆开，再单独增加权限码和角色迁移。

岗位可见范围继续沿用现有订单分配和员工归属规则：能看见任务不等于订单归属该员工；员工只有实际领取/开始执行某条明细后，才成为该明细当前执行人。

## 7. 兼容与数据安全

- 历史 `cancelled` 任务、任务明细和日志不批量迁移、不删除；设计历史取消仍只读，制作/安装历史取消由有权限用户单条执行“恢复到设计/恢复到制作”后，才转换为新的回退链路。
- 新请求即使由旧客户端传入 `to_status="cancelled"`，后端也返回大白话错误，例如：“设计、制作、安装明细不能取消，请使用‘退回设计’或‘退回制作’。”
- 订单级 `cancelled` 不受影响，回收站恢复仍按订单级规则运行。
- 回退不直接删除上传附件；订单源头附件仍保留，阶段任务附件按现有只读/可见权限处理。
- 任何跨阶段变更都写操作人、时间、原因、源任务、目标任务和明细 ID。
- 实施前做数据库备份和只读盘点；第一版不做历史业务数据批量转换。

| 历史取消恢复 | 确定将这条历史取消明细恢复到设计/制作吗？只恢复当前明细，其他明细不受影响。 |

## 9. 风险与取舍

### 主要风险

- 历史代码把 `cancelled` 当作任务终态，改动不完整会继续触发错误的阶段完成判断。
- 同一订单明细可以跨设计、制作、安装流转，回退时若按整张任务重置会破坏混合进度。
- 任务自动创建/复用逻辑可能重复生成任务卡。
- 老前端或脚本仍可能调用取消接口。

### 控制措施

- 后端统一收口状态动作，不依赖前端隐藏按钮。
- 回退用独立命令，禁止用普通状态推进模拟。
- 所有状态、任务汇总和下游创建逻辑增加 `rolled_back` 分支测试。
- 明细 ID 级事务和幂等校验；重复提交不能创建重复任务或重复关联。
- 历史取消不批量迁移；设计历史取消只读，制作/安装历史取消通过权限控制的单条恢复入口兼容，不做危险数据迁移。

## 10. 待确认项

本方案默认：

1. 制作回退到设计，安装回退到制作，按阶段逐级回退。
2. 设计任务删除后订单回到“已确认”，不是“待确认”。
3. 普通员工不能回退已完成明细，经理/管理员也需要独立权限和原因。
4. 订单级取消保持原功能。

如果以上默认规则成立，就可以按后续 `PLAN.md` 实施；若“所有任务都直接回到设计前一级”才是目标，应先调整回退矩阵和验收标准。
