# 员工档案与登录账号绑定设计

## 1. 目标

在不合并“员工管理”和“用户管理”两个业务模块的前提下，补齐二者之间的可视化绑定闭环：

1. 员工管理继续维护人事档案、部门、职位、任职状态和证件资料。
2. 用户管理继续维护登录名、密码、角色和系统权限。
3. 一个未删除的员工档案最多绑定一个登录账号，一个登录账号最多绑定一个未删除的员工档案。
4. 绑定关系由后端统一校验，继续服务于任务执行人、任务可见性和完成统计。

## 2. 数据关系

当前 `employees.user_id` 已经是指向 `users.id` 的可空外键。本次只增加“当前未删除员工档案上的 user_id 唯一索引”：

```text
users 1 ───── 0..1 employees
```

唯一索引条件为 `user_id IS NOT NULL AND deleted_at IS NULL`，原因是员工使用软删除，历史档案不应阻止账号重新绑定到新的有效员工档案。

不自动回填、不自动创建账号、不自动删除另一侧记录。已有未绑定员工仍然可以作为人事档案保存，但不能作为任务执行账号使用。

## 3. 接口

### 3.1 获取可绑定账号

`GET /api/v1/employees/account-options?employee_id=<id>`

只返回启用、未删除且没有绑定其他未删除员工的用户；编辑当前员工时，其现有账号会保留在选项中。返回字段仅包括 `id`、`username`、`real_name`，不泄露密码或权限细节。

### 3.2 绑定或解除绑定

`PUT /api/v1/employees/{employee_id}/account`

请求体：

```json
{"user_id": "用户UUID"}
```

`user_id: null` 表示解除绑定。接口沿用员工管理现有 `system:super_admin` 权限，不给普通用户增加绑定能力。

后端拒绝以下情况：员工不存在或已删除、账号不存在或已停用、账号已绑定其他有效员工、绑定目标员工不是有效在职员工。解除绑定不会删除用户，也不会删除员工档案。

### 3.3 列表展示

员工接口补充 `user_username`、`user_real_name`；用户接口补充 `linked_employee`（工号、姓名、部门）。这些字段只用于展示，不替代角色权限判断。

## 4. 业务边界

- 角色、权限来源：用户管理的 `users -> user_roles -> roles -> permissions`。
- 姓名、工号、部门、在职状态来源：员工管理的 `employees`。
- 任务执行登录身份：先从当前用户 `users.id` 找绑定的有效员工。
- 员工离职、停用或账号停用后，不再进入可执行任务/任务分配选项，但历史任务和统计保留。
- 账号没有员工绑定时，可以按照其角色使用其他允许的模块，但不能被识别为设计、制作、安装的普通执行人。

## 5. 前端交互

- 员工列表新增“登录账号”列，未绑定显示“未绑定”。
- 员工编辑表单增加“登录账号”选择器，可搜索、清空和保存；创建员工先保存档案，创建成功后即可在同一对话框中绑定。
- 绑定选择器下方显示说明：“绑定只建立身份对应关系，不会自动改变角色权限。”
- 用户列表新增“关联员工”列，显示工号、姓名和部门；没有绑定显示“未关联员工”。
- 前端错误提示直接使用后端的大白话提示；后端仍是最终校验边界。

## 6. 非目标

- 不把员工部门或职位自动转换成系统角色。
- 不在本次改造中批量创建登录账号或批量绑定现有数据。
- 不改变订单任务可见范围、设计/制作/安装状态机和完成统计计算规则。
- 不删除现有员工、用户、任务或历史记录。
