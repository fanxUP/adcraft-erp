## 1. 目标与建议结论

取消日常使用中的独立报价流程，统一为“创建订单 → 保存待确认 → 确认并安排执行 → 完成”。订单编辑保留当前报价的分组、批量明细、计价、导入和预览体验；无需先创建报价再转成订单。

授权用户可以在待确认、执行中、已完成阶段修改订单。系统按同一变更批次更新当前订单、关联计划和汇总；涉及已执行、已收付款、已签署或已确认的数据，保留当时版本，并明确生成补做、取消、退款、补结算或单据变更事项。

“同步一致”的验收定义是：当前需求一致、实际发生记录可追溯、差额可解释、待处理事项可完成。不采用把所有历史单据的金额、数量、日期和状态直接覆盖为最新订单值的方式。

默认方案：一个订单入口、一套创建/编辑界面、一个影响确认弹窗、订单详情内查看变更结果；复用现有版本、权限和回收站能力，不新增通用审批中心。

## 2. 当前实现与改造边界

| 当前情况 | 对本次改造的含义 |
|---|---|
| 报价和订单共用 `business_documents`、`business_document_items`、分组及版本表 | 保留统一数据模型，新增订单创建流程，不必拆库或重建所有关联表 |
| 订单已有报价式完整编辑页，以及批量预览、签名确认、并发校验、变更批次和核对接口 | 沿用这条主链路，避免创建第二套订单编辑逻辑 |
| `/orders` 没有直接创建订单的根 POST 接口，列表没有新建按钮，路由没有 `/orders/new` | 必须补齐服务计算、输入模型、接口、权限与页面，改菜单名称不能完成需求 |
| 当前可编辑状态不包括 `completed` 和 `cancelled` | 完成订单需要正式的变更路径；回收站订单先恢复再编辑 |
| 当前将订单总额下调到已收款以下会被拦截 | 要支持这类修改，必须同时建立超收款、退款或转预收的处理闭环 |
| 关联刷新已有部分实现，但不少结果仅标记待复核 | 需要把主要差异落实为有负责人、状态和完成条件的事项，不能只返回一句提醒 |
| 当前确认订单会自动创建设计任务并推进设计中 | 保存待确认不触发任务；确认时沿用现有执行入口，并补充幂等及明细范围控制 |
| 当前订单取消/删除以软删除为主，已有收款时限制取消 | 统一为删除预览和取消入回收站流程，财务结清独立处理 |
| 常规报价、CDR 智能报价、AI 工具、Excel 导入、合同与成本都存在报价入口或引用 | 所有写入口必须一起梳理，不能只隐藏左侧菜单 |

## 3. 用户看到的使用流程

### 3.1 创建订单

1. 客户与销售下保留“订单管理”；新增“新建订单”。
2. 打开与当前报价录入体验一致的订单编辑页：客户、项目、部门/科室、联系人、下单日期、交付信息、分组、明细、优惠、税额、备注及附件。
3. 默认“保存订单”，落为待确认；订单号继续使用 `O...`，不产生新的 `Q...`。
4. “确认并安排执行”复用确认订单能力；提供给有订单确认/状态权限的用户。创建后确认失败时明确显示“已保存为待确认”，重试不得重复创建订单。
5. 支持选择已有客户或输入新客户；进入正式业务前生成或绑定有效客户 ID。新增客户同名时提示选择已有记录，避免每次编辑重复建客。
6. 复用原报价的计价、客户协议价读取、分组和导入能力。保存当前订单不自动修改全客户的协议价；如需保存为协议价，使用明确动作和既有权限。

待确认记录就是订单，不要求额外创建一个新的“报价草稿”模块。沿用 `pending_confirm` 作为初始状态；不完整内容可保留为本地编辑草稿，服务端保存至少要求有效客户/客户名称、项目和合法明细，确认前必须有有效明细及客户 ID。

待确认订单默认不进入实际收入、应收余额及执行任务统计；可在订单列表查看预计金额。已有待确认订单的报表口径如有不同，切换前出具差异清单，避免把口径变化当作数据丢失。已确认订单允许登记预收，不把等待验收作为收款前提。

### 3.2 修改订单

订单列表和详情提供统一的“编辑订单”。详情明细继续只读，增删改全部在完整编辑页完成，沿用此前确认过的界面约定。

- 无关联或不影响关联的普通修改：正常保存。
- 有关联的实质修改：先显示影响弹窗，再一次确认提交。
- 已完成订单：同样可以编辑。只改金额/说明时保留完成状态；新增执行范围时显示补做范围，确认后让对应明细进入待执行，订单重新呈现有未完成工作。
- 已取消或回收站订单：恢复后编辑；恢复时重新核对关联和待执行量，不复活已结算或已经取消的外部业务。
- 订单编号、系统创建时间和实际收付款凭据不是普通编辑字段。下单日期如需修改，仍使用独立预检，并列明报表期间影响。

### 3.3 删除订单

列表/详情的“删除订单”直接进入一个影响弹窗，不要求用户先手动取消再删除，也不要求输入完整订单编号。

确认后执行取消并移入回收站；普通列表不再显示。无关联的误建订单可以快速完成。有执行或财务记录的订单，弹窗必须明确说明停止什么、保留什么以及剩余款项。

是否允许最终永久删除与日常“删除订单”分开。默认不为这次改造开放有关联订单的级联永久删除；已有外协任务的永久删除授权不能自动延伸到订单及其所有财务。真正无引用、无执行及无财务记录的误建单，可在后续独立范围内提供管理员清理。

## 4. 修改字段与同步规则

以稳定的订单 ID、明细 ID、任务关联 ID 和变更版本定位关联项，禁止按同名项目、同金额或客户名称推测对应关系。

| 修改类型 | 默认同步行为 | 必须保留或单独处理的部分 |
|---|---|---|
| 项目名称、部门、普通备注 | 当前任务、项目看板、待处理业务及当前报表展示更新 | 已签署/已确认单据的旧抬头和备注留在原版本 |
| 联系人、联系电话、地址 | 更新本订单当前信息和未执行交付计划 | 不批量覆盖客户主档其他联系人，也不覆盖已完成运输、安装和签收凭证 |
| 分组、排序 | 当前页面、任务明细目录和新导出同步 | 明细 ID 保持不变，不能因排序重建明细或丢任务关联 |
| 售价、优惠、税率 | 重算订单总额、待收/超收、当前毛利、草稿对账与适用汇总 | 外协单价、供应商结算成本、实际收付款不跟随销售单价变化 |
| 数量、规格、材质、工艺 | 更新未执行需求；为已执行部分计算新增、替换或取消范围 | 保留已做数量与实际成本；规格变更不得按比例猜测库存、工时或返工成本 |
| 新增明细 | 创建新明细和阶段需求，可在弹窗确认安排给哪个任务/负责人 | 默认不挪动其他明细、不重置已有进度、不批量新建无关阶段任务 |
| 删除明细 | 从当前有效需求移除，取消未执行范围和有效关联 | 已执行部分留历史引用；有成本/验收/库存/外协事实时生成差异事项 |
| 更换客户 | 未执行、未收款且未签约时按明确映射更新 | 已收款或签约时不可直接改变资金与合同所属客户，需完成退款/分配冲回和重新关联；允许保存修改草稿，解决前不生效 |
| 修改下单日期 | 更新业务期间归属，展示受影响报表与未确认对账 | 实际付款日期、系统登记时间、已确认账单原期间不随订单日期一起改 |

删除最后一条有效明细时，弹窗明确显示“订单将取消并进入回收站”，复用整单删除规则。禁止通过删光明细绕过财务或关联处理。

## 5. 各关联业务如何衔接

| 模块 | 未执行/草稿记录 | 已执行/已确认记录 |
|---|---|---|
| 设计、制作、安装任务 | 同步当前需求、明细范围和交付信息；变更计划量并保留人员分配 | 保存当时明细版本和完成量；补做/返工生成新的待执行范围，不将所有任务归零或重建 |
| 外协任务 | 有明确明细映射时更新需求；采购数量和金额的联动以外协计价方式及确认范围为准 | 在执行、已完成、已结算的外协保留供应商约定；通过外协变更增加/减少未执行量或补结算 |
| 验收单 | 只刷新能明确映射的未提交草稿；已经发送客户或进入审批的版本按已发出单据处理 | 已验收内容留存；新范围生成补充验收，减少范围生成验收变更记录 |
| 普通合同 | 未发出、未签署草稿可按明确规则更新引用项目及金额 | 已签合同金额不能静默变化，创建关联变更/补充单据；订单显示未完成合同变更事项 |
| 框架合同 | 当前项目名称/部门同步；与订单金额绑定的项目额度按规则刷新 | 独立约定的框架额度不等于订单售价，不能直接覆盖；已确认结算需变更记录 |
| 收款、收款分配 | 根据订单最新结算应收重算待收；分配变更必须有来源记录 | 原到账金额、日期和凭证保留；超收单独形成待退/转预收，不作废真实收款来迎合新金额 |
| 客户对账单 | 草稿可根据新订单与资金分配重算 | 已确认对账单保持当时版本，差异进入后续对账或明确重开版本 |
| 支出台账、外协付款、项目成本 | 有来源的计划成本可随来源变更；独立成本不被订单售价覆盖 | 实际支出与付款日期保留，按退款/追补/取消费用调整；总成本重汇总且不得重复入账 |
| 库存出入库 | 更新未执行领料/备料需求，前提是存在明确物料映射 | 已出库记录保留，退料/补料走实际出入库；仅改订单规格不能自动推断应退哪批库存 |
| 车辆申请、派车和车辆费用 | 可调整未执行申请的项目与配送信息 | 已执行派车和费用分摊保留；新增配送产生新的实际申请/费用 |
| 项目队列、工作台、经营与财务汇总 | 在数据库提交后读取最新有效订单和关联需求 | 实收实付仍按真实收付款日期；已确认历史版本与当前值分开展示，不能把订单改价计作现金流 |
| 附件、图稿、CDR 捕获 | 附件继续归属同一订单；新增图稿作为新版本 | 旧图稿和签收文件保留版本引用，不因明细被替换而丢失 |

一条明细可以有不同阶段进度。订单卡片可显示“设计 1 项 / 制作 2 项 / 安装 1 项”，由有效明细和任务关联汇总；这一展示不要求同时重写所有旧任务状态。新增需求根据所需阶段进入队列，不强制整单重新走设计。

对只有订单级关系、没有明细映射的旧记录，在影响弹窗中明确显示“需选择对应明细/处理方式”。没有可靠映射时，不报自动同步成功，也不擅自均摊金额。可以先保存变更草稿，补齐必需映射再让新版本生效。

## 6. 重点场景与财务核对

### 6.1 售价修改

原订单 10,000 元、已收 8,000 元，修改为 12,000 元：实收仍为 8,000 元，待收变为 4,000 元；成本保持实际来源，毛利按新销售金额重新计算。

修改为 7,000 元：实收仍为 8,000 元，待收显示 0，另列超收/待退 1,000 元。退款实际执行前不记为现金流出；转预收或转分配到其他订单必须留下明确记录。该场景目前受旧逻辑限制，须实现并验证后才能开放。

统一核对规则：

- 当前结算应收 = 当前有效明细合计 − 优惠 + 税额 + 已确认且不在明细中重复计入的结算调整。
- 订单净收 = 有效分配到本订单的到账 − 本订单实际退款 − 已转出分配 + 已转入分配；同一笔转入/转出只计一次，客户未分配预收不充当订单实收。
- 待收 = max（当前结算应收 − 订单净收，0）。
- 超收/待退 = max（订单净收 − 当前结算应收，0）。
- 实际成本 = 各有效成本来源按来源去重后汇总，扣除有凭据的退回/冲销。
- 当前毛利 = 当前结算应收 − 实际成本。

税额、折扣的顺序和舍入沿用经过统一校验的服务端计算规则。计划/预计成本如果需要展示，单独命名，不能混入上述实际成本。

### 6.2 数量和执行范围修改

原需 100 件、已完成 60 件：

- 改为 120 件：历史完成仍为 60，新增 20 件需求，总剩余为 60；原任务承担的未做 40 件与新增 20 件有明确分配，不重复派工。
- 改为 50 件：已做 60 件不能显示成只做过 50；对多出的 10 件确认留存、交付、退回或损耗，形成可解释的处理记录。销售应收以确认后的订单及取消结算约定计算，实际成本不能跟着减少 10 件而消失。
- 仅修改售价不触发返工；修改规格/材质需确认已做部分是否仍可交付。无明确判断时不自动把“旧规格完成”计为“新规格完成”。

在未执行数量变化且外协按件计价时，可在确认后沿用外协采购单价重算未执行采购量和金额。固定总价、按面积或分批计价的外协，需要采用自身计价规则或明确输入差额，不能直接套订单销售数量。

### 6.3 删除有历史业务的订单

取消订单不等于应收、应付、已发生成本全部为零：存在取消费用、已交付范围或已付款时，需要确认最终结算应收和未执行应付的取消范围。

删除弹窗展示：原合同/订单金额、建议取消金额、保留的结算金额、净收、待退/待收、实际成本、外协未结及关联执行情况。可明确得到结果的订单一次确认取消入回收站；外部业务尚未同意取消时，保留可见的待取消事项，并在对应任务上提示订单已取消。

回收站和财务页面继续能够定位原订单。财务汇总不能仅因订单有 `deleted_at` 就漏掉真实收付款、剩余结算应收、应付或成本。删除订单不自动永久删除其财务记录、附件或审计记录。

## 7. 一个影响确认弹窗

普通用户不接触版本号、签名或技术状态。弹窗按业务显示：

1. 本次修改：新增/删除几项，哪些字段改变，金额与数量前后差异。
2. 关联目录：设计/制作/安装任务、外协、验收、合同、收付款、成本、库存、车辆、对账等；展示业务编号、当前状态、将执行的动作，可展开查看有权限的明细。
3. 处理结果：自动更新、保留原记录并产生差异处理、必须补充选择后才能提交。
4. 需要用户决定的少量内容：新增任务归属、取消范围、退款或留作预收意向、必要的结算金额。金额和财务明细受权限控制，不向执行人员泄露价格与成本。
5. 有实际影响时填写简短变更原因，可选常用原因；点击“确认修改并同步”或“确认删除并处理关联”。

只需订单修改权限即可发起普通变更，不因存在任意关联就强制增加管理层审批。退款、跨客户资金调整、合同变更等沿用各自权限；当前用户无相应权限时可以生成待处理事项，不能借订单编辑完成越权财务操作。

“已保存”和“所有关联已完成处理”分别准确反馈。仅有可后续办理的退款、补签、退料等外部事项时，新订单需求可以生效，并明确展示负责人及未完成项；会造成归属错误、余额不守恒或无映射写入的情况，必须解决后才能生效。禁止统一返回成功、却把关键同步失败藏在日志里。

## 8. 实现设计

### 8.1 沿用现有基础

- 保留订单/明细 UUID、来源字段、历史报价和版本快照，不批量原地翻转所有报价的 `doc_type`。
- 把当前报价的行计算、表头优惠/税额计算抽为报价历史与新订单共用的计算能力。订单创建、编辑预览、实际保存、导入、AI/CDR 写入和核对使用同一规则；前端小计用于交互，服务端为最终值。
- 新增明确的订单创建模型和服务流程，生成并发安全编号、校验客户与日期、创建分组和明细、初始化余额/成本、记录操作者。不能直接调用当前简化的 `create(doc_type='order')` 后信任前端总额。
- 复用完整订单编辑的 preview/apply 接口和签名凭据，旧行级接口、导入、AI 工具等最终调用同一变更逻辑，避免某个入口绕过联动。

### 8.2 版本与差异事项

继续使用 `business_document_versions` 记录前后快照、变更原因、差异、关联目录、操作人及处理结果；在锁定订单的事务内分配版本序号，保证不重复。

对任务完成、验收、合同、外协结算等需要历史凭据的记录，保存或引用其执行/确认时的订单版本与明细快照。当前任务页读取最新需求，历史完成记录能查看旧需求，不能只靠实时 JOIN 显示被覆盖后的内容。

现有变更结果中的待处理数组不足以支持责任人和完成状态。优先给既有业务记录增加变更来源及必要状态；确实没有对应实体时，增加一张订单变更处理事项表，记录变更批次、关联业务、处理类型、责任人、状态和完成凭据，展示在订单详情的现有变更记录内。

退款/预收转移需有可核对的独立资金记录或分配事件；如当前系统没有此能力，本期必须补齐，不能把它记为普通项目成本，也不能用直接修改 `paid_amount` 替代。

### 8.3 一致性、并发和失败恢复

1. 预览不写业务；提交时锁定订单并重读当前版本、关联任务状态及有效收付款，重新计算影响。
2. 订单修改、同步投影、版本、待处理事项和操作审计在同一数据库事务内完成。下游服务不得提前提交整个共享会话。
3. 对并发变化的相关记录采用稳定顺序锁定或版本校验，包含“预览后新收款、任务刚完成、外协刚结算、库存刚出库”等情况；不能只检查订单 `updated_at`。
4. 预览凭据过期或关联范围变化时要求重新预览；重复点击、断线重试使用同一幂等键，返回同一次结果。
5. 数据库失败整体回滚，不出现订单更新但关联数据只改了一半。提交后再发通知、刷新页面或推送消息；通知失败可以补发，不反向破坏已提交业务。
6. 只有确实跨外部系统的动作才进入持久化待处理/重试；本地强一致写入不推给后台异步“慢慢同步”。不为此新增消息中间件。
7. 保存后执行核对；数据库内可检查的资金、数量、来源和跨单归属约束在提交前验证，未解决的差异不能标为全部核对通过。

## 9. 报价入口、智能功能和历史数据

### 9.1 停用范围

最终日常导航取消常规报价与智能报价的独立业务入口；报价新建、确认、转单、回退到报价等动作停止作为日常流程。原计价规则、产品材质工艺、客户协议价仍可供订单使用。

CDR/智能能力定位为“辅助生成或更新订单明细”：解析预览后创建待确认订单；对已有订单的修改走相同影响确认流程。图稿、捕获和计价的技术版本可以保留，但不再要求用户维护第二张可流转报价单。客户端与 AI 工具必须同步切换，不得在后台继续创建隐藏报价。

Excel 模板、批量导入、成本入口、合同选单、打印标题、AI 页面能力说明、智能助手操作、权限及通知链接同时替换。旧写接口分阶段退役，后台明确拒绝已停用的报价写操作；历史读取按现有可见范围保留。

### 9.2 历史处理默认值

| 历史记录 | 默认处理 |
|---|---|
| 已有订单 | 保留原 ID、订单号、日期和所有关联；不重新创建 |
| 已转单报价 | 保留为只读来源凭据；通过已有 `source_quote_id` 去重，不再生成订单 |
| 未转单报价 | 默认只读归档，按需“继续处理为订单”创建待确认订单；同一来源操作幂等，不因停用报价就批量制造业务量 |
| 已取消/已删除报价 | 保留原状态，不自动恢复或转成活跃订单 |
| 有成本/合同/外协等独立关联的历史报价 | 出具逐项映射清单；继续处理前明确转移关系，防止关联与成本在历史报价和新订单重复计算 |
| 历史 CDR 版本、图稿和来源明细 | 保留引用和文件；订单显示历史来源，新输入走订单流程 |

归档不再作为日常报价菜单展示，可在订单历史来源或受权限控制的历史数据入口查询。旧链接跳转到对应订单或历史只读视图，不能把任意报价 ID 当作订单 ID。

若未来明确要求把所有未转单报价一次性转为待确认订单，再单独运行有预览、来源唯一约束和核对结果的批处理；这不作为默认上线动作。

### 9.3 数据变更与回滚

实施时先重新只读盘点实际生产数据，输出源记录、目标记录、关联归属、金额/日期、冲突和不可自动处理项。准备数据库与上传文件备份，在脱敏或受控测试副本上演练、检查约束和索引，并评估锁等待与执行时间。仅应用必要的增量迁移，不清空报价表、不删除来源字段、不重建数据库。

上线初期保留旧读取能力与兼容字段，新建与编辑流使用受控开关。回滚优先关闭新入口、切回兼容版本，保留新产生的订单和变更记录；不对已收款、退款、派工等真实业务执行批量反向删除。正式停用报价前确认所有调用方已经切换。

当前工作区还包含上一轮核验的未提交修复，应先分清这批修复与本改造的提交范围，不能在部署时把未经此次验收的内容一并混入。

## 10. 权限与报表默认规则

- 新建、读取、编辑、删除、变更状态继续分别使用 `order:create/read/update/delete/change_status`，下单日期沿用独立权限。
- 历史报价权限只用于历史读取；报价角色转换为订单权限时逐角色核对，避免给原本只看报价的人员自动开放订单价格、成本、收付款或删除权限。
- 执行人员按订单/任务可见范围读取明细；影响目录只展示其有权限的信息，财务处理可交给财务角色完成。
- 待确认、正式有效、取消、回收站状态有明确报表纳入规则；订单金额、合同金额、计划成本、实际成本、实收和实付各自保持含义。
- 修改发生时间、下单日期、实际收付款日期分别保留。已确认对账及导出保留版本，新报表显示最新有效值并能追溯变更。
- 原项目/部门/供应商/分类筛选可继续使用；不恢复用户已否定的“维度汇总”功能。

## 11. 分批实施建议

每批独立验证，整套功能满足验收后再正式关闭报价业务；中间阶段不向用户展示一个只能创建、不能正确联动的半成品。

| 批次 | 工作与交付 | 完成条件 |
|---|---|---|
| 1. 统一核心规则 | 金额/折扣税额、并发编号、事务、状态与财务差额定义；建立输入与关联样本 | 创建、预览、保存、核对的计算一致，已收/已做边界可复现 |
| 2. 直接创建与统一编辑 | 订单创建 API、权限、列表按钮、创建/编辑共用组件、分组/导入/预览 | 无需报价可建立有效待确认订单；确认只创建所需任务且重试不重复 |
| 3. 完整关联变更与删除 | 完成订单变更、退款/预收、任务差额、外协、验收、合同、库存、成本、回收站 | 一个影响弹窗可准确解释并执行变更；无无法追溯的覆盖或漏账 |
| 4. 所有入口与历史切换 | AI/CDR、导入、选单、打印、菜单、旧接口、历史来源及权限适配 | 新业务不再生成报价；历史链接、附件、金额和来源仍可查询 |
| 5. 全链路验收与发布 | 测试副本迁移、真实角色浏览器流程、核对清单、兼容回滚演练 | 通过下表验收；上线前后余额和引用守恒，业务入口完成切换 |

不承诺仅改页面即可上线。已完成订单可修改与超收后能退款/转预收是本需求的重要组成部分，不能当作以后再补的小尾项。

## 12. 验收清单

1. 直接创建订单：已有/新客户、分组、面积与按件计价、优惠税额、Excel 导入、复制、附件，全部无需生成报价。
2. 金额样本：明细 1,000、优惠 100，总额 900；不修改内容保存后仍为 900。税率和各计价模式单独验证，报价与订单历史不重复计收。
3. 阶段样本：同一订单内有设计、制作和安装中的不同明细；改一条不能重置其他明细进度。
4. 数量样本：100 件已做 60，分别改 120、50；已完成量、待执行量、取消/追加范围均可解释，外协不重复派发。
5. 财务样本：已收后加价、减价至已收以下、分批收款、退款、转预收、合同跨单分配；总资金与分配守恒，不伪造实收实付日期。
6. 已完成订单：只改售价/说明保留完成；新增交付范围只补对应执行/验收任务，历史验收与完工凭据可查。
7. 已签合同、已确认对账、已结算外协、已出库：旧版本可查，差额事项能完成，并有来源、处理人和完成凭据。
8. 删除：无关联、有未执行任务、有实际成本/收付款/结算、删除最后明细、回收站恢复均覆盖；取消订单的真实款项和未结余额不从财务消失。
9. 安全与并发：两个用户同时编辑、预览后收款/完工/结算/出库、双击保存、断网重试、关联模块失败回滚；无重复订单、版本或任务，无半套更新。
10. 权限：销售、设计、制作、安装、财务和管理员分别验证；看不到的价格/成本不能从影响弹窗或 AI/CDR 接口泄露。
11. 旧入口：菜单、直达路由、API、AI、CDR、导入脚本不继续产生隐藏报价；旧报价来源、旧链接及历史附件仍有效。
12. 核对：上线前后订单应收、订单净收、待收/待退、实际支出、成本、利润、合同分配、任务/明细引用逐项对照。明确列出由状态口径改变造成的报表差异，不能只看总行数。

## 13. 建议确认的默认方案

统一使用“订单管理”；复用现有报价式编辑体验；先保存待确认、确认后安排执行；所有有效阶段允许修改，已取消订单恢复后修改；保存前一个弹窗说明关联影响；当前计划和汇总自动更新；历史实际记录通过版本及差异处理保持可追溯；删除进入回收站并停止未执行需求；收付款、成本及结算记录随真实处理结果变化；历史报价只读兼容，AI/CDR 和其他新业务统一写入订单。

本文件作为已确认设计依据；实际实现、验证和环境限制以实施报告为准，尚未部署。
