# 订单改造后的项目看板与用户权限衔接方案

日期：2026-10-26。状态：已在本地实施并验证，尚未提交和部署。实施记录见 `docs/order-first-2026-10-26/BOARD_PERMISSIONS_ALIGNMENT.md`。

检查基线：master `e501fa4`，包含当前工作区尚未提交的历史报价档案页面移除改动。本轮没有连接生产数据库，不能据此断言线上各角色已拥有或缺失某项权限。以下“现状”指代码行为，“建议”指下一轮实施范围。

## 1. 结论与边界

需要配套调整。现有独立项目看板和工作台内嵌看板已经按设计、制作、安装任务分别展示，订单变更也已有计划刷新、补做任务、范围快照与待处理事项。这些能力应继续复用。

本轮建议补齐三件事：看板准确表达订单当前需求与执行事实；页面、接口和按钮按同一权限判断；报价退役后角色配置与关联事项处理同步收口。总体风险为中高，主要风险是错误扩权、把订单修改误当作实际完工，以及漏展示任务。

范围：两个看板、订单相关权限与按钮、关联变更事项、角色目录/初始化、页面上下文、针对性验收。保留现有任务分配和员工绑定规则，不另建项目系统、审批中心或新的进度数据源。本方案不执行历史业务数据清理，也不批量重置角色权限。

## 3. 看板默认方案

### 3.1 保留现有结构，明确每列代表什么

采用“待确认/待安排、设计、制作、安装、已完成项目”。第一列复用现有 `pending_confirm/confirmed` 订单集合，不把它当作有执行进度的任务列。确认订单后按现有业务机制生成任务；多个明细可以处在不同阶段，同一订单也可以同时出现在多个阶段。

活动阶段一张卡片对应一个任务业务编号；完成列一张卡片对应一个订单。卡片标明关联订单、项目、客户/部门、执行明细摘要、负责人、当前进度、计划时间、外协及变更状态。金额仅对有价格权的人展示。

进入阶段任务查看和操作；看板不通过拖动卡片直接修改整单阶段，不恢复订单详情行级编辑/删除。

### 3.2 订单变更后的显示规则

| 订单操作 | 看板结果 |
|---|---|
| 修改名称、部门等当前信息 | 当前业务展示刷新；历史执行范围或凭据保留当时版本，明确标注历史信息 |
| 只改售价、优惠、税率 | 授权用户看到最新订单金额；执行进度不归零，已完成项目不因此重新进入执行列 |
| 新增明细或追加已完成数量 | 展示新生成的执行任务，标注补做/追加及范围；原完成事实保留 |
| 修改正在执行的数量、规格 | 展示当前任务范围和“订单已变更/待复核”，进入详情查看差异；沿用现有复核闸门 |
| 删除明细或订单 | 无效执行范围退出活动列，真实已做内容仍可追溯；整单删除后退出正常看板 |
| 已完成订单重新产生工作 | 退出“整单已完成”集合，对应补做任务进入执行列；原完成数量、时间和人员仍保留 |
| 恢复订单 | 只恢复本次取消允许恢复的范围，重新计算卡片；不复活独立取消或已结算的业务 |

数量以任务关联与范围快照为依据，不拿百分比倒算真实件数。明细单位不同则分行显示，不把平方米与件相加。旧数据实际完成量不明时显示“未记录”，不写成0或当前订单数量。

例如：原制作10件已完成，订单改成12件。原记录仍为完成10件，追加任务为2件；新任务进度从自己的范围计算。订单改成8件时，显示当前需求8件、历史已做10件及超做2件待处理，不能把历史已做直接改为8件。

### 3.3 完成记录与统计口径

- 已完成项目由当前整单状态判断；某一阶段做完只进入该阶段完成记录，不等于整单完成。
- 完成详情区分“当前需求数量”和“本次/累计实际完成数量”，执行事实取范围快照和完成记录；未知历史数据标注缺失。
- 看板统计分别显示可见订单数、未完成任务数、完成项目数。任务平均进度明确为任务口径，不标成项目总体进度。
- 员工完成列标明本人参与范围；管理人员全量完成视图继续单独要求全量权限。
- 金额按订单去重汇总，不能把同一订单在三个阶段卡片上的金额相加。

### 3.4 刷新、分页与异常

两个看板共用同一套取数、可见列、统计和变更提示规则。每列支持继续加载或分页，总数由服务端在授权范围内计算，不以第一页长度代替。过滤、计数和分页尽量在数据库完成，关联信息批量读取，避免逐任务查询造成等待。

保存订单、完成任务、登记复核、删除/恢复后刷新相应数据；页面重新聚焦或返回时也刷新，不新增常驻后台服务。接口失败单列显示“加载失败/重试”，不把失败显示成“暂无任务”。无权限的列隐藏，缺少前置权限时给可解释的提示。

## 4. 权限默认方案

### 4.1 入口、数据、字段、操作分别判断

沿用现有原子权限，不新增一个包揽所有能力的“项目管理员”权限。

| 区域/操作 | 建议判断 |
|---|---|
| 看板入口 | 下列任一数据源可用即可进入；只请求和展示授权的数据源 |
| 待确认/待安排订单列 | `order:read`；价格另查 `order:view_price` |
| 设计/制作/安装活动列 | `task_queue:read` 加对应阶段 `*:read`，并应用现有订单任务可见范围 |
| 已完成项目列 | `task_completion:read` 加至少一个可读阶段；本人/全部继续按完成统计范围授权 |
| 全量活动任务 | 单独的 `task_queue:view_all`；现有任务分配管理的全量能力保持兼容，不给普通读权限隐式扩权 |
| 完整订单创建/编辑 | 对应 `order:create/update`、`order:read`、订单及明细价格权限；后端和页面一致校验 |
| 确认订单 | 复用 `order:change_status`，补齐 `order:read` 前置条件，保留状态校验和幂等 |
| 删除订单 | 继续要求 `order:delete` 与价格读取，经过现有影响预览；默认仍由管理员处理 |
| 分配任务、阶段操作 | 分别按现有分配/阶段权限与对象范围判断，不因能读看板就能操作 |
| 收款、退款、预收分配 | 沿用订单读取与资金读写权限；订单编辑权不能替代资金权限 |

完整商业订单写入能力应纳入现有敏感权限组合规则；任务执行人员继续通过任务页操作执行内容。仅修改非价格执行信息不应靠把脱敏后的完整订单重新提交来实现。

详情页编辑按钮需同时满足“有编辑权”和“当前订单业务允许编辑”；列表、详情、编辑器、直达路由、导入、预览/批量接口均须一致。权限更新后刷新服务端用户档案；后端每次操作仍作权威判断。

### 4.2 关联变更事项按业务分工处理

移除事项查看/处理必须拥有 `order:update` 的统一前置条件。改为逐项检查相关业务的读取/处理权限与该对象可见范围，并返回每项允许的动作及不可操作原因。

- 设计、制作、安装事项：由具备相应任务操作权且能看该任务的人处理。
- 外协事项：由具备外协读取/更新权限的人处理，不要求其能修改整个订单。
- 资金及成本事项：由具备对应财务权限的人处理；成本权限映射对齐实际成本API，修复未定义权限码。
- 合同、验收、对账事项：与各自模块当前实际读写/确认权限对齐。
- 销售/订单负责人可看协调摘要；没有价格、成本或财务权限时，不在摘要、原因或编号链接中泄露受限内容。
- “登记处理结果”不能绕过实际退款、复核或单据变更。超收未处理等阻断继续有效；记录处理人、时间、结果和可追溯凭据。

不新增通用待办中心，入口仍在订单变更面板和相关任务详情；看板显示待处理标记并跳转至授权页面。

### 4.3 默认岗位边界

| 岗位 | 默认能力 | 继续分开的能力 |
|---|---|---|
| 管理员 | 全部业务配置、订单删除、角色管理 | 所有操作仍记录审计 |
| 销售 | 新建/编辑/确认订单、查看价格、跟进并分配任务 | 删除维持独立授权；不自动增加执行或额外财务权限 |
| 经理 | 全部任务进度与完成统计、订单基础信息只读 | 默认不显示价格、成本，不编辑订单和任务 |
| 设计/制作/安装 | 在现有可见订单范围内读取授权阶段、操作本岗位阶段、查看本人完成记录 | 默认不授予商业订单编辑或价格/财务；现有跨阶段只读能力保留 |
| 财务 | 订单与金额只读、收退款/预收、财务关联事项处理 | 不为处理财务事项授予订单编辑；活动任务列另行授权 |
| 外协管理员 | 外协业务及相关变更处理 | 不自动获得整个内部项目和订单的操作权 |
| 自定义角色 | 按具体权限及前置依赖组合 | 不按角色名称或旧报价权限一键扩权 |

现有“订单未指定可见员工时，符合权限者可见；指定后按员工范围限制”的规则继续保留。本轮不把它改成仅 `assigned_to` 本人可见，也不新增部门数据隔离规则。

### 4.4 报价权限退役与存量角色衔接

1. 报价创建、编辑、删除、确认、转单等停用写权限从日常配置和默认权限包移除，标为退役；历史读取兼容权限收纳到“历史兼容”，保留必要旧链接/来源读取。
2. 定价规则、客户协议价、图稿采集与AI辅助功能按仍存在的能力命名和授权，不因前缀带 quote 就全部删除。
3. 权限目录、种子脚本和角色管理共用退役状态规则，初始化不得再把退役项设回 active，也不得重新追加退役默认授权。
4. 发布前只读导出生产角色、用户多角色权限并集、前置缺失和冲突，形成逐角色差异清单。检查默认销售与自定义业务角色是否已有订单创建/修改/确认所需能力。
5. 旧 `quote:create/update` 只作为迁移建议依据，不自动获得订单编辑、删除、资金处理或全量任务权限。实际补权按角色职责完成并保留前后快照；已有只读角色继续只读。
6. 不删除权限主键、角色主键或历史授权审计，不重建用户、不重设密码；权限回退使用快照定向恢复。

## 5. 实施顺序与数据保护

1. 只读盘点：线上角色配置、用户权限并集、订单/任务范围、完成快照缺失、超过200条的列及历史重复完成关联。输出待修复清单，不根据同名项目猜测关联。
2. 先修授权衔接：入口/API/按钮一致、商业订单写入前置、关联事项分工、退役目录与种子脚本、用户档案刷新。
3. 补看板展示：变更/补做标记、执行范围、当前与历史数量、明确统计口径，两个看板共用规则；修复路由/AI页面上下文。
4. 完成取数：分页、授权总数、批量关联加载、列级失败/重试及业务操作后的刷新。
5. 隔离环境验收后发布；权限变动前备份相关配置并核对差异，记录实际发布版本。生产使用当前实际部署方式，不因仓库有Docker配置就切换部署架构。

优先复用现有数据库字段和权限状态字段；只有验收证明现有快照不足以保存必须的事实时才提出最小增量迁移，补做备份、演练和回滚说明。缺失历史量不猜测回填。上一轮报告的重复历史完成关联需按业务事实复核，本轮不自动删除。

## 6. 验收场景

| 场景 | 必须达到的结果 |
|---|---|
| 保存待确认订单 | 进入待确认列，无执行任务、无实际完工统计 |
| 确认及重试 | 进入实际阶段，仅生成必要任务，无重复卡片 |
| 同单A设计、B制作、C安装 | 三阶段并存、进度独立，订单金额不重复汇总 |
| 完成10件后追加2件，再追加1件 | 每次只增加必要的新范围；原10件完成事实不变；看板能辨认补做 |
| 已完成数量从10改为8 | 当前需求与已做分别展示，差额事项可追踪，完成历史不被覆盖 |
| 只改售价 | 仅有价格权的人看到新金额；进度、已付款及历史完成事实不变 |
| 删除部分明细、整单删除与恢复 | 活动范围、取消范围、回收站和恢复范围一致，无失效卡片 |
| 自定义角色有阶段读取、无队列读取 | 无失败接口被假装为空项目；可见入口/列和缺失提示符合权限组合 |
