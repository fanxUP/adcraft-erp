# 订单级三阶段资料源设计方案

## 1. 对需求的理解

本次调整不是简单地把 `task_id` 改成可选，而是要改变附件的业务归属：

1. 订单是三类资料的唯一业务源头。
2. 订单下固定有三个阶段资料区：
   - 设计：任务附件；
   - 制作：任务附件；
   - 安装：现场照片与视频。
3. 附件归属于“订单 + 阶段”，不归属于某一张设计、制作或安装任务。
4. 是否已经创建任务、任务是否完成、任务是否被删除或重新生成，都不能决定订单资料能否上传、下载或删除。
5. 设计任务、制作任务、安装任务详情页只是订单资料的不同入口和阶段过滤视图；它们调用订单资料接口，不复制资料，也不再建立任务级附件关系。

因此，正确的数据关系是：

```text
订单 O
├── 设计资料集合
├── 制作资料集合
└── 安装现场媒体集合

设计任务详情 ─┐
制作任务详情 ─┼─> 同一个订单资料服务（按阶段过滤）
安装任务详情 ─┘
```

任务只负责提供进入页面时的上下文、当前阶段和权限判断，不再是附件的所有者。

## 2. 当前实现与问题根因

当前版本已经增加了订单详情的“任务资料”卡片，但仍然是任务级模型：

- `OrderTaskAttachmentService` 的上传方法要求 `task_type + task_id`；
- 服务端通过 `_get_task()` 校验任务存在且属于订单；
- 列表响应按设计、制作、安装任务逐张分组；
- 订单详情的前端上传区域绑定到某一张任务；
- 设计、制作、安装任务详情页仍直接调用 `/attachments/upload`，使用 `related_type=*_task` 和任务 ID；
- 附件的订单归属是通过“附件 -> 任务 -> 订单”间接推导的。

这会带来几个实际问题：

- 订单还没有任务时，无法在订单中先上传资料；
- 任务被删除、合并或重新生成后，附件展示依赖旧任务关系；
- 同一阶段存在多张任务时，同一组订单资料容易被重复展示或分散；
- 不同入口各自维护上传、下载、删除逻辑，权限和展示容易再次分叉。

## 3. 推荐的数据方案

### 3.1 继续复用通用附件表，增加订单级可选归属字段

不新建第二套物理文件表，也不搬动现有上传文件。对现有 `attachments` 表增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `order_id` | UUID，可空，外键指向 `business_documents.id` | 订单级附件所有者；新资料的权威归属字段 |
| `stage` | 字符串，可空 | `design`、`production`、`installation` 三个阶段 |

新资料的约定为：

- `order_id` 必填；
- `stage` 必填且只能取三个阶段之一；
- `related_type='order_stage'`、`related_id=order_id` 仅用于兼容通用附件表的非空字段约束；
- `category` 继续表示文件类型，例如 `image`、`video`、`pdf`、`document`、`cad`、`archive`，不拿它表示业务阶段；
- `file_path` 继续使用随机文件名和现有安全目录；
- 不要求 `task_id`，也不新增任务外键。

`order_id + stage` 是新的业务查询键。`related_type/related_id` 不再作为订单三阶段资料的权限依据。

这样做的好处是：

- 现有通用附件能力和物理文件无需迁移；
- 订单级资料可以独立于任务存在；
- 订单、任务、完成项目详情可以共享同一套数据；
- 其他模块的车辆、订单明细、报价等附件仍按原有关系工作，不被改写。

### 3.2 历史数据迁移

为当前已经上传的设计、制作、安装任务附件补齐订单归属：

- `related_type='design_task'`：通过 `design_tasks.document_id` 回填 `order_id`，`stage='design'`；
- `related_type='production_task'`：通过 `production_tasks.document_id` 回填 `order_id`，`stage='production'`；
- `related_type='installation_task'`：通过 `installation_tasks.document_id` 回填 `order_id`，`stage='installation'`；
- 保留历史 `related_type/related_id`，便于旧接口兼容和追溯；
- 订单明细、车辆、报价等其他附件不参与迁移；
- 找不到所属任务或订单的孤儿记录只统计并报告，不静默删除、不移动文件，后续可人工归档。

迁移必须支持 dry-run、幂等执行和迁移前后数量核对。只补充元数据，不复制、不重命名、不删除物理文件。

### 3.3 索引与一致性

增加以下约束和索引：

- `(order_id, stage, created_at)` 索引，支持按阶段读取和时间排序；
- `order_id` 外键仅限制真实订单，不改变软删除语义；
- `stage` 使用数据库检查约束或服务端白名单校验；
- 新资料必须同时有 `order_id` 和 `stage`，旧模块资料允许继续为空；
- 删除订单任务不会级联删除订单资料；订单软删除后资料保留但不可访问，订单恢复后重新可见。

## 4. 订单源接口

### 4.1 规范接口

建议将订单接口命名为“订单资料”，不再把任务关系写进核心接口名：

```text
GET    /api/v1/orders/{order_id}/attachments?stage=design|production|installation
POST   /api/v1/orders/{order_id}/attachments
GET    /api/v1/orders/{order_id}/attachments/{attachment_id}/file?download=false
DELETE /api/v1/orders/{order_id}/attachments/{attachment_id}
```

接口规则：

- `stage` 不传时返回订单下三个阶段的资料集合；上传时必须传 `stage`；
- 上传表单只需要 `stage + file`，不需要 `task_id`；
- 下载和删除只用 `order_id + attachment_id`，服务端按 `order_id` 精确校验附件归属；
- 响应只返回文件名、类型、分类、大小、上传时间、上传人和逻辑操作信息，不返回服务器物理路径；
- 图片和视频使用同一个受保护的文件接口预览，其他文件按文件名、类型、大小、上传时间提供预览或下载；
- 返回结构按阶段组织，不再返回任务列表、任务数量或任务状态作为附件条件。

推荐的响应形状（当前实现保留 `groups` 作为兼容字段名）：

```json
{
  "order_id": "...",
  "groups": [
    {
      "stage": "design",
      "label": "设计任务：任务附件",
      "attachment_count": 0,
      "attachments": []
    },
    {
      "stage": "production",
      "label": "制作任务：任务附件",
      "attachment_count": 0,
      "attachments": []
    },
    {
      "stage": "installation",
      "label": "安装任务：现场照片与视频",
      "attachment_count": 0,
      "attachments": []
    }
  ]
}
```

### 4.2 兼容接口

当前已经发布的 `/orders/{order_id}/task-attachments` 和旧的 `/attachments/upload` 不立即删除：

- 保留一个过渡版本；
- 旧接口内部改为“任务上下文 -> 订单 ID + 阶段 -> 订单资料服务”的适配器；
- 旧接口的 `task_id` 仅用于兼容调用方和建立可见性上下文，不能作为资料所有权或删除依据；
- 新前端不再调用旧接口；
- 经过一轮发布周期、日志确认无旧客户端调用后，再清理旧接口和旧的任务级附件写入路径。

这样可以避免前端切换期间形成两套数据源。

## 5. 权限与数据范围

### 5.1 权限矩阵

保持用户已经确认的规则，同时兼容设计、制作、安装人员不能看价格的要求：

| 入口 | 查看/下载 | 上传/删除 | 可见阶段 |
| --- | --- | --- | --- |
| 订单详情 | `order:read` | `order:read` | 三个阶段 |
| 设计任务详情 | `design_task:read` | `design_task:update` | 设计 |
| 制作任务详情 | `production_task:read` | `production_task:update` | 制作 |
| 安装任务详情 | `installation_task:read` | `installation_task:update` | 安装 |
| 管理员 | 现有管理员权限 | 现有管理员权限 | 权限范围内的全部 |

说明：用户已明确“有查看订单权限的用户可以上传、下载、删除”，因此 `order:read` 在订单入口继续同时授予三类订单资料的这三个操作。任务入口只开放对应岗位阶段，避免设计人员通过资料接口读取或操作制作、安装资料。

### 5.2 服务端最终校验

服务层增加统一的 `authorize_order_attachment()` 规则：

1. 订单必须是未软删除的 `doc_type='order'`；
2. 订单入口必须通过现有订单可见性范围；
3. 任务入口必须通过对应任务的可见性范围，且任务的 `document_id` 必须等于请求的 `order_id`；
4. 任务入口的阶段由服务端路由固定，不能相信客户端传入的任意阶段；
5. `order_id` 不存在或不属于当前用户范围时，统一返回不存在/无权访问，不泄露订单是否存在；
6. 订单级附件查询永远以 `attachments.order_id` 为准，不因为某一张任务被删除、完成或改派而改变；
7. 没有价格权限的任务响应继续不返回订单金额、单价、小计、成本或利润字段。

第一期不新增重复的 `order_attachment:*` 权限，避免权限组合变复杂；如果后续确实需要把订单资料操作从 `order:read` 中独立出来，再单独增加模块化权限并做角色迁移。

## 6. 前端入口设计

### 6.1 统一组件

将资料展示统一收敛到可复用的 `OrderTaskAttachments.vue` 阶段组件：

- `orderId`：必填；
- `stage`：`design | production | installation`；
- `readonly`：完成项目详情使用；
- `compact`：任务详情页使用。

订单详情页渲染三个阶段区，每个阶段只有一个资料集合和一个拖拽上传区，即使该阶段暂时没有任务也可以操作。

设计、制作、安装详情页各渲染同一个组件的对应阶段。任务 ID 即使作为可选的入口
校验上下文传入，也不参与附件归属；订单级入口完全不需要任务 ID。

完成项目详情页也读取同一个订单级资料源，三个阶段各显示一行/一个只读区，不再按任务数量重复渲染安装资料。

### 6.2 保留的交互能力

- 拖拽或点击选择，支持批量上传和单个失败重试；
- 图片显示缩略图，点击放大并保持较慢、可控的缩放速度；
- 视频显示媒体缩略图，点击打开播放器；
- PDF、Word、Excel、CAD、压缩包等不强制生成缩略图，显示文件名、类型、大小、上传时间，并提供预览或下载；
- 删除需要二次确认；
- 上传、删除成功后订单详情和任务详情刷新同一资料集合，保证跨入口一致。

### 6.3 空状态和状态文案

不再显示“暂无设计任务，所以无法上传”这类误导信息。无任务时显示：

```text
当前暂无设计任务，但仍可上传订单设计资料
```

完成、取消或删除任务不会锁住订单资料；订单被软删除或取消时是否只读沿用订单生命周期规则，不使用任务状态判断。

## 7. 文件、安全与审计

- 继续复用服务端 magic-byte、MIME、扩展名和大小校验；前端 `accept` 只做体验提示，不能作为安全边界；
- 设计/制作允许 JPG、PNG、WEBP、视频、PDF、Word、Excel、CAD、压缩包；安装只允许 JPG、PNG、WEBP、MP4、WEBM、MOV；
- 继续使用随机存储文件名、受限目录权限和 `confined_path`，不使用用户文件名拼接路径；
- 预览和下载必须通过带认证的订单文件接口，不把 `file_path` 或可绕过权限的公开上传 URL 放进响应；
- 删除前后都校验订单级附件归属，不能凭猜测的附件 ID跨订单读取或删除；
- 操作日志改记为订单资料的新增/删除，包含订单 ID、阶段、附件 ID、文件名、大小、类型、操作人和入口上下文；
- 不将 JWT、Cookie 或其他认证信息写入附件 URL 或普通访问日志；
- 不新增第三方依赖，不执行压缩包解压、不解析 CAD 内容，降低恶意文件处理面。

## 8. 不纳入本期

- 不改变订单状态、任务状态、任务进度、任务分配和外协规则；
- 不把订单资料细分到订单明细，除非后续另行提出明细级资料需求；
- 不让任务自动生成或删除订单资料；
- 不做服务器端缩略图服务、对象存储迁移和在线 Office/CAD 编辑；
- 不在完成项目详情中增加上传、删除、状态变更等写操作；
- 不删除其他模块的通用附件和历史文件。

## 9. 主要取舍

本方案选择“在现有通用附件表上增加订单级字段”，而不是新建 `order_attachments` 独立表：

- 优点：物理文件不搬迁，已有附件表和文件校验可以复用，回归范围较小；
- 代价：通用附件表会同时存在历史任务关系和订单级关系，必须由常量、统一仓储查询和兼容适配器隔离，禁止在业务代码中散落字符串判断；
- 如果未来订单资料需要版本、审批、明细归属或复杂协作，再升级为独立资料表；当前阶段不提前引入该复杂度。
