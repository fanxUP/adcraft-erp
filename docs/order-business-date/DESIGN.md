# 订单业务下单日期设计

## 1. 目标与边界

订单需要同时表达两个不同事实：

- `created_at`：系统实际写入数据库的时间，只用于审计、并发版本和技术追踪，不能被业务页面修改。
- `order_date`：订单业务上的下单日期，使用北京时间的自然日，允许经过受控流程修正。

本阶段只处理订单业务日期，不修改订单号、不修改报价日期、不重置任务、不改付款/成本/验收/附件事件时间，也不物理删除任何历史事实。

## 2. 数据与初始化

- 在 `business_documents` 增加可空 `order_date DATE`；报价记录保持 `NULL`。
- 迁移时仅对 `doc_type = 'order'` 的历史记录按现有 `created_at` 的业务日回填；线上 `created_at` 为 UTC 存储的无时区时间，回填先转换为 `Asia/Shanghai` 再取自然日，并增加订单日期索引与订单非空约束。
- 常规报价转订单、CDR 报价转订单和直接创建订单都显式初始化北京时间业务日。
- 订单号仍是创建/转单时生成的编号，修改业务日期不重新编号。

## 3. 变更流程

采用独立接口，不把日期混进订单明细批量编辑：

1. `POST /orders/{id}/order-date/preview` 返回变更前后日期、系统创建时间、订单状态、风险和影响目录，并签发短时预检凭证。
2. `PATCH /orders/{id}/order-date` 在行锁、版本校验和签名校验通过后写入日期，生成版本快照和操作日志。

请求必须包含原因和 `expected_updated_at`；正式提交必须携带预检凭证。日期不能晚于北京时间今天，日期未变化直接拒绝。

权限边界：

- 需要 `order:change_date`；默认授予管理员和销售角色，定制角色由管理员单独配置。
- 已完成、已取消订单的日期修正只允许 `system:super_admin`。
- 已收款、有成本或命中已确认对账单的订单属于高风险，必须在预检后明确确认；这些事实本身不会被改写。

## 4. 关联影响

- 订单列表排序、经营日报/月报订单口径、验收单订单日期、客户账期逾期天数和对账单覆盖判断使用 `order_date`。
- 付款的 `paid_at`、成本的 `expense_date`/记录时间、任务的 `created_at`/完成时间、验收事实时间、附件上传时间继续使用各自原始字段。
- 日期变更不触发任务重建、任务状态回退、负责人变更、进度重算、付款重分配或成本重算。

## 5. 并发、审计与回滚

- 预检和提交使用 `updated_at` 乐观锁；提交时再锁订单并重新计算风险目录。
- 预检凭证绑定订单、目标日期、原因、操作者、订单版本和影响目录，10 分钟后过期。
- 版本快照记录 `change_type=order_date_change`、前后订单快照、系统创建时间、影响目录和原因；操作日志使用订单更新动作。
- 数据迁移是单个加法迁移，降级删除新增列/索引/约束；生产执行前必须备份并在副本 dry-run。
