# 员工建档自动开通登录账号设计

## 1. 规划状态与任务分类

- 状态：方案已落地为代码，生产数据迁移和上线验证待发布窗口执行。
- 类型：员工主数据、登录认证、账号生命周期和后台管理入口调整。
- 风险模式：`STRICT`。
- 风险级别：高。改动会影响登录入口、密码初始化、角色权限、任务执行人归属、历史审计和生产账号数据。

## 2. 结论：想法合理，但不能只改页面

这个想法总体合理，而且比“员工档案和登录账号分别新增、再手工绑定”更符合实际管理流程：

1. 员工档案成为人员身份的主入口，减少漏建账号、错绑账号和姓名/工号不一致。
2. 工号是公司内部稳定标识，作为登录名比随意填写用户名更容易培训和维护。
3. 用户管理可以收敛为角色、启停状态、密码和权限维护，职责更清晰。
4. 当前系统已经有 `employees.user_id`、未删除员工账号唯一索引，以及任务执行和完成统计按员工账号绑定解析的逻辑，具备渐进改造基础。

但以下做法不够安全或不完整：

- 只删除前端“新增用户”按钮而保留 `POST /users/`，仍然可以通过接口制造没有员工档案的账号。
- 直接把数据库列 `users.username` 改名为 `employee_no`，会扩大迁移范围，也会影响管理员等系统账号。
- 把工号、手机号、身份证号或生日当作永久初始密码，会造成明显的账号安全风险。
- 仅按部门自动推导角色，会把人事组织信息误当成授权规则；当前角色是 RBAC 权限集合，部门和角色不是严格一一对应。
- 不制定历史账号迁移规则，会出现“新员工必须用工号登录、老员工仍用旧用户名”的双轨状态。

推荐结论：保留现有用户表和员工表，保留 `employees.user_id` 绑定关系，把“员工新建”改造成唯一的人员账号开通流程；用户管理保留账号治理能力，但不再提供普通账号创建入口。

## 4. 目标身份模型

### 4.1 主数据职责

继续使用两张表，各自职责不变：

- `employees`：工号、姓名、手机号、部门、岗位、在职状态和人事资料，是员工身份主数据。
- `users`：认证凭据、角色、权限、邮箱、登录启停状态和密码变更状态，是系统访问控制数据。
- `employees.user_id`：员工与登录账号的一对一关系；保留现有 UUID，不改成把工号直接写入订单、任务和历史表。

工号与登录名的关系为：

```text
employees.employee_no == users.username
employees.user_id    == users.id
```

这里的等式只对员工账号成立。`admin` 等系统账号可以作为明确的例外保留，不强行伪造员工档案。

### 4.2 关键不变量

1. 新建在职员工成功后，员工和账号在同一个数据库事务中成功或同时回滚。
2. 新员工账号的 `username` 必须等于最终保存的 `employee_no`。
3. `employee_no` 全局唯一；账号创建后工号不可修改。当前 `EmployeeUpdate` 已没有开放 `employee_no`，应继续保持这个边界。
4. 新员工账号不能通过用户管理页面直接创建，必须从员工建档流程产生。
5. 角色仍由管理员明确分配，不根据部门名称、岗位名称或姓名猜测。
6. 不删除或重建已有用户 UUID，以免破坏订单销售人、任务执行人、操作日志、通知和聊天等历史引用。
7. 离职、停职、员工档案停用或删除后，账号不能继续作为在职任务执行人使用；历史业务数据保留。

## 5. 推荐的业务流程

### 5.1 新建员工并自动开通账号

1. 管理员填写员工资料、最终确认工号和系统角色。
2. 后端校验工号格式、唯一性、在职状态和角色组合。
3. 后端创建员工档案。
4. 后端创建用户：
   - `username = employee_no`
   - `real_name = employee.name`
   - `phone = employee.phone`
   - `is_active = employee.is_active and employment_status == "active"`
   - `must_change_password = true`
   - 角色来自本次明确选择的 `role_ids`
5. 写入 `employees.user_id`，创建用户偏好记录。
6. 事务提交后返回员工、工号、账号状态和一次性的初始密码提示信息。

如果任一校验、角色设置或账号写入失败，整次创建回滚，不能留下只有员工没有账号，或只有账号没有员工的半成品。

### 5.2 初始密码

推荐支持两种输入方式，但默认采用随机临时密码：

- 页面允许管理员手工设置一个符合密码策略的初始密码；或
- 页面留空时由后端使用安全随机数生成一次性临时密码。

无论哪种方式：

- 明文密码不写入数据库、操作日志、应用日志或永久文档。
- 新账号必须设置 `must_change_password = true`，第一次登录只能先改密。
- 随机临时密码只在创建成功响应或一次性结果弹窗中显示；关闭后不能再次从系统读取，只能走“重置密码”。
- 不使用工号、身份证号、手机号、生日等可猜测信息作为默认密码。

### 5.3 角色分配

推荐在“新建员工”表单的“系统账号”区域增加角色选择，并在后端复用现有 `UserService._validate_roles()` 的组合校验。

- 不做“部门 = 角色”的隐式映射。
- 对需要登录的在职员工，至少选择一个业务角色；如果确实存在只建档、不允许登录的人员，应另行增加明确的“开通登录”选项，而不是靠空角色产生隐含规则。
- 用户管理继续允许管理员调整角色；员工档案编辑不直接修改角色，避免人事变动意外扩大系统权限。

### 5.4 账号生命周期

推荐采用“员工状态只能触发停用，不能自动恢复账号”的安全策略：

| 事件 | 员工档案 | 登录账号 | 任务/历史数据 |
| --- | --- | --- | --- |
| 新建在职员工 | active | 创建并启用，首次登录强制改密 | 可在符合角色和岗位规则时分配 |
| 新建停职/离职档案 | 非 active | 创建但停用 | 不进入可执行员工列表 |
| 员工改为停职/离职或停用 | 保留档案 | 自动停用并使现有 token 失效 | 历史任务和统计保留 |
| 员工恢复在职 | active | 不自动恢复，管理员明确启用 | 启用后重新按既有规则参与 |
| 员工软删除 | deleted | 停用，不删除用户记录 | 保留历史审计和业务引用 |
| 用户管理手工停用 | 员工不变 | 保持停用 | 不影响历史数据 |

员工账号不能在用户管理中“删除后再建一个同工号账号”来绕过历史关系；如需重新开通，应优先恢复/重置原用户，保留原 UUID 和审计链。

## 6. 登录与界面方案

### 6.1 登录

- 登录页字段文案从“用户名”改为“工号”，占位符改为“请输入工号”。
- 后端物理查询仍可使用 `users.username`，因为新建账号的值就是工号；不需要为了文案改动而重命名数据库列。
- 对已绑定员工账号，认证时同时检查用户启用状态和员工有效在职状态。
- `admin` 等系统账号保留明确的系统账号例外；不要求为了本次改造把管理员强行变成员工。
- 认证和 `get_current_user` 都必须排除 `deleted_at`，并在账号/员工被停用后拒绝旧 token。

### 6.2 用户管理

用户管理不再负责“创建人员身份”，而负责账号治理：

- 删除页面右上角“新增用户”按钮。
- 删除新建用户对话框、`createUser` 前端调用和普通账号创建表单。
- 列名由“用户名”改为“工号”；员工账号显示关联员工工号，系统账号显示“系统账号”。
- 工号不可编辑。
- 保留角色编辑、账号启停、密码重置、查询和关联员工展示。
- 员工姓名、手机号等身份字段以员工档案为准；建议用户管理显示为只读或由后端同步，邮箱可以继续作为账号附属资料维护。
- 对关联员工账号，不建议保留“删除”作为常规动作；推荐用“停用”保留账号历史。系统账号和过渡期遗留账号可按单独规则治理。

后端也要关闭或废弃 `POST /api/v1/users/`，返回明确提示“请在员工管理中新建员工”，不能只依赖前端隐藏按钮。过渡期可以保留内部创建服务供员工开通流程调用，但不再暴露为普通管理接口。

### 6.3 员工管理

- 新建员工表单移除“选择已有登录账号/手工绑定”控件。
- 增加“系统账号”分组：角色、初始密码策略、账号是否启用的只读结果。
- 保存成功后展示“已自动创建账号：工号 xxx”；如果使用随机临时密码，仅一次性展示。
- 编辑员工时显示关联账号和账号状态，账号角色/密码仍通过用户管理维护。
- 保留过渡期管理员专用的绑定/修复能力，用于历史数据整理，但不出现在普通建档流程。

### 6.4 个人中心和移动端

桌面个人中心、移动个人中心中的“用户名”统一改为“工号”。返回 API 可以继续保留 `username` 技术字段以兼容现有状态管理，但对用户展示优先使用员工工号。

## 7. 历史数据迁移策略

本次代码不在应用启动时自动执行生产迁移。上线前必须先做只读盘点和干跑报告，至少分类以下数据：

1. 已绑定员工且 `users.username == employees.employee_no`：无需改名，只做状态和密码策略检查。
2. 已绑定员工但用户名不等于工号：保留原用户 UUID、角色、密码和业务引用，只把用户名改成工号；冲突时阻断，不自动覆盖。
3. 在职员工没有绑定账号：列入“待开通账号”清单。是否批量创建要单独确认初始密码分发方式，不在部署迁移中偷偷创建大量可登录账号。
4. 用户没有绑定员工：`admin` 等系统账号保留；其他账号标为“遗留账号待处理”，不自动猜测对应员工。
5. 工号与用户名之间发生重复或大小写/空白规范化冲突：先人工处理，迁移脚本不得选择一个覆盖另一个。

推荐分两步：

- 第一步只读检查、备份和生成报告；报告通过后再迁移已确定的一对一绑定账号。
- 第二步由管理员授权，分批为明确的在职员工补建账号，并逐人确认初始密码/强制改密状态。

迁移过程中不删除已有账号、不改写订单或任务历史、不替换用户 UUID。旧操作日志中的历史操作者名称允许保持历史快照。

## 8. 主要风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 工号与现有用户名冲突 | 迁移前 SQL 盘点；冲突即阻断；不覆盖账号 |
| 同时新建两个员工生成相同工号 | 对工号生成增加数据库锁/序列或唯一冲突重试；不能只依赖前端 |
| 创建员工成功、创建用户失败 | 员工与用户在同一个请求事务中完成，失败整体回滚 |
| 只删按钮仍可调用接口 | 后端撤销/阻断 `POST /users/`，增加 API 回归测试 |
| 默认密码泄露 | 随机临时密码、只显示一次、强制改密、日志脱敏 |
| 部门变更导致权限错误 | 角色不从部门推导；角色由管理员明确维护 |
| 离职账号继续使用 | 员工状态变更停用账号、token 失效、认证再次校验 |
| 删除重建破坏任务历史 | 账号软停用，不删除/重建用户 UUID |
| 旧账号双轨登录 | 先完成绑定/用户名盘点，再决定兼容窗口和迁移批次 |

## 9. 非目标

- 不合并 `employees` 和 `users` 表。
- 不改变订单、报价、任务、工资、考勤和完成统计的业务规则。
- 不根据部门或岗位自动授予系统权限。
- 不在应用启动脚本中执行生产数据库迁移、批量创建账号或重置现有密码；历史用户名迁移必须经过备份和干跑门禁。
- 不删除 `admin` 等系统账号，也不强制把系统账号伪装成员工账号。
- 不把明文密码保存到员工表、用户表、备份外的文档或日志。

## 10. 推荐默认决策

如果没有额外业务要求，实施时采用以下默认值：

1. 新建在职员工必须自动创建一个用户，登录名等于工号。
2. 工号创建后不可修改；物理列仍叫 `users.username`，仅调整业务文案和取值规则。
3. 初始密码由管理员输入或系统随机生成，统一首次登录强制改密，绝不使用工号作为密码。
4. 创建员工时明确选择系统角色，不根据部门自动映射。
5. 用户管理保留编辑角色、停用/启用、重置密码和查询，不保留普通新增用户能力。
6. `admin` 作为系统账号例外保留；其他遗留无员工账号先盘点再处理。
7. 员工离职/停职自动停用账号，恢复在职后需管理员明确启用。
