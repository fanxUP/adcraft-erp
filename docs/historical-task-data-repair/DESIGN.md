# 设计、制作、安装历史异常数据修复方案

## 1. 当前结论

- 类型：生产历史业务数据修复规划。
- 模式：`STRICT`。
- 风险：高。涉及订单状态、三阶段任务卡、订单明细关联、回退历史和完成统计；错误修复可能让订单重复进入阶段、误显示为完成，或丢失审计事实。
- 本轮状态：H-001 已完成修复；本次复核并完成 H-002 的明细状态纠偏，不删除历史记录。
- 范围：聚焦此前已经讨论过的设计、制作、安装任务链历史异常。财务、权限、附件物理文件和员工资料不在本轮自动修复范围。

## 2. 目标与非目标

### 2.1 目标

1. 找出历史版本造成的重复任务卡、阶段回退后未重新进入、任务进度/订单状态不一致等问题。
2. 只对能够由稳定的订单明细、任务关联和状态时间线确定的记录自动修复。
3. 对无法证明真实业务意图的记录输出待确认清单，不猜测、不批量覆盖。
4. 保留任务历史、状态日志、操作日志、附件和外协/车辆等关联；每次修复都有前后快照和审计记录。
5. 修复后重复执行是幂等的，且可以用修复前数据库备份恢复。

### 2.2 非目标

- 不批量把所有 `cancelled` 历史记录恢复成可执行任务。
- 不把历史任务日志中出现过的完成状态直接当成当前状态。
- 不凭项目名称、客户名称、员工姓名或任务编号猜测订单明细归属。
- 不为旧的整单任务强行补造逐条明细进度、执行人或完成时间。
- 不删除 `task_item_status_logs` 中引用已删除任务的历史记录。
- 不修改上传文件本身；若后续合并任务卡，只调整数据库中的任务归属引用。
- 不新增 Alembic 迁移、第三方依赖或通知渠道。

### 4.3 现有重复任务修复工具的边界

仓库已有 `backend/scripts/repair_duplicate_stage_tasks.py`，默认仅处理“旧版本自动按明细拆卡、卡片仍是未修改的自动任务形态”的重复组。线上对设计、制作、安装分别执行只读预览均未发现符合该工具筛选条件的组。

这不表示数据库不存在重复任务，而是说明当前 H-004/H-005 不符合该工具的安全自动合并条件。后续若要合并，必须先单独生成合并计划，再由管理员确认保留卡、明细状态和所有外部引用。

## 5. 事实优先级

修复脚本按以下顺序判断，不允许用任务卡整体状态覆盖明细事实：

1. 订单明细是否属于当前订单、是否仍为 `lifecycle_status = active`。
2. `task_order_item_links` 中当前阶段的明细关联和 `item_status`。
3. `task_item_status_logs` 的实时状态事件和时间顺序。
4. 任务表中的 `status`、`progress_pct` 和兼容用 `order_item_id`。
5. 订单状态日志、任务操作日志，以及附件/外协/车辆引用。

规则：

- `pending`、`designing`、`pending_review`、`revision`、`in_progress`、`rework`、`assigned`、`pending_acceptance` 是当前阶段可解释的执行状态。
- `rolled_back` 表示退出当前阶段但保留历史，只有来源阶段在回退之后再次完成时才可重开。
- `cancelled` 表示历史取消，普通阶段推进不自动复活。
- 任务卡整体状态和历史日志只能辅助判断，不能替代逐条明细关联。

## 6. 修复分类

### A 类：确定性修复

满足全部条件才允许写入：

1. 当前明细有效且属于目标订单。
2. 来源阶段存在明确的完成事件。
3. 目标阶段存在 `rolled_back` 关联，且该回退事件早于来源完成事件。
4. 目标阶段不存在其他有效关联。
5. 没有进行中的外协阻断，且没有并发修改。
6. 修复只涉及当前明细，不重置同卡其他明细。

写入内容：目标关联设为该阶段等待状态、进度设为 0、完成时间清空、当前执行人清空；随后按有效明细重算目标任务卡。保留原 `rolled_back` 状态事件，并新增 `source = repair` 的逐条修复事件和 `operation_logs.action = data_repair` 审计记录。

### B 类：订单状态同步候选

仅在业务规则确认后处理：当前订单不是人为回退/取消状态，所有有效明细在设计、制作、安装均有明确完成事实，且没有活动任务、回退明细或外协阻断。修复必须通过服务层的订单状态同步逻辑，不使用孤立 `UPDATE business_documents`。

### C 类：重复任务卡合并候选

只有在明细集合、任务属性、附件、操作日志、外协引用和车辆引用都能安全转移时才允许合并。取消任务默认是历史记录，不作为“多余卡片”删除；不能确认的卡片只做历史隐藏/展示层处理，不能物理删除。

### D 类：不可推断历史

旧整单任务无逐条状态、执行人或可靠时间时，只输出“历史未记录/待人工确认”。不伪造员工归属、不把历史完成日志复制成当前明细完成状态。

## 7. 事务、安全与回滚

- 使用独立的一次性修复脚本，默认 `dry-run`，不在应用启动、页面刷新或部署脚本中自动执行。
- `--apply` 必须同时提供明确订单/明细范围、操作人和修复前数据库备份引用；首批禁止无范围的全库写入。
- 事务中锁定订单、任务卡和目标明细关联，提交前再次检查状态时间线；任一步失败全部回滚。
- 使用确定性的 `repair_key` 检查 `operation_logs`，重复执行已完成修复时只返回幂等结果，不重复创建任务或日志。
- 物理上传文件不移动、不删除；合并任务卡时只更新数据库引用并核对附件数量。
- 修复前后输出 JSON/TSV 快照，至少包含订单、明细、来源任务、目标任务、旧状态、新状态、旧进度、新进度、操作人和时间。
- 优先使用系统备份管理生成并核对新备份；出现问题先恢复应用版本，只有确认业务数据需要恢复时才使用备份，不用危险 SQL 反向猜测。
