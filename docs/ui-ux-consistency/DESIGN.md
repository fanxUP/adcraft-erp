# UI/UX 全栈一致性设计方案

## 1. 目标

让用户在任何业务模块都能快速回答四个问题：

1. 我现在位于哪个业务对象和流程阶段？
2. 当前状态是什么，进度如何？
3. 下一步能做什么，谁可以做？
4. 如果不能操作，原因是什么，应该等待什么条件？

这里的“一致”不是把所有页面做成同一种卡片，而是统一以下五层：

```text
视觉语言 → 页面骨架 → 交互反馈 → 业务状态与权限 → API 数据契约
```

## 2. 当前基线

### 2.1 技术与结构

- 前端是 Vue 3 + TypeScript + Element Plus + Pinia + Vue Router。
- 后端是 FastAPI + Pydantic + SQLAlchemy，接口前缀为 `/api/v1`。
- 前端有桌面端 `DefaultLayout`、移动端 `MobileLayout`、登录用 `BlankLayout`。
- 任务已经具备订单明细多选、明细阶段、单条进度、外协阻塞原因等重要业务能力。
- 全局已有主题变量和 Element Plus 覆盖，但业务页面仍大量保留自己的样式和状态映射。

### 2.2 一致性风险证据

以下是基于当前代码的静态盘点，不代表页面视觉审计的最终结论：

- `frontend/src/views` 约有 99 个页面。
- 使用 `el-table` 的页面约 72 个，使用 `el-dialog` 的页面约 57 个，使用 `el-form` 的页面约 64 个。
- 约 115 个页面或组件包含局部 `<style>`，约 94 个文件存在行内样式。
- 约 113 个页面或组件直接写颜色值，说明全局 token 尚未成为唯一颜色入口。
- 状态标签/颜色在至少 36 个文件中各自定义，同一个状态可能在不同页面显示不同文案或色调。
- `DashboardView.vue` 与 `ProductionTaskBoard.vue` 都实现了项目任务卡片、进度条和状态显示，存在重复维护风险。
- `navigation.ts`、路由 `meta.roles`、后端 `require_permission` 同时参与权限判断，尚未形成一个统一的能力模型。
- 后端有 `ApiResponse`、`success_paginated` 等统一响应工具，但业务接口仍同时存在统一包裹、直接返回字典和 `HTTPException` 三种风格。

### 2.3 文档与实际界面存在偏差

现有 `docs/05_前端页面与UI规范.md` 仍以“红黑科技风”为建议，而当前全局主题实际以蓝色和浅色商务主题为主。后续应以实际产品定位重新定义视觉基线，避免代码、设计文档和用户认知三套标准并存。

### 2.4 证据边界

本轮浏览器界面未能稳定加载，因此本文件是“代码结构 + 业务契约”驱动的规划，不把未成功截取的页面当作视觉证据。实施前的 UI 基线阶段必须补齐桌面端和手机端真实截图，并以截图作为视觉验收依据。

## 3. 设计原则

### 3.1 业务优先

核心路径优先于装饰：订单、任务、明细进度、外协阻塞、成本登记、收款和安装现场操作必须先清楚，再做视觉增强。

### 3.2 状态优先

状态、进度、可操作性和阻塞原因要在同一个视觉层级表达。不可操作的明细不能只变灰，必须同时给出原因，例如“制作中”“已完成”“外协任务进行中”。

### 3.3 一个事实来源

状态码、状态文案、颜色语义、终态判断、进度计算和动作能力由后端业务契约提供；前端只负责呈现和交互，不在每个页面重新猜测业务规则。

### 3.4 渐进式迁移

不一次性重写 99 个页面。先用订单、任务、成本三个高频链路建立标准，再按模块迁移，旧页面通过兼容适配器逐步收口。

### 3.5 明确的动作层级

每个页面只有一个主要动作，次要动作收纳在操作区，危险动作必须说明影响和对象。禁止继续出现“看起来像整单完成、实际只应完成选中明细”的模糊操作。

### 3.6 低认知负担

减少无必要的审核、重复确认、隐藏在下拉框里的对象和重复跳转；对业务人员用业务名称，对系统细节只在需要时展示。

## 4. 目标架构

### 4.1 视觉层：语义化 Design Tokens

保留现有主题切换能力，但将 `--ad-red` 等历史命名逐步迁移为语义命名：

```text
品牌：--ui-brand、--ui-brand-hover、--ui-brand-soft
文本：--ui-text、--ui-text-secondary、--ui-text-muted
背景：--ui-bg、--ui-surface、--ui-surface-subtle
边框：--ui-border、--ui-border-strong
语义：--ui-success、--ui-warning、--ui-danger、--ui-info
业务状态：pending、in-progress、blocked、completed、cancelled
布局：space-1..space-8、radius-sm/md/lg、shadow-sm/md
排版：title、section、body、caption、numeric
动效：duration-fast/normal、ease-standard
断点：desktop、tablet、mobile
```

迁移期可以让旧变量指向新变量，不要求一次性修改所有页面。硬编码颜色只允许出现在 token 文件、图表调色板或打印模板等明确例外中。

### 4.2 页面层：统一页面骨架

建立少量高复用页面原语，而不是把所有页面抽象成一个巨型组件：

- `AppPage`：页面宽度、内边距、加载和错误边界。
- `PageHeader`：标题、说明、面包屑/返回、主操作。
- `PageToolbar`：筛选、刷新、导出、批量动作。
- `DataTableShell`：表格、空态、分页、加载、列密度。
- `DetailHeader`：对象编号、状态、金额/负责人、主操作。
- `SectionCard`：详情页分区，不承担业务逻辑。
- `FormDialog` / `FormDrawer`：统一宽度、按钮区、校验、提交态。
- `StatusTag`：状态码到文案、语义色和可访问名称的统一呈现。
- `ProgressBar`：任务进度、阶段色、100% 终态规则统一。
- `EmptyState`、`ErrorState`、`PermissionState`、`ConflictState`：空、错、无权限、并发冲突分开表达。
- `BatchActionBar`：只对当前勾选对象操作，并展示选中数量与不可操作数量。

组件只统一结构和表现，业务条件仍由页面或 composable 提供，避免“通用组件里偷偷改变业务规则”。

### 4.3 信息架构层：同一对象同一入口

推荐的主导航语义保持现有业务范围，但收敛为以下几类：

```text
工作台
销售管理：客户、报价、合同、订单
交付中心：项目看板、设计、制作、安装、外协、库存
财务中心：应收、支出、项目成本、对账、外协付款
资源运营：车辆、高空作业车
经营分析：日报、月报、异常、经营报告
系统管理：用户、角色、设置、日志、备份、AI 配置
```

旧 URL 保持兼容，通过导航别名和重定向迁移；不在本项目中贸然删除已有可用路由。

### 4.4 业务呈现层：统一状态视图模型

后端对任务、订单、明细和外协对象提供统一的状态展示字段。推荐模型：

```json
{
  "status": {
    "code": "in_production",
    "label": "制作中",
    "tone": "info",
    "terminal": false
  },
  "progress_pct": 60,
  "capabilities": {
    "select": {"allowed": true, "disabled_reason": null},
    "complete": {"allowed": false, "disabled_reason": "外协任务进行中"}
  }
}
```

对于任务处理的订单明细，必须同时返回：当前阶段、阶段文案、本任务状态、本任务进度、是否可选、不可选原因、外协阻塞状态。现有 `TaskOrderItemOption` 已具备其中大部分字段，应优先围绕它收口，而不是再造第二套字段。

任务聚合规则固定为：

```text
任务进度 = 该任务已关联订单明细的进度聚合值
任务完成 = 选中/关联明细全部完成，且后端状态进入终态
看板显示 = 非终态 且 progress_pct < 100
```

设计、制作、安装的“两层关系”只在这三个阶段生效；其他模块不应复用这套假设。

### 4.5 API 层：统一数据与错误契约

继续使用 `/api/v1`，但逐步收敛为：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "..."
}
```

错误响应统一包含：

```json
{
  "code": 40001,
  "message": "请先选择订单明细",
  "data": null,
  "details": {"field_errors": {}, "reason_code": "EMPTY_SELECTION"},
  "request_id": "..."
}
```

约定如下：

- 列表统一 `items / total / page / page_size`。
- ID 在 JSON 中统一为字符串。
- 时间统一 ISO 8601，明确时区；旧数据由边界适配器处理。
- 金额统一由金额格式化器显示，财务新接口避免使用二进制浮点作为事实来源。
- 422 映射为字段级错误，403 映射为权限或状态阻塞，409 映射为并发/业务冲突，网络错误映射为可重试提示。
- 前端 API 拦截器只负责解析一次、统一错误映射一次；页面不再各自拼接同类错误提示。

### 4.6 权限层：从角色判断升级为动作能力

角色仍由后端管理，但 UI 显示和按钮可用性以“资源 + 动作 + 当前对象状态”的能力为准：

```text
can(resource, action, context)
```

前端路由只承担页面级兜底；后端必须是最终授权者。页面上的按钮、批量操作、明细勾选框和禁用原因使用同一份能力结果，避免“导航能看、按钮能点、提交才报错”的体验。

## 5. 核心业务流的目标体验

### 5.1 订单详情

顶部显示订单编号、客户、订单状态和整体交付摘要；下方先展示订单明细列表，再展示按设计/制作/安装聚合的任务进度。每条明细可看到当前阶段、当前任务、进度、外协阻塞和关联成本。

### 5.2 任务处理

任务详情顶部只显示本任务信息和本任务进度；“关联订单明细”使用列表多选，不使用隐藏式下拉。每行显示项目内容、材质/工艺、规格、当前阶段、进度、外协状态和不可选原因。

完成动作只提交当前勾选明细；提交前显示“将完成 N 条明细”，提交后重新拉取任务和明细状态。没有勾选、全部不可操作或存在外协阻塞时，按钮禁用并说明原因。

### 5.3 项目看板/工作台

工作台和项目看板使用同一个任务卡片组件与同一套任务进度计算。卡片显示任务阶段、状态、项目/订单、明细摘要、负责人、截止时间和进度条。任务达到终态或 100% 后从未完成看板隐藏，但不删除历史数据。

### 5.4 成本登记

成本归属弹窗统一宽度和栅格；订单明细一行一条记录，字段固定为：项目内容、产品/材质/工艺、规格、面积、数量、单位、单价、小计、关联成本。支持多选明细，成本按用户选择的明细关联；整单成本和明细成本的互斥关系必须在界面明示，并由后端校验。

### 5.5 一并纳入的优化与改进

UI/UX 统一不只处理颜色和排版。本次计划同时处理下面这些会直接影响使用效率、正确性和后续维护成本的问题，但仍以核心业务链路为边界，不扩张为一次性重写全站。

#### A. 视觉与样式治理

- 建立颜色、间距、圆角、阴影、字号、层级和断点的语义 token；核心波次新增样式不得继续增加未登记的颜色值和行内样式。
- 统一页面密度、表格表头/行高、数字右对齐、弹窗宽度、抽屉宽度、按钮高度、层级和 z-index，避免同一类页面每页一套尺寸。
- 统一浅色主题为默认视觉基线；深色主题作为兼容主题进行对比度验收，不在迁移期间再引入第三套品牌风格。
- 删除已被公共组件替换的重复 CSS、状态颜色映射和无引用组件；保留有业务价值的页面特例，并登记原因。

#### B. 交互与反馈治理

- 所有列表、详情、表单和批量操作统一具备加载中、空数据、请求失败、无权限、状态冲突和提交成功后的反馈。
- 写操作统一防重复提交、提交态锁定、成功后刷新事实数据；失败时只给出一次清晰提示，并保留可重试路径。
- 选择型操作明确显示已选择数量和不可操作数量，禁用项必须展示原因；完成动作只提交当前勾选的明细集合。
- 按风险分级确认：删除、撤销、金额影响等高风险动作需要确认；普通保存和阶段推进不增加无意义的重复审核或重复确认。
- 统一页面返回、刷新、筛选条件保留、分页切换和弹窗关闭后的焦点回归，减少用户迷路和重复录入。

#### C. 响应式与可访问性治理

- 按 1440、1024、平板和 390 宽度验收；表格在窄屏使用可解释的横向滚动或优先级列收缩，不把业务明细强行压成难以阅读的卡片。
- 触控目标、键盘 Tab 顺序、焦点可见性、对比度、状态标签的文本含义和表单错误关联统一。
- 移动端只保留当前场景必需的主要动作，避免底部按钮被键盘、抽屉或安全区域遮挡。

#### D. 性能与数据加载治理

- 列表统一分页、筛选防抖和请求取消；避免因页面重复挂载或逐行请求造成重复请求和 N+1 请求。
- 任务看板、订单明细和成本列表优先只加载当前视图需要的数据；大列表预留虚拟滚动或服务端分页的扩展点，不先引入不必要的依赖。
- 统一缓存失效和刷新策略，所有状态变更后以服务端事实为准，不能用局部乐观更新掩盖失败。

#### E. 全栈可靠性与安全治理

- 任务明细完成、成本关联、阶段推进等写操作必须由后端事务和对象级校验兜底，校验当前勾选集合、阶段、终态、外协阻塞和权限，防止未勾选明细被一起完成。
- 对重复提交、并发编辑和过期数据返回 409 或明确业务错误；前端使用统一的冲突提示，不静默覆盖他人更新。
- 前后端统一 request id、错误码和可重试语义；日志不记录密码、令牌和不必要的敏感信息，用户可见的敏感字段按权限脱敏。
- 所有展示型文本默认按安全文本渲染；文件上传、下载、导出和外部链接沿用权限校验，不因统一 UI 绕过后端授权。

#### F. 内容与业务语言治理

- 建立状态、动作、错误和空态文案词典，例如“制作中”“外协任务进行中”“已完成”“无法选择，因为……”在列表、详情、看板和移动端保持同一含义。
- 金额、日期、数量、面积、百分比和空值统一格式化；不让不同模块自行拼接单位、精度和负数显示。
- 主要动作使用业务动词，避免“处理”“提交”“完成”等没有对象范围的模糊按钮；批量动作明确作用对象和数量。

#### 优先级与纳入方式

| 优先级 | 纳入范围 | 处理原则 |
|---|---|---|
| P0 必须 | 状态/能力单一事实来源、明细选择正确性、错误反馈、权限和安全 | 随 P01-P05 一起完成，未达标不得进入下一波 |
| P1 应做 | token、页面原语、响应式、可访问性、请求去重、表格/表单密度 | 随对应模块迁移完成，不单独制造大重构 |
| P2 后置 | Storybook、OpenAPI 自动生成、E2E 平台、行为指标、打印/PDF 体系 | 进入 backlog，待核心波次稳定后评估 |

## 6. 实施策略

### 第一波：建立标准并迁移三个核心链路

顺序：设计 token 与页面原语 → 工作台/项目看板 → 订单 → 设计/制作/安装任务 → 项目成本。

选择这三个链路是因为它们共享订单明细、任务进度、状态和成本，是最能验证“全栈一致性”是否真实生效的区域。

### 第二波：销售与财务

迁移客户、报价、合同、应收、支出、对账和外协付款，重点处理金额、表格密度、表单校验、导出和权限可见性。

### 第三波：资源、AI 和系统管理

迁移车辆、高空作业车、AI、员工、人事和系统管理；这些模块保留各自业务特有组件，但必须复用全局 shell、状态、反馈和权限能力。

## 7. 不在本轮范围内

- 不重新设计业务流程，不新增审核人员。
- 不删除或迁移历史数据，不改变订单/任务/成本的事实规则。
- 不接入短信、邮件、飞书通知。
- 不引入 Storybook、UI 框架替换或大型第三方组件，除非后续证明现有 Element Plus 无法满足需求。
- 不把所有页面强制改成卡片，不取消业务上需要的表格、看板或移动端专用页面。
- 不在规划阶段修改应用代码或部署环境。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 一次性改动页面过多 | 回归范围失控 | 以订单/任务/成本为试点，按波次迁移 |
| 前后端状态文案不一致 | 用户误判进度 | 后端返回 canonical status view，前端统一呈现 |
| 旧接口兼容问题 | 旧页面不可用 | 先加适配器和契约测试，再切换页面 |
| 抽象过度 | 修改一个页面牵连全站 | 只抽取重复结构和语义组件，业务规则留在领域层 |
| 主题切换回归 | 深浅色显示异常 | token 对比度矩阵 + 桌面/手机截图验收 |
| 权限与 UI 不同步 | 按钮可见但提交失败 | 页面能力由后端返回，前端只做展示性兜底 |

## 9. 成功标准

完成后，用户不需要重新学习每个模块的按钮、状态、表格和弹窗行为；特别是订单、任务、成本三条链路中，同一个状态在列表、详情、看板、移动端和接口返回中应保持同一含义。

同时满足以下改进结果：

- 核心链路不再出现同一状态多套文案、颜色或终态判断。
- 任何批量动作都能明确显示作用范围，不能因页面选择状态丢失而扩大更新范围。
- 核心页面在桌面端和手机端都有可用的加载、空态、错误、无权限和阻塞反馈。
- 核心波次不新增未登记的硬编码颜色、重复状态映射、重复请求和无依据的弹窗确认。
- 后端仍是权限、状态、金额和并发正确性的最终事实来源，UI 统一不会削弱业务安全边界。
