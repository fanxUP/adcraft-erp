# UI/UX 全栈一致性验收标准

每个计划项对应一个主验收项，避免“完成了很多修改但无法判断是否达标”。

## A-UIX-01 对应 UIX-P01：基线可追溯

- [ ] 有路由、页面、角色、主动作、数据状态和组件使用矩阵。
- [ ] 核心订单/任务/成本流程有桌面端和手机端截图，截图状态稳定、非加载中、非空白。
- [ ] 每个已发现的一致性问题都有等级、影响范围和是否纳入本波次的结论。
- [ ] 视觉规范与实际主题一致，不再同时把“红黑科技风”和“蓝色商务风”当作默认标准。

证据：基线清单、截图目录、问题清单、规范版本号。

## A-UIX-02 对应 UIX-P02：公共视觉原语可复用

- [ ] 新增/迁移页面只通过语义 token 使用品牌色、语义色、背景、边框、间距和圆角。
- [ ] 列表、详情、表单、弹窗、空态、错误态和加载态在试点页面拥有统一结构。
- [ ] `StatusTag` 和 `ProgressBar` 在相同状态码下呈现相同文案、色调和终态行为。
- [ ] 公共组件有 TypeScript 类型和最小单元测试；没有把业务规则隐藏在纯展示组件中。
- [ ] 现有主题切换至少在浅色默认主题下通过，深色主题不出现不可读文字或边框。

证据：组件样例/测试入口、组件测试、截图对比、`npm run typecheck`、Lint 结果。

## A-UIX-03 对应 UIX-P03：壳层与权限一致

- [ ] 同一个角色在导航、路由、页面按钮、批量动作和后端接口上的权限结果一致。
- [ ] 无权限、会话过期、强制改密和无数据四种状态分别有清晰反馈。
- [ ] 桌面端侧栏收缩后仍能定位当前页面；移动端返回和主要操作不被遮挡。
- [ ] 任何不可点击动作都能看到可理解的禁用原因或下一步提示。

证据：角色矩阵、权限测试、各角色截图、关键操作录屏或操作记录。

## A-UIX-04 对应 UIX-P04：数据和错误契约统一

- [ ] 试点接口统一返回 envelope 和分页字段，前端只在 API 层解包一次。
- [ ] 400/401/403/409/422/5xx 和网络失败都能映射到统一的用户反馈，不重复弹窗。
- [ ] 任务、明细、外协状态包含 canonical code、label、tone、terminal；前端不再为试点状态重复维护 map。
- [ ] 动作能力包含 `allowed` 和 `disabled_reason`，并且后端会再次校验，不能只依赖前端禁用。
- [ ] 时间、ID、金额在新契约中有明确格式并有兼容旧数据的边界处理。

证据：OpenAPI/接口样例、schema 测试、前端类型、后端契约测试、错误场景测试。

## A-UIX-05 对应 UIX-P05：订单/任务/成本试点闭环

- [ ] 一个订单的不同明细可处在不同阶段，列表、详情、看板和任务处理显示一致。
- [ ] “已完成”只作用于勾选的订单明细；未勾选明细不会被修改。
- [ ] 当前阶段不匹配、明细已完成和外协进行中的明细不可选择，标签和原因可见。
- [ ] 任务进度由关联明细聚合；任务达到终态或 100% 后不出现在未完成项目看板。
- [ ] 工作台与项目看板使用同一任务进度结果。
- [ ] 成本登记明细每行一条，支持多选，关联成本、整单/明细互斥和金额校验一致。

证据：前后端单元测试、关键流程截图、真实测试数据回归、API 请求/响应记录。

## A-UIX-06 对应 UIX-P06：销售与财务波次一致

- [ ] 客户、报价、合同、应收、支出、对账和外协付款复用试点页面骨架和反馈模式。
- [ ] 金额右对齐、精度、空值、负数、合计和导出显示一致。
- [ ] 财务敏感字段按角色隐藏或脱敏，按钮能力与后端权限一致。
- [ ] 列表筛选、分页、刷新、批量操作、详情返回在各页面行为一致。

证据：模块回归清单、角色截图、财务计算测试、构建和全量测试结果。

## A-UIX-07 对应 UIX-P07：资源/AI/系统波次可控

- [ ] 资源、AI、人事和系统页面使用统一壳层、标题、反馈和权限能力。
- [ ] 业务专用页面可以保留特有布局，但不再自定义一套相互冲突的状态色、错误处理和确认语义。
- [ ] 移动安装和照片上传流程在手机宽度下主要动作可见、可点击、可回退。

证据：跨模块截图、移动端回归、关键权限测试。

## A-UIX-08 对应 UIX-P08：发布质量门禁

- [ ] 前端构建、类型检查、Lint、前端测试均通过。
- [ ] 后端全量测试、API 契约测试和数据库迁移检查均通过。
- [ ] 关键页面不再依赖已删除组件、死路由、死状态映射或重复工具函数。
- [ ] `git diff --check` 通过，变更范围符合当前波次，无无关重构。
- [ ] 有部署前备份、目标 commit、健康检查和回滚说明。

证据：命令输出、变更清单、部署记录、健康检查、回滚点。

## 证据限制

截图可以证明布局、文案、颜色、可见性和部分交互结果，但不能单独证明：

- 权限真正由后端执行；
- 并发条件下没有覆盖更新；
- 金额计算和数据库事实正确；
- 键盘/屏幕阅读器完整可用。

这些必须由接口测试、服务测试、并发测试和可访问性检查补充。

## 优化项验收补充

为避免把“看起来统一”误判为“全栈一致”，以下优化规则与对应波次同步验收：

- 状态、进度和动作能力必须只有一个业务事实来源；试点页面不得继续各自维护同一状态的文案、颜色或终态判断。
- 批量完成、成本关联和阶段推进必须按当前勾选集合写入；重复点击、过期数据和并发更新不能扩大更新范围或静默覆盖。
- 列表、详情、表单、弹窗和看板必须分别覆盖加载、空态、失败、无权限、阻塞/冲突、提交中和成功后刷新。
- 1440、1024、平板和 390 宽度下，主要动作、关键字段、返回路径和错误提示可用；键盘焦点可见，状态不依赖颜色单独传达。
- 核心波次不得新增未登记的硬编码颜色、行内样式、重复请求、重复确认、控制台错误、敏感日志或未使用代码；清理内容要有清单。
- 新接口和写操作必须具备对象级权限/状态校验、事务边界、防重复提交、并发冲突语义和 request id；前端禁用只能改善体验，不能代替后端授权。
- 文案、金额、日期、数量、面积、百分比和空值格式必须在列表、详情、看板和移动端复用同一套规则。

P0 优化项未通过时，不得进入下一波；P1 优化项如因兼容性暂缓，必须登记例外、影响和补做计划；P2 项保持在 backlog 中，不得被标记为已完成。
