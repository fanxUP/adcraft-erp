## 4. 发布后健康检查与冒烟

部署完成后，先验证运行时再开放流量。健康接口为：

```text
GET /api/v1/health
```

通过标准：HTTP 200，响应中 `data.status=ok` 且 `data.database=ok`；数据库不可达时应为 HTTP 503，不能误报健康。

- [ ] `/api/v1/health` 返回 200，记录响应时间与 request id。
- [ ] 登录、登出、过期登录和 403 页面显示统一；无权限按钮没有绕过后端授权。
- [ ] 工作台与项目看板显示同一个任务进度；100%/终态任务不出现在未完成看板。
- [ ] 设计、制作、安装任务只允许当前阶段、未完成且无进行中外协阻塞的订单明细；勾选集合与提交结果一致。
- [ ] 成本登记支持明细多选、整单/明细互斥校验、金额展示和失败重试。
- [ ] 客户、报价、合同、应收、支出、对账、外协付款，以及资源、AI、人事、系统和移动安装页面能正常加载、空态、错误重试和分页。
- [ ] 1440/1024/390 三种视口无横向溢出；键盘能到达主要操作；移动端主要触控目标不小于 40px。

## 5. 回滚方案

触发任一条件即暂停放量并评估回滚：健康检查失败、5xx 持续上升、登录/权限异常、订单明细误更新、任务进度聚合错误、成本数据错误、批量写操作越权或移动端核心流程不可用。

回滚顺序：

1. 停止继续放量，保留错误时间、环境、request id、接口、响应码和最近一次已知正常检查结果。
2. 恢复上一个已知可用的前端产物和后端运行包/镜像，不直接删除当前产物。
3. 重新访问 `/api/v1/health`，确认数据库连接正常；再执行登录、权限、任务看板、明细选择和成本登记冒烟。
4. 本轮没有数据库迁移，代码回滚默认不执行数据库恢复；只有在发布批次确实包含迁移且经过兼容性评估后，才按独立的数据库恢复预案操作。
5. 如果发现数据已经被错误写入，冻结相关写操作，依据审计日志和备份恢复预案处理，禁止用前端重复点击“补偿”。
6. 记录回滚 revision、产物摘要、开始/结束时间、影响范围和后续修复任务，再决定是否重新发布。

## 6. 观察窗口

发布后至少观察一个业务高峰或约定窗口，并记录：

- HTTP 401/403/409/422/5xx 按接口与时间的数量；
- request id 关联的失败样本和前端错误日志；
- 任务看板未完成任务数量、任务进度与订单明细阶段一致性；
- 批量任务处理、外协阻塞、项目成本登记和财务列表的成功率；
- 移动端 390 宽度登录及现场安装流程的失败率；
- 数据库连接、响应时间、前端首屏产物大小和静态资源加载失败。

观察期内发现用户阻塞或安全风险，立即按第 5 节回滚；仅视觉微调、非阻塞文案和设计系统增强登记到后续 backlog，不在热修复中扩大业务范围。
