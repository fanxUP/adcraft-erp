# 业务流程与权限治理重构设计

## 1. 本阶段定位

- 类型：业务流程状态机、对象级数据范围、字段级脱敏和代码边界治理。
- 风险：高。设计、制作、安装、外协、订单价格和经营数据都涉及不同的访问边界。
- 模式：STRICT。
- 实施策略：模块化单体。先抽出无数据库依赖的领域内核，再用兼容适配器逐步替换旧服务，禁止一次性重写全部业务。
- 本阶段范围：P-GOV-01～P-GOV-03；建立治理基线、统一状态机注册表和统一数据范围策略入口。

## 2. 当前问题

现有系统已经具备权限目录、权限依赖/冲突校验、订单任务员工可见范围和按订单明细推进能力，但仍存在四类扩展风险：

1. 状态流转定义虽然集中在 `backend/app/domain/workflows.py`，但状态标签、完成判定、任务状态映射和订单阶段推进仍分布在多个服务中，新增状态容易只改一处。
2. 订单任务的“是否全量可见”、阶段读取和外协可见性分别由不同 helper 判断，后续增加项目完成页、统计页或附件入口时容易漏接对象范围。
3. 订单级可见员工和订单明细级执行人是两层语义，目前代码已有正确的业务意图，但缺少一个可复用的策略对象来表达“功能权限 + 数据范围”。
4. `BusinessDocumentService`、`task_service` 体量较大，查询、状态副作用、序列化和权限脱敏交织；继续堆功能会放大回归面。

## 3. 设计原则

```text
事实数据 -> 领域规则 -> 应用命令/查询 -> 权限策略 -> API/前端
```

- 状态机是领域规则的唯一来源；服务只调用状态机，不自行拼接允许状态。
- 权限是能力，角色只是能力组合；业务代码不以角色名称作安全判断。
- 功能权限、数据范围、字段权限和业务状态条件四层分开判断，缺一不可。
- “能看见任务”不等于“拥有订单”，订单级可见范围不等于明细执行所有权。
- 默认拒绝：没有明确的全量范围权限，就不能把列表扩成全公司数据。
- 兼容优先：旧权限码、旧表、旧接口和旧状态值先保留，通过适配器逐步迁移。
- 读写分离：查询只组装可见投影，命令只修改事实并记录副作用，禁止在序列化器中隐式修改数据。

## 4. 目标分层

### 4.1 业务对象层

```text
订单
  └─ 订单明细
       └─ 明细工作单（明细 × 设计/制作/安装）
            └─ 任务卡片（工作单聚合视图）
```

当前阶段不立即合并三张任务表，也不新增迁移。先让现有任务表通过统一状态机和策略适配器对外提供同一套契约。后续再把“明细工作单”作为事实模型迁移目标，避免继续依赖任务卡片聚合状态反推明细状态。

### 4.2 流程层

每个流程由 `WorkflowDefinition` 描述：

- 流程编码和中文名称；
- 状态编码、展示名称；
- 允许的来源/目标状态；
- 稳定的转换命令标识；
- 是否为无出边的终态。

应用层后续使用 `start_work`、`complete_work`、`rollback_work` 等业务命令，由命令解析到注册表中的转换；本阶段先提供稳定转换元数据和兼容 `allowed_targets/ensure_transition` 入口。

### 4.3 授权层

统一授权结果至少包含：

```text
allowed
reason_code
message
required_permissions
missing_permissions
matched_scope
```

四层判断：

| 层 | 例子 | 失败结果 |
| --- | --- | --- |
| 功能权限 | `design_task:read` | 不能进入/调用功能 |
| 数据范围 | 未分配订单、已分配订单、当前执行人 | 列表/详情不返回该对象 |
| 字段权限 | `order_item:view_price` | 价格字段直接省略 |
| 流程条件 | 明细已完成、外协进行中、非本岗位 | 不能推进状态 |

数据范围标准值：`all`、`assigned`、`self`、`department`。`all` 必须由单独的全量范围权限明确授予；阶段读取权限不能隐式扩大范围。

## 5. 本阶段实现设计

### P-GOV-01：治理基线和范围锁定

- 固定当前分支、测试入口、变更预算和允许文件范围。
- 将长期重构拆成可单独验收的阶段，避免把“清理死代码”与安全逻辑改造混在一次提交里。
- 不改数据库、不批量变更角色、不改变已上线业务规则。

### P-GOV-02：状态机注册表

- 由注册表生成兼容的 `ORDER_WORKFLOW`、`DESIGN_TASK_WORKFLOW` 等映射。
- 对每一条转换生成稳定命令编号，例如 `production_task.in_progress.to.completed`。
- 启动/测试时校验转换目标必须是已登记状态，防止悬空状态。
- 保持现有错误文案格式，避免破坏已有 API 和前端提示。

### P-GOV-03：授权策略入口

- `AuthorizationPolicy` 复用现有 `AuthorizationEvaluator`，不另造一套权限并集、依赖和冲突逻辑。
- `AccessRequest` 明确功能权限和数据范围；执行人、本人、部门、全量分别表达。
- 未传范围权限时，全量范围请求拒绝；内部任务（没有 viewer）保持现有可信调用语义。
- 先接入任务队列阶段读取、任务分配可见性和外协读取判断，后续查询/附件/统计直接复用。

## 6. 后续目标架构

```text
api/
  commands/       # 写操作入口：校验权限、调用命令、提交事务
  queries/        # 读操作入口：调用查询服务、返回已脱敏投影
application/
  commands/       # 状态推进、分配、附件、成本等用例
  queries/        # 工作台、看板、完成项目、经营驾驶舱
  dto/            # 稳定 API 输出模型
domain/
  workflow/       # 状态机注册表和转换规则
  authorization/  # 能力、范围、字段策略
  delivery/       # 明细工作单和任务聚合规则
  attachments/    # 文件资产与业务绑定
infrastructure/
  repositories/   # 数据访问和批量查询
  projections/    # 看板/统计读模型
```

迁移顺序是“旁路新增、双读校验、切换读取、最后删除旧路径”。任何旧服务只要仍有外部调用，就保留薄适配器，不直接删代码。

## 7. 明确不做

- 本阶段不引入微服务、工作流 SaaS 或第三方权限包。
- 不直接合并设计/制作/安装三张历史任务表。
- 不重命名现有权限码和状态码。
- 不以数据库脚本批量修改现有订单、任务、角色或用户。
- 不以隐藏前端菜单代替后端授权。
