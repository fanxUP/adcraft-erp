# 订单可见范围与明细执行归属设计

## 1. 目标与风险等级

- 类型：现有设计、制作、安装任务的授权边界、明细级执行归属和状态流转修正。
- 模式：STRICT。
- 风险：高。问题同时涉及权限、状态写入、历史数据纠偏和数据库结构；错误实现会导致员工越权操作、明细负责人串行覆盖或统计归属错误。
- 本阶段目标：让“谁能看见订单”和“谁实际负责某条明细”彻底分离，并让设计、制作、安装只能操作自己的岗位流程，同时可以只读查看订单的完整执行链路。

## 2. 现状审计结论

现有代码已经有订单级可见范围的基础，但把任务级负责人误当成明细级执行人：

| 现有对象 | 当前含义 | 现存问题 |
|---|---|---|
| `order_task_assignees` | 订单允许哪些员工看见任务，空集合表示所有员工可见 | 语义基本符合需求，应保留 |
| `task.assigned_to` | 设计/制作/安装任务表上的单一负责人 | 状态变更时会被写成当前操作人，并在页面逐条复用，导致一条明细变更后所有明细显示同一人 |
| `task_order_item_links` | 一条任务和多条订单明细的关联、明细状态、明细进度 | 缺少当前明细执行人，无法表达同一任务内不同明细由不同员工负责 |
| `task_item_status_logs.assignee_user_id` | 当前实现记录状态事件使用的负责人 | 已有事件审计基础，但目前传入的是任务级有效负责人，不能作为当前明细负责人唯一来源 |
| `design_task:change_status`、`production_task:change_status`、`installation_task:change_status` | 三个阶段的状态操作权限 | 路由已有阶段权限，但明细选择和服务层还需要统一使用该能力 |

直接导致 D20260910-0015 问题的代码链路是：

1. 前端 `TaskOrderItemLinkCard` 使用任务响应里的 `assigned_to/assigned_to_name` 计算 `itemAssigneeLabel`。
2. 这个计算值被渲染到每一条 `item.is_linked` 的明细行。
3. 状态变更服务先解析一个任务级 `effective_assignee`，再执行勾选明细的状态变化，最后写入 `task.assigned_to = effective_assignee`。
4. 因此即使请求只包含一条 `order_item_id`，任务对象的单一负责人也会被更新，页面随后把它显示到所有已关联明细。

这个问题不是简单的前端显示错误；只改页面会留下后端错误归属，必须调整数据模型和状态变更事务。

## 3. 目标业务模型

### 3.1 三层关系

```text
订单可见范围                  阶段明细执行归属                 状态操作权限
order_task_assignees    ->    task_order_item_links       ->    stage change_status
谁可以看到这张订单             哪条明细由谁负责                   谁可以执行哪个岗位流程
```

三层关系互不替代：

- 订单可见范围不等于订单归属，也不等于明细执行人。
- 明细执行人只对当前阶段、当前任务、当前订单明细有效；同一订单的设计、制作、安装可以是不同员工。
- 权限决定“能不能执行某个阶段”，订单可见范围决定“能不能看到订单”，明细执行人决定“能不能操作某一条已领取明细”。

### 3.2 订单级可见范围

继续使用 `order_task_assignees`：

| 订单分配状态 | 设计/制作/安装员工的可见范围 |
|---|---|
| 没有任何分配记录 | 所有拥有 `task_queue:read` 且通过对应订单可见性校验的员工都能看见 |
| 已选择一个或多个员工 | 只有被选择的在职员工能看见该订单的任务及任务明细 |
| 管理员/具备 `order:task_assign` 的管理人员 | 可维护分配，并按管理权限查看订单 |

这里的页面文案建议从“任务分配”改成“订单可见员工”或“订单任务可见范围”，避免员工误解为订单已经归属于某个人。

订单可见范围校验必须继续覆盖：

- 工作台任务队列；
- 设计、制作、安装任务详情；
- 任务明细选项接口；
- 附件上传、删除和预览关联任务的权限边界；
- 后续新增的任务相关接口。

### 3.3 阶段明细执行归属

在 `task_order_item_links` 增加可空的 `assignee_user_id`：

```text
task_type       design | production | installation
task_id         当前阶段任务
order_item_id   当前订单明细
item_status     当前阶段明细状态
item_progress   当前阶段明细进度
assignee_user_id 当前阶段当前执行人，可为空
```

使用用户 ID 而不是员工 ID，原因是当前任务状态日志、任务表和登录态已经以 `users.id` 为主；返回页面时通过有效员工绑定解析姓名。必须校验对应用户仍绑定在职员工，停用员工不能继续领取或被新分配。

同一订单明细在不同阶段是三条独立的执行单元：

```text
订单明细 A
├── 设计任务：执行人甲，设计中/已完成
├── 制作任务：执行人乙，制作中
└── 安装任务：未领取
```

### 3.4 任务表 `assigned_to` 的处理

第一版不直接删除三张任务表里的 `assigned_to` 列，避免回滚和旧数据迁移风险，但将其冻结为兼容字段：

- 新的明细状态变更不再写入 `task.assigned_to`。
- 订单可见范围不读取 `task.assigned_to`。
- 任务详情不再把 `task.assigned_to` 当作明细负责人显示。
- 旧的任务级分配入口不再作为正常操作入口；如果保留兼容 API，必须标记弃用，不能再静默把一个人写到整张任务。
- 任务列表中的 `assigned_to` 筛选要么移除，要么改成明确的“明细执行人”筛选并通过 link 表查询，不能继续按任务单一负责人筛选。
- 依赖 `task.assigned_to` 的超期提醒和旧通知逻辑要改为使用明细执行人或订单可见员工，不能继续给错误的整单负责人发通知。

待新模型稳定、确认没有旧客户端依赖后，再单独做删除列的清理迁移；本次不以删列作为上线前置条件。

## 4. 明细领取与状态变更规则

### 4.1 谁可以领取

状态变更请求不再携带一个全局 `assigned_to` 来覆盖任务。服务端根据当前登录用户解析在职员工，并按每一条勾选明细分别处理。

对设计、制作、安装分别使用对应的 `*_task:change_status` 权限：

| 角色/能力 | 可见订单流程 | 可执行阶段 |
|---|---|---|
| 设计岗位 | 订单可见范围内的设计、制作、安装流程 | 仅设计 |
| 制作岗位 | 订单可见范围内的设计、制作、安装流程 | 仅制作 |
| 安装岗位 | 订单可见范围内的设计、制作、安装流程 | 仅安装 |
| 管理员/阶段管理人员 | 依据权限组合 | 依据明确授予的阶段权限 |

不按角色名称硬编码判断，使用模块化权限代码判断；角色名只是默认角色配置。

### 4.2 首次领取

当员工把某条“未分配”的明细从阶段等待状态推进到该阶段的第一个可执行状态时，系统在同一事务中：

1. 校验员工拥有该阶段 `change_status` 权限；
2. 校验订单可见范围；
3. 校验明细属于该任务、当前状态允许流转、外协阻塞规则允许；
4. 将当前登录员工写入该条 link 的 `assignee_user_id`；
5. 只更新请求中的 `order_item_ids`；
6. 写入明细状态事件，记录当前执行人和实际操作人；
7. 重新聚合任务状态和进度。

例如冯亚宁只选择“标识牌”点击“设计中”：

```text
标识牌：设计中，执行人=冯亚宁
其他明细：状态和执行人保持原值，未领取明细仍为未分配
任务聚合进度：按所有明细重新计算，不直接跳到 100%
```

### 4.3 已领取明细

- 明细没有执行人：同一订单可见范围内、拥有该阶段操作权限的员工都可以领取。
- 明细已有执行人：默认只有该执行人可以继续推进或回退该明细。
- 其他员工仍能看见该行的状态、进度和执行人，但勾选框和状态操作不可用，并显示“该明细由 X 负责”。
- 具备明确阶段管理/明细分配权限的用户可以通过单独的明细分配动作改派或代操作；该动作必须指定明细集合，不能再对整张任务隐式生效。

批量操作遇到“自己可操作”和“他人已领取”混合选择时，后端整批拒绝并返回具体明细名称，不能部分成功，避免用户以为所有勾选项都已处理。

### 4.4 回退、返工和取消

默认规则如下：

| 操作 | 明细执行人处理 |
|---|---|
| 同一阶段内推进/回退，例如制作中 → 待制作（重新排队） | 回退到阶段等待状态时清空当前执行人，允许其他员工重新领取 |
| 返工，例如制作中 → 返工 | 保留原执行人，仍由原执行人继续处理；有阶段管理权限者可改派 |
| 设计中 → 待分配 | 清空设计阶段执行人 |
| 安装中 → 待分配/已分配 | 回到未领取队列时清空执行人；如果“已分配”被定义为正式领取状态，则由操作人重新领取 |
| 完成/取消 | 保留最后执行人用于历史展示，但不可再次操作 |
| 下游任务自动生成 | 不继承上游阶段执行人，制作/安装分别重新领取 |

如果业务希望“回退后仍由原人保留”，可以作为一个明确的后续配置项；本方案先采用回到队列即释放，符合“其他员工可以执行剩余未分配明细”的初衷。

## 5. 跨阶段查看与权限边界

### 5.1 读取面

所有设计、制作、安装岗位保留 `task_queue:read`，在订单可见范围内可以看见：

- 订单下设计、制作、安装任务卡片；
- 每条订单明细当前所处阶段；
- 每个阶段的状态、进度、执行人；
- 是否已完成、是否被外协阻塞（外协详情仍受 `outsource_task:read` 单独控制）；
- 不显示订单金额、明细单价、小计等价格字段，沿用现有价格脱敏规则。

任务列表入口继续不向设计、制作、安装岗位开放；从工作台或项目看板进入详情时，其他阶段只读。

### 5.2 操作面

后端同时执行三道校验：

1. 任务类型对应的阶段变更权限；
2. 当前用户是否为该明细执行人，或是否有阶段管理/明细分配权限；
3. 明细当前状态、订单阶段、外协阻塞和终态规则。

前端置灰只是体验，不能替代服务端拒绝。移动端、AI 操作、直接 API 请求和历史页面都复用同一服务层规则。

### 5.3 推荐权限组合

默认岗位权限建议统一为：

| 权限 | 设计岗位 | 制作岗位 | 安装岗位 | 管理员/销售管理 |
|---|---:|---:|---:|---:|
| `task_queue:read` | ✓ | ✓ | ✓ | ✓ |
| 三个阶段的 `*_task:read` | ✓ | ✓ | ✓ | ✓ |
| `design_task:change_status` | ✓ | - | - | 按需 |
| `production_task:change_status` | - | ✓ | - | 按需 |
| `installation_task:change_status` | - | - | ✓ | 按需 |
| 三个阶段的 `*_task:list` | - | - | - | 按需 |
| `order:task_assign` | - | - | - | 订单管理人员 |
| `*_task:assign` | - | - | - | 阶段管理人员 |
| `outsource_task:read` | 单独授予 | 单独授予 | 单独授予 | 按需 |

这里的“所有阶段 `read`”只代表只读查看，不代表获得状态变更权。

## 6. 接口与返回契约

### 6.1 任务明细选项返回

`GET /api/v1/task-queue/order-item-options` 的每个明细补充：

```json
{
  "is_linked": true,
  "task_status": "designing",
  "assignee_user_id": "...",
  "assignee_name": "冯亚宁",
  "assignee_state": "claimed",
  "can_select": false,
  "disabled_reason": "该明细由冯亚宁负责"
}
```

`assignee_state` 建议至少包含：`unassigned`、`claimed`、`historical_unknown`、`terminal`。

无负责人返回 `assignee_user_id: null`、`assignee_name: null`，而不是把任务表旧的 `assigned_to` 复制过来。

### 6.2 状态变更

三类状态接口保留 `order_item_ids`，但移除其“整张任务负责人”的语义：

```json
{
  "to_status": "designing",
  "order_item_ids": ["item-a"],
  "reason": ""
}
```

服务端用登录用户作为领取人；如果勾选项中有其他人已领取明细，返回大白话错误并整批回滚。

### 6.3 明细改派

增加一个明确的阶段明细分配接口，示例：

```http
PUT /api/v1/{stage}-tasks/{task_id}/order-items/assignees
```

请求：

```json
{
  "order_item_ids": ["item-a", "item-b"],
  "assignee_user_id": "employee-user-id-or-null"
}
```

规则：

- 只接受当前任务内明确指定的明细 ID；
- 只能由对应阶段的 `*_task:assign` 或管理员操作；
- 不改变明细状态和进度；
- 改派、释放和操作人写入现有操作日志；
- `null` 表示释放明细，释放后可由该订单可见范围内的岗位员工重新领取。

现有 `PUT /{task_id}/assignee` 不再作为正常入口。第一版可保留兼容但返回明确弃用提示，不能继续覆盖整张任务；确认无调用方后再删除。

## 7. 历史数据与 D20260910-0015 修复策略

### 7.1 迁移原则

- `task_order_item_links.assignee_user_id` 默认为空，不影响现有状态和进度。
- 不把旧 `task.assigned_to` 批量复制到所有明细；这会把本次错误永久化。
- 只有能够证明属于某条明细的实时状态事件，才允许回填该明细负责人。
- 由旧逻辑产生的整单负责人只保留为兼容审计信息，不能作为新明细操作权限依据。
- 已完成/已取消的历史明细若没有可靠负责人记录，显示“历史未记录”，不伪造姓名。

### 7.2 D20260910-0015 的安全修复流程

上线前必须先在服务器做只读核查和数据库备份：

1. 按任务编号定位任务、订单、所有 link 行、状态事件和操作日志。
2. 对比状态事件中实际勾选明细，判断哪些负责人有可靠证据。
3. 对无法证明的批量负责人不自动归属冯亚宁；将对应明细当前执行人置空，保留状态和进度。
4. 如果业务能确认某些明细确实由冯亚宁负责，只恢复那些明确的明细行。
5. 修复后由员工按明细重新领取，确认一条明细不会影响其他行。

禁止事项：

- 不重置订单状态；
- 不重置明细进度；
- 不删除任务；
- 不直接把整张任务改派给某一个人作为“修复”；
- 不在没有备份和预览结果的情况下执行批量 UPDATE。

## 8. 统计、通知和其他依赖

- 经营驾驶舱完成统计改为以阶段明细 link 的当前负责人或完成事件为准，不能继续以 `task.assigned_to` 归属全部明细。
- 完成事件仍记录 `assignee_user_id`（执行归属）和 `operated_by`（实际点击账号），两者可以在管理员代操作时不同。
- 任务超期提醒按未完成明细负责人发送；无负责人时进入未领取提醒/管理人员提醒，不发送给旧任务负责人。
- 任务分配通知改为订单可见范围通知或明细明确改派通知；短信、邮件、飞书本阶段仍不接入。
- 订单看板、工作台和任务详情都使用同一套明细状态/执行人返回契约，不能各自从任务级字段推导。

## 9. 非目标

- 不新增审核人员、不恢复历史待确认/需修改/变更历史模块。
- 不改变设计、制作、安装本身的状态顺序和进度聚合公式，只修正负责人绑定维度和权限判断。
- 不让设计员工变更制作或安装状态。
- 不让订单可见员工自动获得订单编辑、价格查看、外协查看或任务列表权限。
- 不把一个员工的订单可见资格误写成订单所有明细的执行归属。
- 不在本阶段接入短信、邮件、飞书。
