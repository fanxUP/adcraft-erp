# 模块化权限与安全组合设计方案

## 1. 任务属性

- 类型：权限架构、认证授权、字段级数据安全和前后端权限契约改造。
- 风险：高；涉及用户访问边界、订单金额、成本、外协信息和系统管理能力。
- 实施模式：STRICT。
- 当前基线：`13c80d9`（已包含订单任务可见员工、任务详情边界和外协权限拆分）。
- 本轮状态：P-MP-01～P-MP-07 已在本地实施并通过自动化验证；P-MP-08（生产发布、线上迁移和回滚演练）未执行，需单独授权。

## 2. 目标

将当前“角色名 + 权限码 + 页面硬编码 + 少量手工校验”的混合模式，收敛为一套可以安全组合的授权模型：

1. 权限以模块、资源、动作、字段和数据范围拆分，角色只是权限组合，不再代表固定的业务身份。
2. 多个角色、权限模块或权限包可以组合；组合结果由服务端统一计算，不能因为前端漏隐藏或某个接口漏校验而越权。
3. 权限依赖、父子模块关系、敏感权限冲突和状态操作条件由统一策略定义，不再散落在路由和页面代码中。
4. 设计、制作、安装人员继续看不到订单价格、明细价格、目录价格和财务字段；这一条改为数据安全策略，不依赖角色名称。
5. 订单任务可见范围、任务详情权限、外协可见性、价格字段可见性和状态变更条件相互独立，但能够组合成一个可解释的授权结果。
6. 管理员配置权限时可以看到“将获得什么、缺什么前置条件、与哪些能力冲突、会影响多少用户”。

## 3. 非目标与边界

- 不改订单、订单明细、任务进度、任务状态机、成本和收款事实数据。
- 不删除历史权限记录、操作日志或业务数据。
- 不在本阶段实现按部门、客户、区域、项目金额等复杂 ABAC 数据范围；只保留现有订单任务员工可见范围作为对象级策略。
- 不新增短信、邮件、飞书通知。
- 不引入第三方 RBAC/ABAC 依赖包。
- 不把前端隐藏当作安全边界；所有真实授权仍由后端执行。

## 4. 当前实现审计

### 4.1 已有基础可以复用

- 已有 `roles`、`permissions`、`user_roles`、`role_permissions` 多对多关系。
- 已有 `require_permission()`、`require_any_permission()`、`require_all_permissions()` 和用户权限并集计算。
- 已有订单任务可见员工关联表，能够承载对象级可见范围。
- 已有独立的订单价格、明细价格、目录价格、成本财务、财务报表和外协权限。
- 已有任务列表与任务详情分离、资源中心父级权限、外协商/外协任务拆分等安全边界。

### 4.2 当前会导致组合缺陷的地方

1. **角色名仍然参与安全决策。** 后端的 `require_role("admin")` 仍用于后台管理、回收站、任务删除等多处接口；前端路由也有 `meta.roles: ['admin']`。自定义角色即使拥有合理权限，也无法使用这些功能。
2. **组合规则写死在角色名和权限集合中。** `UserService._validate_roles()` 会拒绝执行角色与销售/财务角色并存；`RoleService` 又按角色名限制敏感权限和资源中心权限。新增角色或重新组合权限时，规则容易漏同步。
3. **权限字典存在多份事实来源。** 后端常量、`seed_permissions.py`、前端 `access.ts`、角色管理页面各自维护权限/分组/敏感集合。当前 `permissions` 表只有 `code/name/description`，seed 中的部分 `group` 元数据并没有落库。
4. **授权检查实现重复。** 路由依赖、任务 API 的 `_user_has_permission()`、AI 助手 `PermissionGuard`、多个 service 内的 `user_has_permission()` 都各自判断；父级权限和子权限是否同时需要也由调用方手工决定。
5. **前端仍是角色优先的混合判断。** `ACCESS_ROLES`、`ACCESS_PERMISSIONS`、路由 `meta.roles` 同时存在；权限 profile 尚未成为所有页面、路由和操作按钮的唯一能力来源。
6. **seed 有覆盖风险。** 现有 seed 会为已存在的内置角色重新替换权限集合。对于“内置角色是不可编辑模板”尚可接受，但不适合未来让权限模块自由组合，也容易覆盖管理员刚做的内置角色例外配置。
7. **缺少统一的授权解释结果。** 当前接口通常只返回“权限不足”，管理员无法知道是缺少父级权限、对象不在可见范围、字段属于敏感数据，还是状态操作条件不满足。

### 4.3 当前组合原则的重新定义

“权限能随意组合”应定义为：

- 业务模块、资源和动作可以按需组合，不再受角色名称限制；
- 角色之间按权限并集生效；
- 必要前置权限自动校验；
- 明确的安全冲突由配置化规则拦截或要求显式例外；
- 数据字段权限、对象范围和状态机条件不会因为拥有另一个模块而自动放大。

这不是把所有权限无条件相加。无条件相加会让“任务操作权限 + 价格权限”“外协查看权限 + 订单详情权限”等组合产生数据泄露。系统要做到的是“自由组合功能，严格组合安全边界”，并把冲突原因说清楚。

## 5. 目标授权模型

### 5.1 四层授权结构

```text
权限目录（原子能力、依赖、冲突、敏感等级）
                |
        角色 / 权限包 / 直接授权
                |
       统一 AuthorizationEvaluator
          /          |           \
     路由动作     数据范围       字段脱敏
          \          |           /
       前端导航、按钮、页面能力摘要
```

四层职责如下：

| 层级 | 解决的问题 | 例子 |
| --- | --- | --- |
| 功能权限 | 能不能进入/执行某个业务动作 | `production_task:change_status` |
| 依赖关系 | 一个动作必须具备哪些前置能力 | 外协任务状态变更需要外协中心和外协任务查看/操作能力 |
| 数据范围 | 能看哪些对象 | 订单任务未设置员工时全员可见，设置后按员工关联过滤 |
| 字段权限 | 返回哪些字段 | `order:view_price` 决定订单金额字段是否存在 |

### 5.2 原子权限目录

保留现有权限码作为兼容标识，不在第一阶段大规模改名；为每个权限补充结构化元数据：

| 字段 | 含义 |
| --- | --- |
| `code` | 稳定唯一权限码，兼容现有 API 和历史审计 |
| `module` | 业务模块，如订单、设计任务、制作任务、外协、财务、资源中心 |
| `resource` | 资源，如订单、任务、外协商、成本、车辆 |
| `action` | `read/list/create/update/delete/change_status/assign/export` 等动作 |
| `kind` | `module/action/field/scope/system` |
| `sensitivity` | `normal/price/financial/external/security` |
| `requires` | 必须同时具备的权限，单独存依赖关系，不写死在页面 |
| `status` | `active/deprecated`，废弃权限不再分配但保留历史数据 |
| `sort_order` | 管理页面的稳定排序 |

示例：

```text
design_task:read
  module=delivery
  resource=design_task
  action=read
  kind=action
  sensitivity=normal

order_item:view_price
  module=order
  resource=order_item
  action=view_price
  kind=field
  sensitivity=price
  requires=order:read
```

权限码仍然是后端唯一授权依据；中文名称、分组、敏感标记和依赖关系由权限目录统一提供，前端不再自行维护敏感权限集合。

### 5.3 依赖、冲突和例外

增加三类可配置策略：

1. **依赖（requires）**：缺少依赖时不能保存角色配置，或由界面自动勾选并在保存前展示。建议服务端最终拒绝不完整配置，避免静默扩权。
2. **冲突（conflicts）**：两个能力默认不能出现在同一安全主体上，返回明确冲突说明。例如执行任务能力与价格/财务敏感字段能力的默认冲突。
3. **例外（exception）**：确有兼职或临时岗位需要冲突能力时，由管理员显式提交理由、有效期和范围；默认不提供永久静默绕过。例外必须写操作日志，并在到期后自动失效。

默认安全顺序：

```text
未授权 < 授权并集 < 依赖补齐 < 冲突拦截 < 显式安全例外
```

不引入“通配符权限”或“看到某模块就拥有该模块全部动作”的隐式继承。

### 5.4 角色与权限包

- 角色不再代表固定身份，只保存一组原子权限或权限包。
- 权限包只是配置快捷方式，例如“设计任务处理”“制作任务处理”“外协只读”“财务查看”“资源中心车辆管理”。
- 权限包在保存角色时展开为明确的原子权限快照，运行时不依赖前端名称，也不产生隐藏授权。
- 内置角色作为系统模板；自定义角色可以任意选择多个模块和动作。
- 角色修改前先生成“变更预览”：新增权限、移除权限、依赖补齐、冲突、受影响用户数。
- 角色删除前必须确认没有用户绑定；不能删除系统最后一个超级管理员。

### 5.5 统一授权评估器

后端新增统一 `AuthorizationEvaluator`（名称可按项目规范调整），所有入口只调用这一层：

```text
evaluate(user, capability, resource=None, field=None, action_context=None)
  -> allowed
  -> reason_code
  -> missing_permissions
  -> matched_scope
  -> redaction_policy
```

至少提供以下统一方法：

- `has(user, permission)`：只判断原子权限。
- `require(user, all_of=[...])`：校验依赖和父级门槛。
- `can_access_object(user, resource, object_id)`：校验订单任务可见范围。
- `can_view_field(user, field)`：统一字段权限和脱敏。
- `explain(user, request)`：给管理端和测试使用，不向普通业务用户暴露敏感授权结构。

`require_role()` 只保留给迁移期间的兼容入口，最终业务接口全部改为权限或超级管理员能力；超级管理员也通过稳定的系统权限表达，不让业务代码直接判断字符串 `admin`。

## 6. 当前项目的组合规则落地

### 6.1 设计、制作、安装任务

```text
工作台任务可见 = task_queue:read
              AND 当前阶段:*:read
              AND 订单任务员工范围允许

任务列表可见 = 当前阶段:*:list
               AND 当前阶段:*:read

变更状态 = 当前阶段:*:change_status
           AND 当前登录账号已绑定在职员工
           AND 订单任务员工范围允许
           AND 当前明细状态/外协阻断/状态机允许

负责人维护 = 当前阶段:*:assign
             AND 目标员工有效
```

任务人员不因为拥有任务权限而获得 `order:view_price`、`order_item:view_price`、`catalog:view_price` 或 `finance:view_cost`。

### 6.2 外协

```text
外协商查看 = outsource_center:read AND outsource_vendor:read
外协任务查看 = outsource_center:read AND outsource_task:read
外协任务状态 = outsource_center:read
               AND outsource_task:read
               AND outsource_task:change_status
外协付款 = outsource_payment:read/create
           （不自动继承外协任务写权限）
```

无 `outsource_task:read` 时，任务详情接口不返回外协标识、供应商、编号、状态和外协阻断原因；前端也不显示外协卡片。该规则由统一响应策略执行，不由各页面自行决定。

### 6.3 订单和价格字段

- 订单基础字段与价格字段分开授权。
- 订单明细基础工作字段与单价、小计、成本、利润分开授权。
- 缺少字段权限时直接省略字段，不用 `0`、`null` 或“--”伪造金额。
- 导出、聊天卡片、通知、附件下载、AI 上下文和报表必须调用同一字段策略。

### 6.4 资源中心

资源中心父级只负责入口，不自动授予车辆或高空车全部能力；每个子模块按自身资源动作授权。所有接口必须同时经过统一父子依赖校验。

## 7. 管理界面方案

角色权限页面改为三栏或分步式配置：

1. 左侧：角色列表、内置/自定义、绑定用户数、最近变更时间。
2. 中间：权限模块和权限包；模块内再按查看、创建、编辑、删除、状态、分配、字段权限展开。
3. 右侧：实时权限预览和安全检查，显示“将看到的页面/字段/动作”“缺失前置”“冲突能力”“影响用户”。

保存行为：

- 先调用 dry-run 校验；校验通过后再提交。
- 依赖未满足、冲突未处理、权限编号不存在时整批拒绝，不保存半套权限。
- 变更结果展示 before/after 差异，并记录操作人、时间、理由、客户端 IP 和有效期。
- 角色页面不再维护执行角色、敏感权限、资源权限的本地 Set；这些信息由权限目录接口返回。

## 8. 数据迁移建议

建议新增而不破坏现有关系：

```text
permissions                         # 扩展模块/资源/动作/敏感级别等元数据
permission_dependencies             # 子权限 -> 前置权限
permission_conflicts                # 权限组合冲突和处理策略
permission_packs                    # 可选的权限包定义
permission_pack_items               # 权限包内的原子权限
role_permission_packs               # 角色使用的权限包
role_permissions                    # 保留，保存展开后的明确权限
user_roles                          # 保留
```

不建议第一阶段删除旧 `role_permissions` 或直接改权限码。先采用兼容双读：新评估器读取明确的原子权限，旧权限码继续可用；全部路由迁移并完成回归后，再清理废弃的角色名判断和旧宽泛权限。

## 9. 失败保护、测试与发布

### 9.1 防止组合后出问题

- 目录启动检查：重复权限码、未知依赖、依赖环、冲突自冲突、废弃权限重新被分配均失败。
- API 契约检查：每个业务路由必须声明一个权限策略；禁止新代码直接使用 `require_role("admin")`，除启动/超级管理员兼容层外。
- 组合矩阵测试：单权限、多角色并集、父子权限、缺依赖、冲突组合、临时例外、禁用用户、无员工绑定。
- 数据泄露测试：任务、订单、聊天、导出、下载、AI 和报表响应断言敏感字段“不存在”，而不是只断言页面没显示。
- 前端契约测试：导航、路由、按钮使用同一权限码；自定义角色可直接访问允许页面，不能通过直访 URL 绕过。
- 角色变更影响测试：修改角色前模拟所有绑定用户的有效权限，发现冲突则整批拒绝。

### 9.2 发布和回滚

- 先发布只读目录和评估器兼容层，再逐批迁移路由，最后切换管理页面。
- 每批迁移前备份角色、权限、角色权限关联、用户角色关联和授权审计数据。
- seed 只做权限目录幂等 upsert；内置角色默认权限通过版本化变更更新，不再每次部署无条件覆盖管理员配置。
- 任何一批失败，优先回滚应用和前端版本；不使用全库恢复覆盖业务数据。
- 迁移期间保留旧权限码映射，确保旧版本回滚后仍能读取新权限记录。

## 10. 预期收益与代价

### 收益

- 新增一个模块或一个动作只需登记权限目录、依赖和测试，不需要同时修改多个角色判断集合。
- 角色可以组合，且组合前有明确的依赖和冲突解释。
- 后端、前端、字段脱敏和对象范围使用同一套能力语义。
- 任务人员的价格隔离、外协隔离和订单任务员工范围不会因为新增角色而意外失效。
- 管理员可以审计权限变更和影响面，定位“为什么看不到/为什么能看到”。

### 代价

- 初期要增加权限目录、策略关系和组合校验，权限管理页面比现在复杂。
- 需要一次性迁移现有按角色名的路由和前端导航。
- 需要维护组合矩阵和权限契约测试；这是一项持续治理成本。
- “完全任意组合”与敏感数据安全存在天然张力，必须保留配置化冲突和显式例外，而不能无条件相加。
