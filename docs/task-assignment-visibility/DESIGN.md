# 订单任务可见范围与任务详情权限设计

## 1. 目标

本方案只处理订单任务的可见范围、任务负责人和任务详情操作权限，不改变既有的设计、制作、安装状态机、订单明细进度计算或外协业务规则。

需要满足四条业务规则：

1. 设计、制作、安装人员不拥有任务列表入口，只通过工作台进入自己可见的任务详情。
2. 订单可以指定一个或多个可见员工；没有指定时，拥有相应任务详情权限的员工都可以看到。
3. 任务详情中的负责人维护只允许拥有对应 `*:assign` 权限的用户操作；其他员工推进状态时，后端强制把操作归属记录为当前登录账号绑定的在职员工。
4. 没有 `outsource_task:read` 的用户不能在任务详情中看到外协卡片、外协标签、外协编号或外协阻断信息。

## 2. 数据模型

新增表 `order_task_assignees`，一行表示一个订单与一个员工的可见关系：

| 字段 | 含义 |
| --- | --- |
| `id` | 关联记录 ID |
| `document_id` | 订单 ID，外键级联删除 |
| `employee_id` | 员工 ID，只允许绑定在职且绑定登录账号的员工 |
| `assigned_by` | 维护人用户 ID，可为空 |
| `created_at` / `updated_at` | 审计时间 |

`(document_id, employee_id)` 唯一，避免重复授权。空记录具有明确语义：该订单没有设置可见范围限制，所有拥有对应任务详情权限的员工均可见。清空多选后删除该订单的关联行，不写入“全员”哨兵记录。

## 3. 可见性判定

对设计、制作、安装任务及其订单明细选项、任务附件统一应用同一条规则：

```text
管理员/拥有 order:task_assign 的管理者 -> 可维护并查看全部订单任务
普通用户 -> 订单没有员工关联记录
           或存在一条关联记录，其 employee.user_id = 当前登录用户
           且员工在职、启用、未删除
```

所有判定在后端执行。前端隐藏导航和按钮只是体验层，不作为数据安全边界。无权访问的任务按“不存在或当前账号无权查看”处理，避免泄露订单是否存在。

## 4. 权限矩阵

| 能力 | 管理员/销售 | 设计人员 | 制作人员 | 安装人员 |
| --- | --- | --- | --- | --- |
| 工作台任务读取 | 有 | 有 | 有 | 有 |
| 设计/制作/安装任务列表 | 有显式 `*:list` | 无 | 无 | 无 |
| 本阶段任务详情 | 有 | 仅设计 | 仅制作 | 仅安装 |
| 本阶段负责人维护 | 有 `*:assign` | 默认无 | 默认无 | 默认无 |
| 本阶段状态变更 | 按现有 `*:change_status` | 有 | 有 | 有 |
| 订单任务可见员工维护 | 有 `order:task_assign` | 无 | 无 | 无 |
| 外协情况 | 按 `outsource_task:read` | 默认不可见 | 默认不可见 | 默认不可见 |

任务列表权限和任务详情权限分开，避免“能处理任务”自动变成“能浏览整个任务库”。任务负责人接口也与普通任务编辑接口分开，允许拥有分配权限但没有编辑权限的管理用户正常维护负责人。

## 5. 状态变更归属

- 有本阶段 `*:assign` 权限的用户：可以从在职员工选项中选择负责人，保存负责人或在状态变更时提交指定负责人。
- 没有 `*:assign` 权限的用户：界面不显示可编辑的负责人选择器；状态变更请求不得指定其他负责人，后端会拒绝伪造请求，并将本次操作归属到当前登录账号绑定的在职员工。
- 当前账号未绑定在职员工时，状态变更返回明确提示：`当前登录账号未绑定在职员工，无法变更任务状态，请联系管理员完善员工绑定`。

## 6. 前端行为

- 左侧任务列表导航与列表路由使用 `design_task:list`、`production_task:list`、`installation_task:list`。
- 工作台任务卡片和任务详情路由使用 `task_queue:read` 与对应阶段 `*:read`。
- 订单详情的“任务可见员工”使用多选员工列表；空选择表示全员可见，保存后显示当前限制人数。
- 任务详情的负责人选择器仅在对应 `*:assign` 权限存在时显示；普通员工看到只读负责人和“状态变更后自动记录当前登录员工”提示。
- 外协卡片和明细外协标签继续以 `outsource_task:read` 为唯一前端显示条件。

## 7. 迁移与回滚

- 迁移只新增 `order_task_assignees`，不改订单、明细、任务、员工和历史数据，不做回填。
- 迁移前后均可用空关联表示全员可见，旧任务在没有新记录时保持原有可见行为。
- 回滚顺序：停止应用写入 -> 回退应用版本 -> 如确需回退数据库，再执行该迁移的 downgrade；回滚数据库会删除新建的订单任务可见范围记录，因此必须先备份该表。
