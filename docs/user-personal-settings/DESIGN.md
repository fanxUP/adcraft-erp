# 用户个人设置方案

## 1. 需求理解

为每个登录用户提供自己的设置入口，能够：

- 修改自己的登录密码；
- 选择自己的界面风格；
- 调整自己的文字大小；
- 在桌面端和移动端使用同一份个人设置；
- 不改变用户已有的角色、菜单、数据范围和设计/制作/安装岗位权限。

这里的“自己的”有两个边界：

1. 用户只能修改当前登录账号的密码和界面偏好，不能通过请求参数修改其他用户。
2. 主题和字号属于个人偏好，不属于角色权限，也不影响其他用户。

## 2. 当前系统基线

当前系统已经有以下能力，可以直接复用：

- `frontend/src/views/profile/ProfileCenter.vue` 已有“修改密码”表单；
- `POST /api/v1/auth/change-password` 已经由当前登录用户身份校验，并通过 bcrypt 校验原密码；
- `GET /api/v1/auth/me` 是登录后恢复用户资料的统一入口；
- `frontend/src/stores/app.ts` 已有主题、字号和字重状态；
- 已有三套主题：`light-blue`、`light-white`、`dark-blue`；
- 已有字号选项：12、13、14、15、16、18、20；
- 移动端已有独立的“我的”页面和登录会话。

需要修正的现状是：主题、字号、字重目前只写入未按用户隔离的 `localStorage`，而管理员“系统设置”页面也提供了同一组控件。因此它们实际是“当前浏览器设置”，不是可靠的用户设置，可能出现换浏览器不生效或不同账号共用浏览器时串用的问题。

## 3. 核心设计决策

### 3.1 入口统一到个人中心

桌面端继续从右上角用户菜单进入“个人中心”，在现有账号信息和修改密码之外增加“我的设置”卡片：

```text
个人中心
├─ 账号信息
├─ 我的设置
│  ├─ 界面风格
│  ├─ 文字大小
│  └─ 高级：文字粗细（兼容现有功能，可保留）
└─ 修改密码
```

移动端“我的”页面增加同一组设置，采用适合手机的纵向卡片；密码继续使用表单或弹窗，不强制用户跳到桌面端。

不新增需要管理员授权的菜单。`/profile` 和移动端 `/mobile/profile` 继续使用 `authenticated` 访问级别，任何已登录用户都能进入自己的设置。

### 3.2 用户偏好单独建表

新增一对一表 `user_preferences`，不把界面偏好字段混入 `users` 表。建议字段：

| 字段 | 类型 | 规则 | 说明 |
|---|---|---|---|
| `user_id` | UUID | 主键，同时外键到 `users.id` | 一名用户只有一份偏好 |
| `theme` | VARCHAR(32) | 非空，服务端白名单 | 只允许现有三套主题 |
| `font_size` | SMALLINT | 非空，服务端白名单 | 只允许现有字号选项 |
| `font_weight` | SMALLINT | 非空，服务端白名单 | 兼容现有字重能力，默认 400 |
| `created_at` | DATETIME | 非空 | 沿用系统时间戳 |
| `updated_at` | DATETIME | 非空 | 修改时自动更新 |

理由：

- 用户身份、密码和个人偏好职责分离，降低修改账号表的风险；
- 后续可扩展语言、时区、紧凑模式、通知偏好，不需要继续膨胀 `users` 表；
- `user_id` 使用唯一主键保证不会出现重复偏好记录；
- 不存储任何密码、令牌或敏感业务数据。

迁移时为已有用户补齐默认记录：主题 `light-blue`、字号 `14`、字重 `400`。迁移是新增表和新增记录，不删除订单、任务、权限及现有用户数据。

### 3.3 接口契约

#### 登录资料

继续使用 `GET /api/v1/auth/me`，在原有用户资料中增加安全的 `preferences` 字段：

```json
{
  "id": "用户ID",
  "username": "用户名",
  "roles": ["designer"],
  "permissions": ["..."],
  "preferences": {
    "theme": "light-blue",
    "font_size": 14,
    "font_weight": 400
  }
}
```

这样刷新页面、登录和恢复会话只需要现有的资料请求，不增加前端启动时的额外竞态。

#### 保存个人偏好

新增 `PATCH /api/v1/auth/preferences`，请求体只允许当前用户的偏好字段：

```json
{
  "theme": "dark-blue",
  "font_size": 16,
  "font_weight": 400
}
```

接口采用部分更新，主题和字号可以分别保存；服务端使用 Pydantic 白名单校验，拒绝任意 CSS、任意文件路径或未登记的字号。服务端从 `current_user.id` 定位记录，不接受 `user_id` 作为目标参数。

保存成功返回完整的当前偏好；前端以返回值作为最终状态。并发更新采用最后一次成功保存覆盖，当前阶段不需要复杂的版本冲突界面。

### 3.4 前端加载与缓存策略

`authStore.fetchProfile()` 加载 `/auth/me` 后，调用应用 store 的统一方法应用用户偏好：

1. 先使用安全默认值初始化页面，避免把上一个账号的主题短暂带给下一个账号；
2. `/auth/me` 返回后，以服务端 `preferences` 为权威值；
3. 应用主题、基础字号和 Element Plus 基础字号变量；
4. 保存成功后，将返回值写入以用户 ID 命名空间隔离的缓存，例如 `adcraft-ui-preferences:<userId>`；
5. 删除旧的未分账号缓存键 `adcraft-theme`、`adcraft-font-size`、`adcraft-font-weight`，不再依赖它们作为跨账号数据源。

缓存只用于提升页面启动体验，不能替代服务端保存。服务端返回值和后端校验结果优先于浏览器缓存。

### 3.5 设置页交互

“我的设置”卡片建议采用如下交互：

- 主题用三张现有风格预览卡选择；
- 字号用现有选项或滑块选择，并显示“示例文字”预览；
- 兼容保留“文字粗细”时，用下拉框放在“高级设置”中；
- 选择后立即在当前页面预览，点击“保存设置”才写入服务端；
- 有未保存变更时显示“未保存”状态，保存按钮进入 loading；
- 保存失败时恢复最近一次服务端值，并用大白话提示“个人设置保存失败，请稍后重试”；
- “恢复默认”只把草稿恢复为 `light-blue / 14 / 400`，仍需点击保存；
- 离开页面时若有未保存变更，给出二次确认，避免误丢设置。

为了让字号真的对公共界面生效，统一应用以下范围：正文、表单、菜单、表格、标签、分页和公共页面组件使用基础字号变量；业务页面中有意固定的标题字号和状态标签字号保持视觉层级，不用一次性把所有业务页面的固定像素全部重写。

### 3.6 “系统设置”页面的去重处理

现有管理员“系统设置”中的主题、字号、字重控件会造成“管理员修改了全系统样式”的误解，但当前实现并没有全局服务端存储。执行本方案时：

- 将这三项从管理员“系统设置”中移除或改为明确的个人设置入口；
- 管理员通过自己的“个人中心”修改自己的样式；
- “系统设置”只保留真正的服务器级参数，例如系统名称、公司信息、JWT 过期时间、AI 和存储配置；
- 本阶段不新增“管理员给所有人设置默认主题”的功能；如确有需要，另立“系统默认偏好”方案。

这样系统中只有一个用户偏好写入入口，不会出现管理员页和个人页互相覆盖。

### 3.7 密码修改规则

密码部分复用现有接口和强制改密机制，并补齐契约边界：

- 原密码、新密码均由服务端校验，前端校验只用于即时提示；
- 沿用当前至少 6 位的兼容规则，本阶段不强制改变所有账号的密码策略；
- 服务端增加最大长度限制，拒绝空值，并拒绝新密码与原密码相同；
- 成功后清除 `must_change_password`，保持现有首次登录改密流程可用；
- 不在响应、日志或前端状态中保存原密码和新密码；
- 密码修改接口继续只允许当前登录用户，使用既有速率限制和 Bearer 认证；
- 管理员重置密码时同步设置 `must_change_password = true`，与现有“重置后首次登录必须改密”的界面文案保持一致；
- 密码修改成功可以保留当前会话，避免破坏现有强制改密流程；“退出其他设备”列入后续增强，不在本次引入新的会话管理界面。

密码操作可写入操作日志，但只记录操作者、对象、动作和时间，严禁记录任何密码内容。

### 3.8 权限与数据安全

| 操作 | 权限要求 | 目标范围 |
|---|---|---|
| 查看自己的偏好 | 已登录 | 当前用户 |
| 修改自己的主题/字号 | 已登录 | 当前用户 |
| 修改自己的密码 | 已登录且提供原密码 | 当前用户 |
| 管理员重置他人密码 | 既有 `user:update` | 指定用户，保留现有后台能力 |
| 修改他人主题/字号 | 本阶段不提供 | 不允许 |

前端路由隐藏只负责体验，后端必须通过 `get_current_user` 和当前用户 ID 再校验一次。个人偏好接口不读取订单、报价、成本、任务或外协数据，因此不会改变设计、制作、安装人员现有的价格和业务数据隔离。

## 4. 关键状态矩阵

| 状态 | 页面显示 | 服务端行为 |
|---|---|---|
| 首次加载 | 显示安全默认值，资料加载中 | 返回用户默认偏好 |
| 已加载 | 显示当前用户偏好 | `/auth/me` 返回完整偏好 |
| 有未保存变更 | 显示“未保存”，允许预览 | 不写库 |
| 正在保存 | 禁用重复保存 | 原子更新当前用户偏好 |
| 保存成功 | 显示新样式并清除未保存标记 | 返回完整偏好 |
| 保存失败 | 回退到最近一次服务端值 | 不产生部分偏好结果 |
| 强制改密 | 只允许认证相关接口 | 现有全局改密弹窗继续工作 |

## 5. 风险与控制

1. **不同账号串用浏览器主题**：取消未按用户隔离的缓存键，服务端偏好优先，按用户 ID 缓存。
2. **只做前端校验导致越权**：接口不接受目标用户 ID，始终使用 `current_user.id`，并添加越权回归测试。
3. **主题或字号注入**：服务端只接受枚举/白名单，前端只从固定选项提交。
4. **登录后主题闪烁**：使用安全默认值启动，资料返回后统一应用；不读取上一个用户的未命名缓存。
5. **管理员页和个人页互相覆盖**：移除管理员页的重复 UI 控件，不新增全局 UI 写入接口。
6. **移动端体验不一致**：桌面端和移动端共享偏好类型、API 和 store，只分别适配布局。
7. **旧任务/旧角色被影响**：不修改角色权限、订单数据、任务状态、价格字段和任务可见性逻辑。
8. **管理员重置密码文案与行为不一致**：重置时设置 `must_change_password`，并用现有强制改密流程验证。

## 6. 非目标

- 不新增角色、权限码或数据范围规则；
- 不允许管理员在本页面批量修改所有人的主题和字号；
- 不支持自定义颜色、上传主题、CSS 编辑或任意字号；
- 不新增头像、姓名、电话、邮箱等资料编辑能力；
- 不在本阶段实现登录设备列表、退出其他设备、短信找回密码或双因素认证；
- 不重做现有任务、订单、项目看板和财务模块；
- 不把固定业务状态颜色随主题任意改变，保证设计/制作/安装状态含义稳定。
