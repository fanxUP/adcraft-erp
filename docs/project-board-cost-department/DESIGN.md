# 项目看板与项目成本部门/科室展示方案

## 1. 任务分类与风险

- 任务类型：既有业务页面的增量展示与数据契约收口。
- 风险等级：高。原因是项目看板和项目成本同时涉及订单可见范围、订单金额权限和管理员/财务入口；不能把前端显示条件当作安全边界。
- 执行模式：`STRICT`。
- 本次重点：在不改变业务事实的前提下，让项目队列和项目成本页面使用订单主表中的同一个“部门/科室”字段。

## 2. 当前实现基线

### 2.1 项目看板

- 独立项目看板使用 `frontend/src/views/tasks/ProductionTaskBoard.vue`，目前加载统一任务队列，按设计、制作、安装和完成列展示；独立页面还没有工作台已有的“项目队列”列。
- 工作台 `frontend/src/views/home/DashboardView.vue` 已有“项目队列”列，当前使用订单列表数据，并把 `pending_confirm`、`confirmed` 订单作为队列项目。
- 工作台的项目卡片目前展示订单号、项目名称、客户和金额，但没有展示部门/科室。
- `frontend/src/components/ui/TaskBoardCard.vue` 的阶段任务卡已经显示部门/科室；`backend/app/schemas/task.py` 的 `TaskQueueItem` 也已经有 `department` 字段。
- `backend/app/services/task_service.py::_enrich_task_order()` 从 `business_documents.department` 补充任务队列的部门/科室，且继续按 `order:view_price` 裁剪金额。
- `backend/app/services/task_queue_service.py::list_task_queue()` 是活跃任务队列，不返回已完成、已取消或进度 100% 的任务；本次不改变这个口径。

### 2.2 项目成本

- `frontend/src/views/payments/ProjectCostList.vue` 是订单和报价的统一入口列表，目前列出来源、编号、项目名称、客户、状态、金额和项目成本，但没有部门/科室列。
- 订单列表响应 `OrderListResponse` 已有 `department`；服务端 `BusinessDocumentService._to_summary()` 也已经返回该字段。
- 项目成本列表的报价分支由 `/project-costs/quotes` 返回，服务端使用统一单据引用 `_to_ref()`，该引用已经包含 `department`；前端 `QuoteCostResponse` 类型尚未声明该字段。
- `frontend/src/views/payments/ProjectCostDetail.vue` 顶部使用订单/报价详情接口；`OrderDetailResponse` 和 `QuoteDetailResponse` 已有 `department`，但详情卡未渲染该信息。

### 2.3 权限基线

- 项目看板任务接口仍要求 `task_queue:read`，设计、制作、安装列继续由各自的 `*:read` 和订单任务可见范围裁剪。
- 项目队列卡片涉及订单金额，因此沿用现有的 `order:read + order:view_price` 能力门槛。系统超级管理员通过现有能力评估器自动通过；不为本需求新增一套“管理员角色名”判断。
- 项目成本页面继续使用现有 `projectCost`/财务权限；增加部门/科室不会增加订单、成本或明细价格权限。
- 没有部门/科室的历史单据显示 `-`，不从员工部门、客户信息或其他字段猜测补齐。

## 3. 目标与非目标

### 3.1 本期目标

1. 管理员进入独立“项目看板”时，可看到与工作台一致的“项目队列”列；项目队列卡片显示部门/科室。
2. 工作台和独立项目看板复用同一套项目队列数据加载、队列状态筛选和卡片组件，避免两个入口再次出现口径差异。
3. 项目成本统一列表增加“部门/科室”列，订单和报价行均从当前单据的 `department` 显示。
4. 项目成本详情顶部信息卡增加“部门/科室”，订单详情和报价详情均能正常显示。
5. 保持后端权限为最终边界，补充无金额权限、无部门数据、订单/报价两种来源和页面直接访问的回归验证。

### 3.2 本期不做

- 不新增或迁移 `department` 字段；不批量修改历史订单、报价或成本数据。
- 不改变设计、制作、安装任务的状态流转、明细进度、任务合并、订单任务可见员工和完成看板规则。
- 不改变订单金额、明细单价、小计、成本、利润、收款等敏感字段的权限和计算。
- 不把项目队列改成“一个订单一张阶段卡”；仍保持项目队列是订单卡，设计/制作/安装是任务卡，完成是完成项目卡。
- 不向设计、制作、安装员工新增订单列表、项目成本或金额权限。
- 不增加新的数据库表、迁移、第三方依赖、消息渠道、筛选器或导出功能。

## 4. 统一信息架构

### 4.1 独立项目看板列顺序

对具备订单队列查看能力的账号，列顺序为：

`项目队列 | 设计 | 制作 | 安装 | 完成`

其中：

- `项目队列`：订单状态为 `pending_confirm` 或 `confirmed` 的订单卡，点击进入订单详情。
- `设计/制作/安装`：继续使用统一任务队列接口和现有 `TaskBoardCard`，一张卡代表一个阶段任务；同一订单可以同时在不同阶段出现，进度互不覆盖。
- `完成`：继续使用完成项目接口和只读完成详情页，不把终态任务放回活跃队列。
- 没有订单金额查看能力的账号不请求、不显示项目队列列，避免为了显示队列而扩大订单数据范围；其余阶段任务按原权限继续显示。

### 4.2 项目队列卡片

新增共享的 `ProjectQueueCard`（名称可按代码规范调整），工作台和独立项目看板共同使用：

```text
订单编号                         [订单状态]
项目名称
客户名称                 部门/科室
订单金额（仅有 order:view_price 时）
```

交互规则：

- 卡片可点击、可用键盘 Enter/空格打开订单详情。
- 长项目名称和部门/科室使用单行省略并提供 tooltip；在窄屏时上下排列。
- 不在项目队列卡片重复显示订单明细、单价、小计或成本。
- 阶段任务卡和完成项目卡继续使用现有组件，不复制项目队列字段到其他卡片。

### 4.3 项目成本统一列表

在“客户”之后增加固定列：

`部门/科室`

订单行和报价行统一读取 `row.department`，空值显示 `-`，支持 tooltip；不改变现有来源、状态、金额、成本和操作列。

前端类型补齐：

```ts
interface QuoteCostResponse {
  department?: string
}
```

服务端不新增字段，只验证报价成本列表的统一单据引用确实带出当前报价的部门/科室。

### 4.4 项目成本详情

顶部信息卡调整为：

`订单/报价编号 | 项目名称 | 客户 | 部门/科室 | 状态 | 项目成本合计`

使用已经加载的订单/报价详情中的 `department`，不再额外请求接口。保持现有响应式换行、成本摘要和金额权限行为。

## 5. 数据流与权限边界

```text
business_documents.department
       ├── /orders/ 或 /project-costs/quotes
       │       └── ProjectQueueCard / 项目成本列表
       ├── /orders/{id}
       │       └── 项目成本详情头部
       └── task-queue enrichment
               └── 设计/制作/安装任务卡
```

- 项目队列的展示条件在前端只用于体验；`/orders/` 仍由后端 `order:read` 校验，金额是否返回仍由后端 `order:view_price` 决定。
- 任务卡的订单任务可见范围仍由 `order_task_assignees` 和服务端 `task_visibility_clause()` 执行；本次不因增加项目队列而让员工看到被限制的任务。
- 成本列表和详情的进入权限、成本操作权限、金额字段权限不变；部门/科室属于单据基础信息，不作为成本权限的替代品。
- 后端返回字段缺失时前端显示 `-`，禁止使用 `|| 0` 或从其他对象拼接，避免把缺失数据伪装成有效数据。

## 6. 数据加载方案

为避免工作台和独立看板的“项目队列”数量不一致，建议在 `frontend/src/api/orders.ts` 增加一个前端组合方法（不新增后端接口）：

1. 并行请求 `pending_confirm` 和 `confirmed` 两种订单状态。
2. 按订单 ID 去重。
3. 按 `created_at` 倒序排列。
4. 工作台和独立项目看板均调用该组合方法。

这样不再依赖“先拉 100 条再在前端过滤”的不完整队列逻辑，也不需要改变订单列表接口的既有分页契约。若未来订单量超过单次上限，再单独评估服务端项目队列接口，不在本期引入。

任务队列和完成项目请求继续与项目队列并行加载；项目队列请求失败时只显示项目队列空态/错误，不阻塞设计、制作、安装和完成列。

## 7. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 只改前端导致员工通过接口看到订单/金额 | 不修改后端授权；订单接口和任务接口继续由服务端裁剪；增加权限回归测试 |
| 工作台与独立看板队列数量不一致 | 共用组合加载方法、共用卡片、共用 `pending_confirm/confirmed` 状态口径 |
| 报价行因类型缺失导致部门列空白 | 补齐 `QuoteCostResponse.department`，验证 `/project-costs/quotes` 的真实响应契约 |
| 历史订单没有部门 | 统一显示 `-`，不做猜测式回填 |
| 项目队列误显示设计/制作/安装人员 | 队列列要求订单读权限和订单价格查看能力；不新增员工订单权限 |
| 项目卡与阶段任务卡混淆 | 项目队列卡点击订单详情；阶段卡仍点击对应任务详情；不合并实体 |

## 8. 质量门槛

- 代码变更只允许落在项目看板、共享卡片/队列加载、订单报价类型、项目成本列表/详情和相应测试/文档范围。
- 不增加依赖，不增加数据库迁移，不改变公共业务状态机。
- 实施前先写失败契约测试；实施后执行后端定向/全量测试、前端 Vitest、typecheck、lint、生产构建和差异/敏感信息检查。
- 发布前必须用管理员、财务、设计/制作/安装员工账号分别确认：项目队列可见性、部门/科室显示、价格字段不扩权和直接 URL 访问行为。

- `B03`：建立部门/科室缺失数据审计清单，由业务人员确认后再补录，不自动推断。
