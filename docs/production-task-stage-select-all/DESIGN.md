# 制作任务按状态批量选择方案

## 1. 目标

在制作任务的“任务处理 - 订单明细”列表上增加两个分类全选框：

- 待制作全选
- 制作中全选

全选只负责快速勾选明细，不直接变更状态；用户仍通过下方“变更状态”流程提交。单条勾选、状态流转、外协阻塞和后端校验规则全部保持不变。

## 2. 当前实现基线

当前复用组件为 `frontend/src/components/tasks/TaskOrderItemLinkCard.vue`，同时服务设计、制作、安装三类任务。订单明细接口已经返回：

- `stage / stage_label`：订单明细当前所处的交付阶段，例如“制作中”；
- `task_status / task_status_label`：该明细在当前任务中的状态，例如“待制作”“制作中”；
- `can_select / capabilities.select`：当前明细是否允许被勾选；
- `is_linked`：明细是否已经关联到当前任务；
- `outsource_blocked`：是否存在阻塞当前阶段推进的外协任务。

后端在新明细加入已存在的制作任务时，会将该明细初始化为 `pending / 0%`。因此，未关联但当前允许关联的制作阶段明细，应在前端的快速选择中归入“待制作”。

## 3. 核心设计决策

### 3.1 只在制作任务显示

全选栏只在 `taskType === 'production'` 且任务不是历史只读状态时显示。设计任务和安装任务继续使用现有列表，不出现不适用的“待制作/制作中”控件。

### 3.2 不改变列表形态

订单明细继续保持当前的一行一条平铺列表，不改成分组卡片、不增加搜索框、不改变明细排序。全选栏放在“订单明细”标题与列表之间，作为一行轻量工具栏。

建议视觉结构：

```text
订单明细                                      刷新状态
[ ] 待制作（3 条可选）  [ ] 制作中（5 条可选）       已选 4 条
------------------------------------------------------
□ 明细 A   制作中   本任务：待制作   数量... 金额...
□ 明细 B   制作中   本任务：制作中   数量... 金额...
...
```

数量只统计当前可以勾选的明细；不可选、已完成、已取消和不满足阶段条件的明细不被全选框纳入。

### 3.3 分组依据使用本任务状态

不得仅使用 `stage_label` 分组，因为它表示订单明细的全局交付阶段，而不是当前制作任务中的工作状态。分组规则如下：

| 快速选择组 | 归入条件 | 说明 |
|---|---|---|
| 待制作 | 已关联且 `task_status === 'pending'`；或未关联、处于制作阶段且 `can_select === true` | 未关联明细提交状态变更时会按后端规则初始化为待制作 |
| 制作中 | 已关联且 `task_status === 'in_progress'` 且 `can_select === true` | 只表示本任务当前正在制作的明细 |
| 不纳入快速组 | `rework`、已完成、已取消、不可确认阶段、无资格关联的明细 | 仍按现有规则展示，可单条处理或保持禁用 |

`返工`有独立业务含义，本方案默认不把它静默并入“制作中”全选。若后续确认业务上需要把返工也作为制作中批量处理，再单独调整映射和验收，不在本次范围内改变。

### 3.4 全选是独立、可叠加的选择操作

- 点击“待制作全选”只增加或移除待制作组的可选明细，不清除制作中组的选择。
- 点击“制作中全选”只增加或移除制作中组的可选明细，不清除待制作组的选择。
- 手工勾选或取消任意一行后，两个全选框实时更新。
- 全选框采用三态：全部选中为选中，部分选中为半选，无选中为空。
- 组内没有可选明细时，全选框禁用；禁用明细不会被“全选”绕过。
- 刷新明细状态时沿用当前组件行为清空旧选择，避免提交已经失效的明细 ID。

### 3.5 不新增提交路径

全选操作只改变 `selectedItemIds`，不调用接口、不保存关联、不改变任务状态。用户点击状态节点后，仍由现有事件传递精确的 `orderItemIds`；后端继续负责阶段、终态、权限和外协条件的最终校验。

如果同时选择了待制作和制作中明细，现有 `getTaskWorkflowControl` 继续按所有选中明细的共同可达状态限制状态节点，避免跨状态批量操作被误当成单一状态推进。

## 4. 建议实现结构

### 4.1 前端状态辅助函数

在任务处理组件内增加小范围、可测试的选择分组辅助逻辑，不新增全局状态：

```text
productionSelectionBucket(item)
  ├─ linked + task_status=pending       -> pending
  ├─ linked + task_status=in_progress   -> in_progress
  ├─ unlinked + stage=in_production
  │  + can_select                       -> pending
  └─ 其他                               -> null
```

组内明细统一通过现有 `canSelect(item)` 再过滤一次，防止前端分组逻辑绕过后端提供的能力结果。

建议提供以下计算结果：

- `productionPendingItems`
- `productionInProgressItems`
- `isStageSelectionChecked(stage)`
- `isStageSelectionIndeterminate(stage)`
- `toggleStageSelection(stage, checked)`

这些函数只负责选择集合，不负责状态流转。

### 4.2 交互与可访问性

- 使用 Element Plus checkbox 的 `indeterminate` 表达半选状态。
- 为两个全选框提供明确的 `aria-label`，包含状态名称和可选数量。
- 全选栏在窄屏下允许换行，不能挤压明细名称、状态标签和金额信息。
- `changing` 或任务只读时禁止批量选择；单条勾选也继续服从现有禁用条件。

### 4.3 文案

推荐文案：

- `待制作（N 条可选）`
- `制作中（N 条可选）`
- `已选 N 条`

不再增加长篇解释性提示；用户通过全选数量、半选状态、每行状态标签和现有不可选原因即可判断当前选择范围。

## 5. 边界与异常处理

1. 待制作或制作中没有可选明细时，对应全选框显示数量 0 并禁用。
2. 列表中存在外协进行中的明细时，继续显示外协标签；全选不能突破 `can_select` 禁止规则。
3. 已完成或已取消明细不进入快速选择，继续显示为不可操作状态。
4. 刷新后明细状态发生变化，重新计算组数量和三态，不保留旧的失效选择。
5. 后端仍是最终事实来源；即使页面状态过期，提交时也不能扩大到未勾选明细，后端返回的业务错误由现有拦截器处理。
6. 选择两个分组后，不自动替用户拆成两次提交；由现有工作流能力决定哪些状态节点可执行。

## 6. 非目标

- 不增加数据库字段、迁移或新的 API。
- 不修改生产任务状态机、进度聚合、看板隐藏规则或外协判定。
- 不给设计任务和安装任务增加“待制作/制作中”控件。
- 不新增“整单选择”、自动完成、自动保存关联或自动跳转。
- 不把返工明细默认改名或并入制作中。
- 不顺带重构任务处理卡片的其他样式和状态逻辑。

## 7. 验收重点

核心验收必须同时证明“选择方便”和“提交范围安全”：

```text
分类全选 -> 只勾选该分类可操作明细
手工调整 -> 全选框正确反映全选/半选/未选
变更状态 -> 仍只提交 selectedItemIds
混合状态 -> 仍由共同可达状态限制，不绕过工作流
刷新/状态变化 -> 不保留过期选择
```
