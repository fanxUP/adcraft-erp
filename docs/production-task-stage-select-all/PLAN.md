# 任务按状态批量选择实施计划

本计划覆盖设计、制作、安装任务订单明细列表的分类全选交互，不改变任务状态机和后端业务事实规则。

## 1. 任务分类

- 类型：已有任务处理页面上的前端交互增强。
- 风险：STANDARD。没有数据库变更，但涉及批量选择集合，若边界错误可能导致错误的订单明细被提交。
- 变更预算：1 个共享任务处理组件、1 组前端回归测试和必要的文档；不扩展到其他页面重构。
- 主要风险：将全局订单阶段误当成本任务状态、全选包含不可操作明细、清除其他分组选择、或改变现有 `orderItemIds` 提交范围。

## 2. 计划项

### STAGE-SEL-P01：冻结状态分组契约

目标：把设计、制作、安装各自的状态分组与不可纳入快速选择的边界写成明确规则。

工作内容：

- 确认三类任务均使用 `task_status` 作为已关联明细的分组依据。
- 确认未关联但处于当前任务阶段且 `can_select` 的明细按对应 pending 分类归类。
- 明确设计需调整/待处理、制作返工、安装待处理、已完成、已取消、不可关联和外协阻塞明细不被错误纳入。
- 明确按任务类型显示对应控件，不互相污染。

对应验收：A-STAGE-SEL-01。

### STAGE-SEL-P02：增加分类全选栏

目标：在订单明细标题和列表之间增加对应状态的三态全选框及可选数量。

工作内容：

- 保持现有平铺列表和明细顺序。
- 设计增加“待分配”“设计中”，制作增加“待制作”“制作中”，安装增加“待分配”“已分配”“安装中”。
- 无可选明细、任务变更中或历史只读时禁用相应控件。
- 在移动宽度下允许换行，保证主要信息不被遮挡。

对应验收：A-STAGE-SEL-02。

### STAGE-SEL-P03：实现选择集合运算

目标：让分类全选与手工勾选能够稳定协作，并且不扩大提交范围。

工作内容：

- 全选时只合并当前分组的可选 ID，并去重。
- 取消全选时只移除当前分组 ID，不影响其他分组。
- 根据当前选择实时计算 checked / indeterminate。
- 继续由 `selectedItemIds` 驱动状态工作流，不新增接口调用。
- 保留现有混合状态工作流限制、外协提示和后端校验。

对应验收：A-STAGE-SEL-03。

### STAGE-SEL-P04：回归测试与边界覆盖

目标：用测试锁定状态分组和批量选择的关键行为。

工作内容：

- 覆盖已关联待制作、已关联制作中、未关联可关联明细。
- 覆盖返工、已完成、已取消、不可选和外协阻塞明细。
- 覆盖全选、取消、半选、两组叠加、手工调整和刷新后清空。
- 覆盖设计、制作、安装任务显示正确的状态全选控件。
- 覆盖状态变更事件仍收到原始选中 ID 集合。

对应验收：A-STAGE-SEL-04。

### STAGE-SEL-P05：质量验证与交付准备

目标：确认没有类型、样式、构建和既有任务处理回归。

工作内容：

- 执行前端单元测试、类型检查、Lint 和生产构建。
- 执行差异检查，确认只触及本功能范围。
- 检查桌面和窄屏下工具栏、checkbox、明细列表的可用性。
- 记录提交版本；本计划不自动部署服务器，部署需另行授权。

对应验收：A-STAGE-SEL-05。

## 3. 推荐顺序

```text
STAGE-SEL-P01
        |
        v
STAGE-SEL-P02 -> STAGE-SEL-P03 -> STAGE-SEL-P04 -> STAGE-SEL-P05
```

## 4. 变更控制

- 不修改 `TaskOrderItemOption` API 字段，除非实际测试证明现有字段无法区分本任务状态；如需扩展，必须另立计划项。
- 不把返工默认并入制作中；业务若提出该变化，记录为单独决策。
- 不把全选动作与保存关联、状态变更或任务完成绑定。
- 不删除现有逐条选择、不可选原因、外协标签和后端校验。
- 任何状态规则变更必须同时更新设计文档、前端类型/组件和测试，禁止只改显示。
