# 设计、制作、安装任务：单项状态操作与附件相册化

## 1. 需求理解

本次需求包含两条相互关联、但应分别设计的改动：

1. 任务状态从“勾选多条明细后统一变更”改为“每条订单明细独立点击操作”。员工点击某一条明细的明确操作按钮，只改变这一条明细；没有被点击的明细保持原状态、执行人和完成时间不变。
2. 设计任务、制作任务的任务附件，以及安装任务的现场照片与视频，上传成功后使用服务端记录的上传日期时间，按日期倒序组织成类似相册的时间轴。图片、视频和普通文件按其能力展示，普通文件不强行生成缩略图。

这里的“单项点击完成”不是把所有状态都简化成一个不可逆的完成按钮。每条明细仍然遵循现有工作流，当前状态对应可执行动作；例如“待制作”显示“开始制作”，“制作中”显示“完成制作”，需要返工或回退时显示对应的次级操作。这样既满足单条推进，也保留既有回退能力。

## 2. 当前系统基线与问题

### 2.1 任务状态

- 桌面端设计、制作、安装任务详情共用 `TaskOrderItemLinkCard`。
- 当前组件用复选框维护 `selectedItemIds`，再把多个明细 ID 传给任务状态接口。
- 组件底部还复用全局 `TaskWorkflow`，交互仍然是批量状态变更。
- 后端共享 `_apply_task_item_status_change`，实际上已经能够按传入的明细 ID 逐条校验、写状态日志、更新完成时间并重新聚合任务进度。
- 移动端安装页 `MobileInstallation.vue` 仍会把整张任务的全部 `order_item_ids` 一次提交，是本次必须纳入的回归风险。

### 2.2 附件

- `OrderTaskAttachments` 已经调用订单级源头接口 `/orders/{order_id}/attachments`。
- 设计、制作、安装任务详情只是复用订单附件接口的展示入口；附件不依赖任务存在，符合“订单是源头”的既有设计。
- `Attachment.created_at` 已由服务端在上传时写入，接口已经返回 `created_at`，且服务端按上传时间倒序返回。
- 前端已有图片放大、视频播放、普通文件预览/下载/删除、拖拽上传和上传队列能力，但当前媒体和文件是平铺展示，没有日期分组。

## 3. 目标交互方案

### 3.1 任务明细改为逐条操作

任务处理卡片改成“订单明细操作列表”，一条订单明细占一行。建议列为：

| 项目内容 | 产品/材质/工艺 | 规格 | 数量 | 订单阶段 | 本任务状态 | 执行人 | 外协 | 本任务进度 | 操作 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 标识牌 | 铝合金面板、丝印…… | 300×200mm | 10 个 | 设计中 | 设计中 | 张三 | — | 50% | 完成设计 |

具体交互：

- 移除正常状态推进所需的明细复选框、阶段全选框、已选数量和底部批量工作流卡片。
- 每行只允许通过清晰的“操作”按钮改变状态；点击整行、项目内容或状态标签不应触发状态变化。
- 主按钮由当前明细状态决定：
  - 设计：`待分配 → 开始设计`，`设计中 → 完成设计`。
  - 制作：`待制作 → 开始制作`，`制作中 → 完成制作`；返工状态按既有工作流显示“继续制作/完成制作”。
  - 安装：`待分配/已分配 → 开始安装`，`安装中/待验收 → 完成安装`，具体以服务端允许的状态为准。
- 回退、返工、取消等动作保留为次级操作，并使用大白话标签，例如“退回待制作”“退回待分配”“退回安装中”。
- 点击动作后弹出简短确认信息，明确显示明细名称和状态变化，例如：

  > 确认完成“标识牌”的设计吗？
  > 当前状态：设计中 → 已完成

- 请求期间仅锁定当前行，其他明细可继续浏览或操作；成功后刷新当前行和任务聚合进度，不做乐观提交。
- 如果某条明细处于已完成、已取消、被其他人领取、外协未完成或无权操作状态，按钮置灰，并在行内显示原因；原因使用普通语言，不暴露内部枚举错误。

### 3.2 未关联明细的处理

当前复选框同时承担“把未关联订单明细纳入任务”和“选择要变更状态”两种职责，容易造成误操作。改成逐条操作后，按以下方式拆开：

- 未关联且可进入当前阶段的明细，在“操作”列显示“加入并开始设计/制作/安装”。点击后只关联这一条，并将这一条推进到该阶段的开始状态。
- 历史任务、已结束任务或不满足阶段条件的明细只显示“添加到本任务”（若用户有权限），不自动改变状态。
- 已关联但尚未开始的明细显示“开始……”。
- 已关联且已经完成的明细只读，不再提供开始或完成操作。

这样既不丢失原有“补充关联订单明细”的能力，也不会因为取消批量选择而无法处理新明细。

### 3.3 权限、执行人和外协边界

- 普通员工只能操作自己岗位负责的流程；设计人员不能推进制作或安装，制作、安装同理。可以看见订单在其他流程中的状态，但不能执行其他流程。
- 订单分配是可见范围，不等于明细归属。只有员工点击某一条明细开始自己负责的流程时，后端才针对这一条明细执行领取/记录执行人。
- 员工只能操作未分配或分配给自己的明细；其他人的明细保持可见但按钮不可用，并提示“该明细已由某某负责”。管理员/有任务管理权限的人员沿用既有规则。
- 生产、安装明细存在进行中的外协任务时，完成动作继续由服务端拦截；有外协权限显示“外协任务进行中”，没有外协权限只显示通用的前置条件未满足提示。
- 价格字段、外协信息和附件操作继续沿用现有权限过滤，不因为换成单项按钮而扩大数据可见范围。

### 3.4 服务端动作契约

推荐保留现有三类任务的 `change-status` 接口及 `order_item_ids` 字段，避免不必要的 API 破坏性改造；新的三个页面统一只传一个 ID：

```json
{
  "to_status": "completed",
  "reason": "",
  "order_item_ids": ["one-order-item-id"]
}
```

服务端仍需以当前数据库状态为准再次校验：

- 明细是否属于订单、是否已关联本任务；
- 当前状态是否允许目标状态；
- 当前登录人是否有该流程权限和该明细操作权；
- 外协前置条件是否满足；
- 领取、完成时间、状态日志是否只写入这一条明细。

为避免以后每增加一种状态都要在多个页面硬编码，建议在明细选项接口中增加轻量动作描述，例如：

```json
{
  "actions": [
    {
      "key": "complete",
      "to_status": "completed",
      "label": "完成制作",
      "allowed": true,
      "disabled_reason": null,
      "kind": "primary"
    },
    {
      "key": "rollback",
      "to_status": "pending",
      "label": "退回待制作",
      "allowed": true,
      "disabled_reason": null,
      "kind": "secondary"
    }
  ]
}
```

前端只负责呈现服务端允许的动作和提交单项 ID，状态机、权限和前置条件仍由服务端负责。

### 3.5 任务进度与订单推进

- 单条明细操作成功后，沿用现有聚合规则重新计算任务状态和进度。
- 只有所有相关明细都达到完成状态，任务才进入完成；一条明细完成不能把其他明细一起完成，也不能直接让任务错误地跳到 100%。
- 工作台、项目看板和完成看板继续使用任务聚合进度；本次不改变进度算法和订单阶段推进规则。
- 状态日志仍按明细写入，保留操作人、执行人、前后状态和时间，便于审计与问题追踪。

## 4. 附件相册/时间轴方案

### 4.1 数据来源与时间规则

- 继续使用订单级附件接口，任务是否存在不影响订单附件的上传、查看、下载和删除。
- 上传日期时间以服务端 `Attachment.created_at` 为唯一可信来源；客户端不传入、不编辑、不覆盖上传时间。
- 不新增日期字段，不做历史数据迁移。已有记录直接使用现有 `created_at`。
- 前端分组必须使用公共日期格式化函数 `formatDate(created_at)`，遵循现有 UTC 无时区时间契约后转换到浏览器本地日期，不能直接截取原始字符串前 10 位，避免跨时区日期错位。
- 日期按新到旧排列；同一天内按上传时间新到旧排列；页面明确显示绝对日期，例如“2026-09-14”，不使用“今天/昨天”替代。
- 历史数据如果 `created_at` 为空，归入最底部“时间未知”组，不在本次改动中伪造时间。

### 4.2 页面结构

每个任务资料模块按日期生成相册组，示意如下：

```text
任务附件

2026-09-14 · 4 个资料
┌────────┐ ┌────────┐ ┌────────┐
│  图片  │ │  图片  │ │ 视频 ▶ │
└────────┘ └────────┘ └────────┘
方案.pdf · PDF · 2.4 MB · 16:20 · 张三 · 预览  下载  删除

2026-09-13 · 2 个资料
┌────────┐ ┌────────┐
│  图片  │ │ 视频 ▶ │
└────────┘ └────────┘
施工说明.docx · Word · 380 KB · 09:15 · 李四 · 下载  删除
```

- 每个日期是一个独立的分组标题，标题显示日期和该日资料数量。
- 图片和视频在日期组内以响应式媒体网格展示。
- 普通文件在同一日期组内以文件行展示，包含文件名、类型、大小、具体上传时间、上传人和可用操作。
- PDF 可沿用现有预览方式；Word、Excel、CAD、压缩包等不强行显示缩略图，提供下载；已有浏览器可直接预览的类型可以显示“预览”，失败时回退到下载。
- 图片点击打开受控图片查看器；视频点击打开播放器。继续使用当前较慢的图片缩放控制，不重新引入过于灵敏的滚轮缩放。
- 删除成功后立即从当前日期组移除；日期组为空时一并移除。失败不改变列表，并显示可读错误。

### 4.3 上传行为

- 保留点击选择和拖拽上传，保留现有格式、大小和安装媒体限制。
- 多文件同时上传时，每个文件由服务端分别产生上传时间；上传成功后按各自时间进入正确日期组，而不是按批次共用一个时间。
- 上传队列展示进度、成功/失败状态；失败文件支持重试，不生成相册记录。
- 图片、视频继续生成浏览器侧预览对象；服务端不新增缩略图生成、转码或媒体处理服务，降低部署和存储复杂度。
- 订单详情、三类桌面任务详情、完成项目详情和移动安装页都复用同一分组组件和同一订单源接口，保证同一份资料在不同入口显示顺序一致。

## 5. 兼容与可扩展性

- 后端保留批量状态接口字段，兼容历史调用、脚本或未来管理端批量工具；业务任务详情 UI 不再使用批量提交。
- 如后续确实需要批量处理，应另做“批量工具”并显式声明范围、预览影响和权限，不重新把批量行为混入单条明细操作。
- 不新增数据库表、不改变任务和附件表结构、不增加第三方依赖。
- 可新增一个复用的 `TaskItemActionList`/动作按钮组件，将桌面端和移动安装端共享单条动作渲染、确认和错误处理，避免两处逻辑再次分叉。

## 6. 非目标

- 本次不重新设计任务工作流状态机，不改变设计、制作、安装的业务状态含义。
- 本次不改变订单阶段、任务聚合进度或完成看板的统计口径。
- 本次不新增“明细专属分配模型”；继续使用现有订单分配、明细领取和权限规则。
- 本次不增加客户端可编辑的上传日期时间。
- 本次不做服务端缩略图、视频转码、对象存储迁移或历史附件清洗。
- 本次不调整短信、邮件、飞书通知。

## 7. 主要风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 去掉复选框后无法关联未关联明细 | 用“加入并开始”和“添加到本任务”两个逐条动作替代 |
| 某一条完成误更新全部明细 | 前端只提交一个 ID；后端测试状态、执行人、日志、完成时间均只作用于该 ID |
| 移动安装页仍整单提交 | 与桌面端一起改为加载明细动作并逐条提交，增加专项回归用例 |
| 服务端与客户端时间分组跨日 | 服务端时间为准，使用统一 `formatDate`，覆盖时区和临界时间测试 |
| 共享附件组件改动影响多个入口 | 统一组件实现，逐入口验证上传、预览、下载、删除和权限 |
| 动作标签与实际工作流不一致 | 优先使用服务端动作描述；前端不自行推断允许状态 |
