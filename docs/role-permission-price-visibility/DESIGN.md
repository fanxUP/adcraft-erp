# 角色权限与订单价格可见性重梳理方案

## 1. 目标与结论

目标是保留设计、制作、安装人员处理任务所需的业务信息，同时从系统层面禁止其看到订单销售价格、订单明细价格以及能够反推出价格的财务字段。

本方案的核心结论：

> “不显示价格”不能只删除前端列，必须由后端按当前用户权限生成安全响应；前端只负责按后端返回的能力进行展示，不能成为安全边界。

本次重梳理不增加审核人员、不改变设计/制作/安装的任务状态流转、不删除数据库已有价格、不接入短信/邮件/飞书。

## 2. 当前实现核查

当前代码已经有 `roles`、`permissions`、`user_roles`、`role_permissions` 和 `require_permission()`，但仍是“模块级 RBAC + 部分页面按角色隐藏”的混合状态，价格字段没有独立的字段权限。

已确认的风险点：

1. 任务响应模型和任务队列包含 `total_amount`；任务服务的 `_enrich_task_order()` 会主动从订单补充订单总金额。
2. 任务处理的订单明细选项复用完整 `OrderItemResponse`，会返回 `unit_price`、各项费用和 `subtotal_amount`。
3. 设计、制作、安装三个任务列表前端仍直接显示任务金额，任务处理卡片仍显示明细金额和小计，项目看板卡片也有金额展示。
4. `/reports/dashboard` 当前只要求登录即可访问，但工作台响应包含今日订单金额、收款金额、本月订单金额、未收金额和客户欠款排名；因此任务人员即使不进入财务菜单，也可能从工作台看到财务数据。
5. 产品、材质、工艺多个接口当前只校验登录，返回默认价格、采购价、销售价等字段；设计/制作人员现有角色还拥有部分产品资料写权限。
6. 前端路由和导航主要按硬编码角色组判断，`/auth/me` 只返回角色名称，没有返回服务器确认的权限码，前端无法可靠地按字段/动作能力渲染。
7. 角色初始化脚本会按角色名重设权限；当前自定义角色可以被创建，但启动初始化时可能被映射为空权限，角色管理功能存在“重启后配置丢失”的隐患。
8. 部分业务路由只有 `get_current_user`，没有对应的模块动作权限；角色权限管理接口本身也使用硬编码 `admin` 角色，而不是统一的角色管理权限模型。

## 3. 价格字段边界

### 3.1 必须隐藏的订单级字段

- `total_amount`
- `paid_amount`
- `unpaid_amount`
- `discount_amount`
- `tax_rate`
- `tax_amount`
- `cost_amount`
- `gross_profit`
- 合同/项目金额、回款、欠款、付款金额等同类财务字段

### 3.2 必须隐藏的订单明细级字段

- `unit_price`
- `process_fee`
- `installation_fee`
- `design_fee`
- `transport_fee`
- `other_fee`
- `subtotal_amount`
- 任何以 `price`、`fee`、`amount`、`cost`、`profit`、`debt`、`unpaid` 表达销售价或财务金额的派生字段

### 3.3 产品/材质/工艺价格字段

- 产品：`default_price`、`min_charge`
- 材质：`purchase_price`、`sale_price`
- 工艺：`default_price`、`startup_fee`、`min_charge`
- 定价规则、客户协议价和智能报价中的成本/利润/价格字段

### 3.4 允许任务人员看到的业务字段

- 订单号、客户名称、部门/科室、项目名称
- 订单明细名称、产品/材质/工艺名称
- 规格、长宽高、面积、数量、单位、图片和任务附件
- 任务状态、明细状态、进度、负责人、计划时间、安装地址和现场联系人

数量、面积和尺寸不是价格字段，保留给设计、制作、安装人员用于执行任务；但不能通过数量乘单价等方式在响应中附带价格。

## 4. 权限模型

采用四层权限模型，避免把“能进入任务页面”和“能看订单价格”混成一个权限：

1. 认证层：是否登录、账号是否启用、令牌是否有效。
2. 模块层：能否进入订单、设计任务、制作任务、安装任务、产品、财务等模块。
3. 动作层：能否创建、编辑、删除、分配、变更状态、上传附件、导出等。
4. 字段层：能否查看订单销售价格、订单明细价格、目录价格、成本/利润和财务报表。

建议新增并统一使用以下敏感权限码，保留现有模块权限码以兼容历史调用：

| 权限码 | 含义 |
|---|---|
| `order:view_price` | 查看订单销售总额、已收、未收、折扣、税额等订单金额 |
| `order_item:view_price` | 查看订单明细单价、费用和小计 |
| `catalog:view_price` | 查看产品、材质、工艺及客户协议价 |
| `finance:view_cost` | 查看成本、付款、利润、欠款等财务字段 |
| `report:view_financial` | 查看工作台和经营报表中的金额、收款、欠款、利润聚合 |

价格字段采用“显式允许”原则：没有对应权限时，后端响应中不返回字段；不返回 `0`、`null`、星号或格式化后的假值，避免前端误认为是真实金额，也避免通过字段存在性混淆业务语义。

## 5. 预置角色矩阵

保留当前六个预置角色，不新增审核角色。角色默认权限建议如下：

| 角色 | 业务范围 | 订单/明细基础信息 | 订单/明细价格 | 目录价格 | 成本/财务 |
|---|---|---:|---:|---:|---:|
| 管理员 `admin` | 全部模块、权限配置、备份和系统设置 | 是 | 是 | 是 | 是 |
| 销售 `sales` | 客户、报价、合同、订单、客户跟进 | 是 | 是 | 按业务需要 | 不默认开放成本/利润 |
| 财务 `finance` | 订单财务、收款、支出、对账、项目成本和报表 | 是 | 是 | 否或只读必要价格 | 是 |
| 设计 `designer` | 设计任务、设计文件、任务状态和进度 | 是 | 否 | 否 | 否 |
| 制作 `production` | 制作任务、库存、生产资料、外协执行 | 是 | 否 | 否 | 否 |
| 安装 `installer` | 安装任务、现场地址、联系人、照片/视频和进度 | 是 | 否 | 否 | 否 |

“是/否”指默认角色权限，不改变任务角色可以看到的客户名称、项目名称、产品/材质/工艺名称、规格、数量和面积。

为保证“设计、制作、安装看不见价格”是硬规则，建议同时执行：

- 后端禁止向三个执行角色授予上述敏感权限；角色管理页面置灰，接口也必须拒绝绕过。
- 同一账号默认不允许同时拥有设计/制作/安装角色与销售/财务角色；管理员例外。这样避免角色叠加导致权限意外放大。
- 自定义角色按权限集合校验，不能通过改名或新增角色绕过敏感权限规则。

如果未来确实需要一个人兼任执行和财务，再单独设计“临时财务授权 + 有效期 + 审计”机制，不在本次直接放开多角色叠加。

## 6. 后端数据隔离设计

### 6.1 统一访问上下文

新增一个只读的访问上下文/策略服务，集中判断：

- `can_view_order_price(user)`
- `can_view_order_item_price(user)`
- `can_view_catalog_price(user)`
- `can_view_finance(user)`
- `can_use_module(user, permission)`

业务服务不直接判断角色字符串，不在各个页面复制 `if role == ...`。角色只负责授予权限，数据序列化统一读取权限码。

### 6.2 安全 DTO 和序列化

新增面向任务执行的基础 DTO，例如 `OperationalOrderItemResponse`，只包含任务执行所需字段，不继承含价格的完整订单明细响应。

任务详情、任务列表、统一任务队列、订单明细选项都改为按访问上下文序列化：

- 设计/制作/安装用户：返回基础任务 DTO 和基础明细 DTO；完全不返回价格字段。
- 销售/财务/管理员：在具备对应权限时返回现有价格字段。
- 内部进度计算仍可读取数据库价格，但只用于业务计算，不进入操作人员响应。
- 禁止把 SQLAlchemy 模型、完整订单字典或完整报价字典直接作为 API 响应。

### 6.3 重点接口范围

第一期必须覆盖：

- `GET /task-queue/`
- 三类任务列表和详情接口
- `GET /task-queue/order-item-options`
- 订单列表、订单详情、订单明细相关接口
- 产品、材质、工艺列表和详情接口
- 工作台 dashboard、日报、月报和客户欠款接口
- 聊天中的订单/报价业务卡片、对象搜索、最近分享对象
- 导出、打印、附件下载和 AI 业务上下文中可能包含金额的入口

### 6.4 写入边界

- 设计、制作、安装角色不能编辑订单价格、订单明细价格、产品价格、材质价格和工艺价格。
- 订单价格变更、报价确认/转订单、成本登记、收款、对账、报表等操作只由销售/财务/管理员的明确动作权限控制。
- 任务更新接口仅接收任务执行字段；即使客户端伪造金额字段，也必须被 Pydantic 输入模型和服务层拒绝。

## 7. 前端一致性设计

### 7.1 权限来源

`GET /auth/me` 返回 `roles`、`permissions` 和必要的页面能力摘要；Pinia 统一提供 `hasPermission()` 和 `canViewPrice()`。

前端角色名只作为过渡兼容，不再作为敏感字段显示的判断依据。

### 7.2 任务页面

设计、制作、安装的任务列表、任务详情、任务处理卡片和项目看板统一：

- 无价格权限时不渲染“金额”列、总额、单价、小计、费用行。
- 关联订单明细列表保留项目内容、产品/材质/工艺、规格、数量、面积、单位和进度，不显示价格。
- 对服务器已省略的字段不使用 `|| 0` 兜底，避免把缺失字段错误显示成金额 0。
- 任务进度、明细状态、负责人、附件和现场信息不受价格权限影响。

### 7.3 工作台和其他页面

- 任务人员的工作台只保留任务数量、任务进度和待处理事项；金额统计、客户欠款和收款信息整块隐藏。
- 产品/材质/工艺页面对任务人员只显示基础资料；价格列、价格编辑控件和定价规则入口隐藏。
- 订单、报价、收款、项目成本、财务报表和价格导出页面直接按模块权限拦截，不能仅靠菜单隐藏。
- 聊天业务卡片和通知不得因为“分享订单”而绕过价格字段权限。

## 8. 角色管理功能优化

- 权限面板按“模块权限 / 操作权限 / 敏感字段权限”分组，敏感权限使用明确的“财务数据”标识。
- `RolePermissionUpdate` 校验所有权限 ID 必须真实存在，不能静默丢弃无效 ID。
- 内置六个角色保护名称和核心权限，不能通过重命名、删除或空权限覆盖破坏系统基线。
- 初始化脚本只同步内置角色，不清空自定义角色的权限；自定义角色权限由管理员显式维护。
- 用户分配角色时校验执行角色与敏感角色冲突，并记录角色变更操作日志。
- 保留现有权限码兼容期，新增权限码通过幂等 seed 写入，不删除历史权限和业务数据。

## 9. 安全与可维护性原则

- 不用全局响应字符串替换或中间件盲目删除字段；按 DTO/序列化器显式返回，避免误伤任务数量、尺寸等非价格字段。
- 不在浏览器端保存价格权限作为可信依据；每次 API 都由后端依据当前用户权限判断。
- 不通过接口返回“被隐藏字段的总数、范围或哈希”来泄露价格信息。
- 导出和附件下载与页面展示使用同一权限策略；报价 PDF、订单报价附件等含价格文件不能被任务角色下载。
- 操作日志记录角色和权限变更，但日志详情中的价格字段也要遵守查看者权限。
- 测试必须验证“字段不存在”，不能只验证页面没有渲染。

## 10. 分阶段范围

1. 盘点并冻结权限字典和六个预置角色矩阵。
2. 建立敏感字段权限和统一访问策略，修复角色 seed 与角色管理缺陷。
3. 后端任务/订单/目录/工作台/聊天/导出链路接入安全 DTO。
4. 前端统一权限能力、任务页面和工作台按能力渲染。
5. 做跨角色 API、响应字段、路由、下载和浏览器回归，备份后再发布。

## 11. 不在本次范围

- 不增加审核人员、审核节点或多级审批流程。
- 不修改订单项目明细的并行进度、任务状态机、任务负责人和外协阻断规则。
- 不删除或修改历史订单价格、报价数据、成本数据和收款数据。
- 不把价格加密后继续发送给前端；不发送就是最小暴露方案。
- 不引入新的权限管理依赖包，不改数据库主业务表结构；若现有权限表足够，本阶段只新增权限记录和代码策略。
- 不在本阶段实现复杂的行级数据范围（例如按部门、按客户、按负责人隔离），该事项另立方案。

## 12. 外协商与外协任务权限隔离（RPV-P11）

本阶段不再使用含义过宽的 `outsource:*` 作为外协模块总开关，而是将“进入外协中心”“外协商目录”“外协任务”“外协付款”拆成可独立授权的能力。外协付款继续沿用既有付款权限，避免把付款金额权限扩散给只需要处理外协业务的人员。

### 12.1 权限字典

| 权限码 | 用途 | 默认角色 |
|---|---|---|
| `outsource_center:read` | 进入外协中心的父级门槛 | 管理员、外协管理员 |
| `outsource_vendor:read/create/update/delete` | 查看、新建、编辑、删除外协商 | 管理员、外协管理员；财务只读查看 |
| `outsource_task:read/create/update/change_status/delete` | 查看、新建、编辑、变更状态、删除外协任务 | 管理员、外协管理员；财务只读查看 |
| `outsource_payment:read/create` | 查看和登记外协付款 | 管理员、财务 |

外协商和外协任务的每个后端路由同时校验 `outsource_center:read` 与对应子权限。外协付款不自动继承外协商或外协任务写权限；需要付款操作时必须单独授予 `outsource_payment:*`。

### 12.2 角色基线

- 新增内置“外协管理员”角色，只管理外协商和外协任务，不默认拥有外协付款权限。
- 设计、制作、安装角色移除历史 `outsource:*` 默认授权，默认不具备外协任务查看权限，因此任务详情不加载外协卡片、不显示外协标签或外协阻断原因。
- 财务保留外协付款能力，并拥有外协商/外协任务只读权限，以便按外协商和任务筛选付款；不授予外协任务写入、状态变更和删除权限。
- 自定义角色不自动扩权。历史 `outsource:*` 记录保留为兼容审计数据，但不再满足新路由的授权条件；管理员须显式迁移到新权限码。

### 12.3 任务详情的数据边界

- 任务列表、任务队列和任务明细选项接口只有在用户拥有 `outsource_task:read` 时才返回 `is_outsourced`、外协任务编号、外协状态和阻断原因等外协信息。
- 没有该权限的设计、制作、安装人员仍可看到订单明细的正常工作字段和“不可推进”的通用提示，但提示不暴露“外协”字样、供应商名称、任务编号、状态或数量。
- 任务详情中的外协卡片及其接口请求均由 `outsource_task:read` 控制；前端隐藏不是安全边界，后端仍对所有外协接口返回 403 或脱敏结果。
- 拥有外协任务查看权限的用户仍须另外拥有任务类型本身的读取/操作权限，外协权限不会绕过设计、制作、安装任务授权。

### 12.4 数据与发布约束

- 不新增表、不改业务表、不改任务状态机、不删除历史外协业务数据。
- 权限 seed 采用幂等 upsert；内置角色只同步新基线，自定义角色保留并输出旧权限审计清单。
- 发布前备份权限、角色和关联表；先 dry-run 检查旧权限分布及内置角色目标集合，再执行 seed；失败时只回滚应用版本或权限关联变更，不覆盖业务数据。
