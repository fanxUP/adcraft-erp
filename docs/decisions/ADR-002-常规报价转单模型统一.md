# ADR-002：常规报价转单模型统一（保留报价历史）

## 状态

待评审 / 未实施

## 日期

2026-08-16

## 背景

系统存在两套「报价 → 订单」转换模型，行为不一致：

| 路径 | 方法 | 做法 | 报价历史 |
|------|------|------|----------|
| 常规报价（`quote_mode=regular`） | `convert_doc_type()` | 同 ID 翻转：报价原地变订单，`doc_no` 重生成（Q-xxx→O-xxx） | 丢失（原报价编号/状态被覆盖） |
| CDR 报价（`quote_mode=cdr`） | `convert_to_order()` | 新建订单 + `source_quote_id` 回链 + 报价保留 | 保留 |

生产数据 27 个报价**全部是 regular 模式**（CDR 路径未启用），即实际使用的是会丢历史的那套。核心问题：常规报价转单后无法回答「这个订单来自哪张报价单、报价编号是多少」，审计链断裂。

## 决策

将常规报价转单与 CDR 路径统一为**单一模型**：

```
报价(draft → confirmed)
   └─ 转订单 → 新建订单(新 id、O-xxx) + source_quote_id 回链报价
               └─ 报价状态 → converted（报价记录永久保留）
```

1. 新增 `convert_regular_quote_to_order()`（改造 `convert_doc_type` 的 quote→order 分支），参照 CDR `convert_to_order` 的「新建 + 复制」模式。
2. 转单时创建**新订单**（新 id、新 `doc_no`），复制共享字段，`source_quote_id = 报价.id`。
3. 复制报价 `business_document_items` 到新订单，`source_quote_item_id` 回链原明细行。
4. 参照 CDR 逻辑生成生产/安装任务，挂到新订单 id 下。
5. 报价 `status → converted`，为报价与订单各写状态日志，返回新订单。
6. **保留 `order → quote` 方向不变**（取消订单转回报价，仍是同 ID 翻转 + 清理关联）。

## 评审结论（实施前必须纳入）

代码审查后确认方案可行，但存在以下需同步处理的关键点：

### 关键遗漏（必须纳入）

1. **现有测试会破坏**：`tests/test_quote_service.py:273` 断言 `quote.doc_type == "order"`（同 ID 翻转语义），需改写为新语义 `quote.status == "converted"` + `order.source_quote_id == quote_id`；同步核查 `test_quote_route_permissions.py`、`test_ai_safe_actions.py`。
2. **AI 助手工具内嵌「同 ID」假设**：`app/ai_assistant/tools/workflow_tools.py:53`、`quote_action_tools.py:25` 的降级逻辑基于「转单后报价查不到」，新模型下无害但过时，需清理注释与冗余分支。
3. **事务原子性 + 幂等**：新方法需显式 `commit()`（当前 `convert_doc_type` 依赖 `get_db` 请求结束提交，且**无幂等校验**）；必须移植 CDR 的 `status=converted` 幂等检查，防止双击重复转单。

### 需明确/注意

4. **版本快照保留**：转单前对报价的 `create_version()` 快照需保留（现有测试断言 `assert_awaited_once`）。
5. **空明细边界**：`confirmed` 但 0 明细的报价能否转单，需产品确认（CDR 路径要求有版本明细）。
6. **明细回链完整性**：`source_quote_item_id` 需在原明细 `flush()` 后取值，新明细 `document_id` 指向新订单。
7. **存量数据甄别**：现有 12 个 `converted` 报价中部分可能是同 ID 翻转后的伪状态（真实身份已变成订单），迁移脚本需甄别，不能简单按 `status=converted` 处理；历史丢失不可回溯，本方案只保证「今后」不丢。
8. **前端行为走查**：跳转已确认用返回的 `order.id`（`QuoteEditor.vue:1044`，天然兼容）；但报价列表对 converted 报价的过滤/置灰需人工走查。
9. **灰度与回滚**：改动收敛在「新增方法 + 转单端点」，**不动 `convert_doc_type` 的 order→quote 分支**，可独立 `git revert` 回滚。

## 实施顺序（增量、可回滚）

1. 新增 `convert_regular_quote_to_order()`，`quotes.py` 转单端点改调它。
2. 保留报价版本快照；明细复制设 `source_quote_item_id` 回链。
3. 同步改写 `test_convert_quote_initializes_order_receivable` + 新增转单测试（幂等、明细回链、事务回滚）。
4. 清理 AI 工具的过时注释/降级分支（可单独提交）。
5. 存量 converted 报价审计脚本单独提供（只读审计，不自动改数据）。

## 数据迁移说明

- 现有 11 个带 `source_quote_id` 的订单（含已修复的 P0）回链正确，无需处理。
- 2 个无 `source_quote_id` 的订单是手工下单，无来源报价，保持不动。
- 历史丢失无法补救；本方案只保证今后新转单不再丢历史。

## 风险与回滚

| 风险 | 缓解 |
|------|------|
| 转单逻辑改动大，引入回归 | 770 现有测试 + 新增转单测试全覆盖 |
| 任务/验收/收款挂 `document_id`，需正确挂到新订单 | 复制明细时同步重建任务，测试覆盖订单详情/任务/收款链路 |
| 重复转单（双击） | `status=converted` 幂等校验 |
| 回滚 | 改动收敛在单一方法 + 端点，可独立 revert |

## 开发约束

- 后续转单相关改动不得再走「同 ID 翻转」，一律「新建订单 + `source_quote_id` 回链」。
- `source_quote_item_id` 是明细级溯源字段，转单复制明细时**必须**回填。
- 转单方法必须显式 `commit()` 且带幂等校验。
- 新增/修改转单行为必须同步更新 `tests/test_quote_service.py` 中的转换断言。
