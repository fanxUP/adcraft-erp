# 财务历史核对闭环设计

## 任务与风险

- 类型：财务数据核对流程实现；风险：STRICT（会新增可审计的财务核对记录和一条数据库迁移）。
- 目标：让财务人员能逐笔登记凭证/银行流水依据，核实无日期历史付款的实际日期及疑似重复成本，同时保留来源记录和可追溯的人工决策。
- 不做：自动删除/合并成本、自动猜测付款日期、重复创建付款、导入银行流水、纳入工资/车辆/库存等当前范围外模块、部署或修改生产数据。

## 用户流程

1. 在付款流水的“日期待核实”项中，选择证据类型，填写原凭证号/银行流水参考、真实付款日期、核实金额和说明。
2. 对汇总型历史已付款允许分笔核实；核实部分转入有日期付款，未核实余额继续留在待核实金额中。付款来源本金及累计已付不变，不生成第二笔业务付款。
3. 对已有的外协付款记录（仅日期为空）按原付款编号核实日期，记录关联到原付款，不新增金额。
4. 对疑似重复成本选择“确认重复 / 确认非重复 / 证据不足”，记录证据和备注。此结论只作核对状态，不改金额；页面提供项目成本、外协任务原记录入口，后续修正仍由有权限人员在原业务页操作。
5. 误录的日期核对可用带原因的撤销恢复为待核实；不物理删除核对历史。

## 数据与安全边界

- 新增两类记录：历史付款日期分笔核对；项目成本—外协任务疑似重复复核。每次写入记录操作者、证据类型、证据参考、时间和必要的撤销原因。
- 历史付款日期核对是原有已付金额的日期分配，不是新付款；同来源有效分配合计不得超过当前可核实历史已付余额。对来源行加锁后校验，防止并发超分配。
- 已软删除来源不允许新增付款日期核对；回收站里的历史付款仍保留在既有统计中，但要先恢复来源、确认业务事实后再核对，避免恢复时原任务付款数据重算导致核对脱离来源。
- 项目成本/经营支出涉及已分配金额的历史已付基数不得被改小或删除；应先撤销相关分配，再按原流程修改来源记录。
- 外协任务删除会连带删除其原付款行；若任务本身或任一原付款行仍有有效日期核对，删除必须被拦截，先按原因撤销核对记录，避免凭证核对成为孤立记录。
- 外协付款日期核对绑定到一条真实的 `outsource_payments` 记录，金额必须等于原记录金额；日期为空才能核对。
- 凭证仅记录类型与编号/银行流水参考，不在本次另建文件上传机制。真实日期必须由人工看过原凭证或银行记录后录入。
- 核对操作要求财务更新权限；查询沿用现有支出、成本与外协来源权限。写操作进入操作日志；SQL 参数化、金额使用 Decimal。
- 疑似重复结论不会自动从成本或付款汇总中剔除任何金额。

## 验收摘要

- 日期核对前后，同一来源累计已付不变；有日期金额增加量与待核实金额减少量相等。
- 历史已付支持部分拆分；超过剩余额、缺凭据参考、未来日期、重复核对外协付款、或并发超额都被拒绝。
- 撤销需原因并保留核对记录；撤销后对应金额回到待核实统计。
- 重复候选结论和证据可读回；保存结论不会修改或删除两边业务来源。
- 权限不足不能查看受限外协候选或执行写操作；未登录请求按现有认证契约拒绝。
- 迁移只建新表/索引/约束，不回填、不改写历史业务行；在隔离 PostgreSQL 上升级、验证和降级。
