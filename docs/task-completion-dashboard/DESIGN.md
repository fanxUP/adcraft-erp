# 经营驾驶舱项目与明细完成统计设计

## 1. 目标与边界

在现有“经营驾驶舱”中增加交付完成统计，支持“全部”和“当月”两个时间范围，并按登录账号的员工归属隔离数据：

- 设计、制作、安装员工只能看到自己的完成统计和自己的完成明细。
- 管理员可以看到组织总计、员工分组统计，并按员工查看个人完成明细。
- 统计不返回订单金额、明细单价、小计、成本、利润等财务字段，不改变既有价格权限规则。
- 不改变设计、制作、安装状态机、订单明细进度聚合、订单级任务可见范围或外协阻断规则。

本方案把“整单完成”和“某员工完成过交付工作”分开命名。这样设计人员完成设计明细后可以看到自己的成果，不会因为订单尚未安装完成而显示为零；同时管理员不会把某个阶段完成误报成整单已交付。

## 2. 现有系统基础

当前实现已经提供了完成统计所需的大部分业务事实：

| 业务对象 | 当前来源 | 对本方案的作用 |
| --- | --- | --- |
| 项目 | `business_documents` 中 `doc_type='order'` 的订单 | 作为项目维度，`id` 是项目唯一标识 |
| 订单明细 | `business_document_items` | 作为明细维度，只统计 `lifecycle_status='active'` 的明细 |
| 阶段任务 | `design_tasks`、`production_tasks`、`installation_tasks` | 表示设计、制作、安装三个阶段 |
| 任务与明细关系 | `task_order_item_links` | 一条关系代表一个阶段任务中的一条独立明细，保存当前状态、进度和 `item_completed_at` |
| 明细执行归属 | `task_order_item_links.assignee_user_id` 与 `task_item_status_logs.assignee_user_id` | 当前明细执行人和完成事件负责人快照，值为 `users.id`；三类任务表的 `assigned_to` 仅保留兼容，不作为统计归属 |
| 员工与登录账号 | `employees.user_id` | 把员工编号转换为登录账号，支持个人数据隔离 |
| 订单完成事件 | `business_document_status_logs` | `to_status='completed'` 的最新记录是整单完成时间来源 |
| 操作审计 | `operation_logs` | 继续保留为审计用途，不直接用 JSON 快照做统计主数据 |
| 订单任务可见范围 | `order_task_assignees` | 继续作为“能否访问该任务”的行级边界；不是完成量归属 |

当前 `TaskOrderItemLink.item_completed_at` 是当前状态快照，明细退回或返工时会被清空。因此仅依赖它无法可靠回答“当月完成过哪些明细”，也无法固定完成当时的负责人。本需求必须增加轻量的明细状态事件记录。

## 3. 统计口径

### 3.1 员工视角：自己的工作完成量

驾驶舱向执行员工显示以下两项主指标：

1. **我完成过的项目**：在所选时间范围内，至少有一条完成事件归属于当前登录员工的不同订单数。一个员工完成同一项目的多条明细只计一个项目。
2. **我完成的明细**：在所选时间范围内完成的阶段明细工作单元数。唯一键为 `(task_type, order_item_id)`，因此同一订单明细分别完成设计、制作、安装时，按三个阶段工作分别计数，并在界面显示阶段分布，避免把数字误认为整单明细数。

员工明细列表显示：项目编号、项目名称、订单明细名称、阶段、任务编号、完成时间。列表不返回价格字段。

### 3.2 管理员视角：组织总计与个人分组

管理员显示两类数据：

- **组织总计**：
  - `整单完成项目`：订单当前状态为 `completed`，且其最后一次完成事件落在筛选范围内的不同订单数。
  - `已完成明细`：最终安装阶段已经完成的不同订单明细数；同一明细只计一次，用于回答“真正交付了多少条明细”。
  - `完成工作明细`：所有阶段 `(task_type, order_item_id)` 完成工作单元数，用于与员工分组统计相加核对。
- **员工分组**：每位员工显示“完成过的项目”和“完成明细工作单元”，并按设计/制作/安装拆分；点击员工后查看该员工的项目或明细列表。

管理员的员工分组项目数不是“该员工独立完成了整单”，而是“该员工完成过明细的不同项目数”，界面统一标注为“完成过的项目”。只有组织总计中的“整单完成项目”使用订单的最终完成状态。

### 3.3 全部与当月

- **全部**：不限制完成时间，但只统计当前有效订单、有效明细和未取消的完成工作单元。
- **当月**：按业务时区 `Asia/Shanghai` 计算当月第一天至下月第一天，使用半开区间 `[start, end)`，按完成事件时间筛选，而不是按订单创建时间筛选。
- 订单完成如果发生过“完成 → 退回安装中 → 再完成”，只使用最后一次完成事件，并要求订单当前仍为 `completed`，避免已退回项目仍计为已完成。
- 明细如果完成后返工，使用最后一次阶段状态事件判断当前是否仍完成；当月统计只计在当月完成且查询时仍保持完成的工作单元。若业务以后要统计“当月完成动作次数”，另行增加事件次数指标，不与本需求的完成数量混用。

### 3.4 “数量”的含义

本期“完成数量”默认指项目记录数、订单明细工作单元数，不把订单明细中的业务 `quantity`（例如 10 个、30 平方米）直接相加。若后续需要“完成件数/完成面积”，应新增独立指标，并明确按 `quantity_mode`、单位和面积口径换算，不能复用本期的明细条数。

## 4. 数据模型与历史记录

### 4.1 新增 `task_item_status_logs`

新增一张追加型表，每次任务处理对勾选明细发生状态变化时，为每个明细写一条记录：

| 字段 | 类型/含义 |
| --- | --- |
| `id` | UUID 主键 |
| `task_type` | `design`、`production` 或 `installation` |
| `task_id` | 对应阶段任务 ID；因三类任务共用一列，保持多态，不伪造跨表外键 |
| `document_id` | 订单 ID，外键 `business_documents.id`，便于统一统计和索引 |
| `order_item_id` | 订单明细 ID，外键 `business_document_items.id`，级联删除 |
| `from_status` | 变更前的明细状态，可为空 |
| `to_status` | 变更后的明细状态 |
| `assignee_user_id` | 完成时任务负责人快照，外键 `users.id`，`SET NULL` |
| `operated_by` | 实际操作账号，外键 `users.id`，`SET NULL` |
| `operated_at` | 事件时间，统一按系统业务时间写入 |
| `source` | `live` 或 `backfill`，用于区分发布前回填数据 |

索引至少包括：

- `(document_id, task_type, order_item_id, operated_at)`：项目/阶段/明细历史查询；
- `(assignee_user_id, operated_at)`：员工当月统计；
- `(task_type, to_status, operated_at)`：阶段完成事件筛选；
- `(order_item_id, task_type, operated_at)`：判断明细后续是否返工。

### 4.2 写入时机

在现有 `_apply_task_item_status_change` 完成状态合法性校验、外协阻断校验后，在更新 `TaskOrderItemLink` 的同一数据库事务中写入事件。每个勾选明细一条，事件中的 `assignee_user_id` 使用本次状态变更最终确认的负责人，`operated_by` 使用当前登录用户。

事件写入失败必须使本次状态变更整体回滚，不能出现“明细完成了但统计没有记录”的半成功状态。

### 4.3 历史数据处理

迁移时对现有 `TaskOrderItemLink` 中已经完成且有 `item_completed_at` 的记录做一次 `source='backfill'` 回填；由于旧任务 `assigned_to` 是整单负责人，不能安全复制到每条明细，历史回填的负责人为空，避免制造错误的个人归属。没有完成时间的历史完成记录可以计入“全部”的当前快照，但不伪造“当月”时间。发布说明中记录统计正式可追溯起点。

这不是业务数据重算，不修改任务状态和进度；回填前必须备份数据库，并提供回滚迁移只删除本次新增的事件表。

## 5. 权限与数据范围

### 5.1 新增原子权限

建议增加两项非财务权限：

| 权限码 | 用途 | 依赖 |
| --- | --- | --- |
| `task_completion:read` | 查看自己的完成统计和完成明细 | 无 |
| `task_completion:view_all` | 查看组织总计、员工分组以及按员工查看明细 | `task_completion:read` |

`task_completion:*` 的 `sensitivity` 标记为 `normal`，不加入现有财务敏感权限集合，确保设计、制作、安装人员可以在不获得价格/报表权限的情况下查看自己的工作统计。接口仍然只返回非财务字段。

建议默认角色组合：

| 角色 | 完成统计范围 | 员工明细范围 | 默认权限 |
| --- | --- | --- | --- |
| 管理员 | 全部人员、组织总计 | 全部人员，可切换个人 | 两项权限；超级管理员按现有评估器放行 |
| 设计人员 | 当前登录员工 | 当前登录员工的设计完成明细 | `task_completion:read` |
| 制作人员 | 当前登录员工 | 当前登录员工的制作完成明细 | `task_completion:read` |
| 安装人员 | 当前登录员工 | 当前登录员工的安装完成明细 | `task_completion:read` |
| 销售/财务 | 本期默认不增加新完成统计范围 | 不开放 | 由管理员后续按业务需要组合 |
| 资源/外协等其他角色 | 不开放 | 不开放 | 不授予新权限 |
| 自定义角色 | 按原子权限决定 | `read` 为本人，`view_all` 为组织级 | 由角色编辑器显示依赖并校验 |

### 5.2 后端强制规则

1. 没有 `task_completion:read` 的用户不能调用统计接口。
2. 没有 `task_completion:view_all` 的用户，服务层强制把范围收敛为当前登录用户，不能通过 `employee_id` 参数查看别人。
3. 有 `view_all` 的用户也必须有 `read`；角色组合校验负责阻止孤立的全员权限。
4. 当前登录用户未绑定在职员工时，个人统计返回零数据和可读提示“当前账号未绑定员工，暂无法显示个人完成统计”，不根据未绑定用户搜索全员数据。
5. 统计查询还要叠加既有 `order_task_assignees` 访问范围；统计归属过滤和任务可见过滤取交集。
6. 员工离职后，历史事件仍保留原员工快照；管理员可看到“已离职”标识，不能把历史数据无声转移给新员工。

## 6. API 设计

保留现有 `/reports/dashboard` 的金额和待处理任务字段，新增独立接口，避免不同角色加载驾驶舱时互相影响：

### 6.1 汇总接口

`GET /api/v1/reports/task-completion/summary?period=all|month`

返回建议结构：

```json
{
  "period": "month",
  "period_start": "2026-09-01",
  "period_end": "2026-10-01",
  "scope": "own",
  "employee": {
    "employee_id": "...",
    "user_id": "...",
    "name": "张三"
  },
  "own": {
    "completed_project_count": 3,
    "completed_work_unit_count": 12,
    "stage_breakdown": {
      "design": 5,
      "production": 4,
      "installation": 3
    }
  },
  "organization": null,
  "employees": []
}
```

管理员响应 `scope='all'`，同时返回：

- `organization.completed_order_project_count`：整单最终完成项目数；
- `organization.completed_detail_count`：最终安装完成的不同订单明细数；
- `organization.completed_work_unit_count`：所有阶段完成工作单元数；
- `employees[]`：员工个人完成过项目数、完成工作单元数和阶段分布；
- `unassigned`：无法归属到员工的历史/未分配完成工作单元，便于总数核对。

### 6.2 明细接口

`GET /api/v1/reports/task-completion/details`

参数：

- `period=all|month`；
- `kind=project|detail`；
- `employee_id`：仅 `view_all` 用户可使用；普通员工传入时返回 403，不静默切换范围；
- `task_type=design|production|installation`：可选阶段筛选；
- `page`、`page_size`：服务端分页，最大 100。

`kind=project` 返回不同订单的项目摘要；`kind=detail` 返回完成工作单元。两种响应都只包含项目编号、项目名称、明细名称、阶段、任务编号、负责人名称、完成时间和状态展示字段，禁止携带 `total_amount`、`unit_price`、`subtotal_amount`、成本或利润字段。

接口统一使用成功信封和现有错误契约：无权限 403，参数错误 422，记录不存在或不在当前可见范围按现有任务资源策略处理。

## 7. 前端交互设计

在 `frontend/src/views/home/DashboardView.vue` 的现有待处理任务统计下方增加“交付完成统计”区域：

1. 顶部提供分段切换 `全部` / `当月`，默认 `当月`，切换时两个接口并行刷新，显示当前统计月份。
2. 员工视图显示两个主卡片：`我完成过的项目`、`我完成的明细`；下方使用两个标签页 `项目`、`明细` 查看分页列表，并显示设计/制作/安装的小分布。
3. 管理员视图先显示组织总计卡片，再显示员工统计表：员工、完成过的项目、完成明细、设计/制作/安装分布；点击员工行只改变明细接口的 `employee_id`，不在前端过滤已经拿到的全量数据。
4. 管理员明细区提供“全部人员”及单个员工筛选；普通员工不渲染员工选择器，也不显示其他人姓名。
5. 统计区域使用空状态、加载状态和错误重试，不因统计接口失败阻塞现有驾驶舱、项目看板和任务卡片。
6. 所有按钮和表格遵循现有共享状态、分页、焦点和移动端规则；390px 宽度下统计卡片单列，员工表改为可横向滚动或转为员工卡片。
7. 新区域不显示金额，不复用现有“财务报表”权限作为前端显示依据；以 `/auth/me` 的新权限能力和后端响应为准。

## 8. 性能与一致性

- 不为每个员工/项目逐条查询，服务层批量获取员工、任务、明细和状态事件，避免 N+1。
- 统计接口只返回分页明细，汇总接口不嵌入全部项目/明细记录。
- 以 `document_id`、`order_item_id`、`task_type` 和事件时间建立索引；当月查询必须命中时间条件。
- 组织总计、员工分组和个人明细使用同一个 `TaskCompletionMetricsService` 的归属规则，禁止在 `ReportService`、前端各自实现一套过滤。
- 完成事件写入与状态更新同事务提交；同一请求重试不得生成重复事件，必要时使用请求幂等键或按任务/明细/状态变更时间做唯一防重策略。

## 9. 非目标与后续备选

- 本期不统计完成件数、面积、金额、毛利、成本或工资绩效金额。
- 本期不新增审批人员、不接短信/邮件/飞书通知。
- 本期不开放销售、财务默认查看全员完成明细；如后续需要，仅组合 `task_completion:view_all`，仍不等于价格权限。
- 如管理层未来需要“按完成动作次数”“按最后操作人”或“按部门汇总”，在事件表基础上增加独立口径，不改写本期指标含义。
