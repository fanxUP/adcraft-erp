# 任务分配与变更状态合并方案

## 1. 需求理解

本方案将“任务分配”放到“变更状态”旁边，并与现有“任务处理”合并为一个卡片。这里将“变更状态三方”理解为“变更状态标题旁边/同一操作区”。

目标是：

- 设计、制作、安装任务使用统一的任务处理卡片；
- 在变更状态操作区直接选择任务负责人；
- 没有负责人时，不能推进、回退或取消任务状态；
- 已关联订单明细的每一条继续显示当前任务负责人；
- 选择新负责人后，可以先保存分配，也可以在点击状态时与状态变更一起安全提交；
- 不改变状态只作用于勾选订单明细的既有规则。

## 2. 当前实现基线

当前项目已经具备三类任务的任务级分配模型：

- `design_tasks.assigned_to`；
- `production_tasks.assigned_to`；
- `installation_tasks.assigned_to`。

任务处理页面使用共享组件 `frontend/src/components/tasks/TaskOrderItemLinkCard.vue` 展示订单明细和状态工作流；三个详情页目前在组件外部各自显示“任务分配”卡片。

任务响应已经能返回 `assigned_to` 与 `assigned_to_name`，任务明细接口能返回 `is_linked`、明细状态和明细进度。现有状态变更接口已经接收 `order_item_ids`，后端也已经按选中明细执行状态流转。

## 3. 核心设计决策

### 3.1 一个卡片、两个操作区

保留一个“任务处理”卡片，订单明细列表之后的“变更状态”区域改为：

```text
变更状态                         任务分配：[选择员工 ▼] [保存分配]
请先勾选要推进的订单明细          当前负责人：张三

待分配  ✓  ───>  设计中  ───>  已完成
```

桌面端将负责人选择器放在“变更状态”标题右侧；窄屏自动换行到标题下方。原来三个详情页底部独立的“任务分配”卡片删除，避免同一页面出现两个分配入口。

### 3.2 负责人是状态变更的前置条件

对设计、制作、安装任务的所有可执行状态变更统一要求负责人：

- 向前推进要求负责人；
- 回退要求负责人；
- 取消任务也要求负责人；
- 已完成、已取消和历史只读任务本来不能变更状态，不因本规则重新开放；
- 没有勾选订单明细时，继续先提示“请先勾选要变更状态的订单明细”；
- 没有负责人时，状态节点禁用；即使绕过页面直接调用接口，后端也拒绝。

推荐的用户提示：

```text
请先选择分配人，再变更任务状态
```

不使用技术化的 `pending -> confirmed` 等错误提示作为用户提示。

### 3.3 分配与状态变更采用安全的两种模式

为了兼顾“只派工”和“派工后立即推进”，提供两个入口，但都放在同一个卡片中。

#### 模式 A：仅保存分配

用户选择员工后点击“保存分配”：

```text
PUT /design-tasks/{id}
PUT /production-tasks/{id}
PUT /installation-tasks/{id}
```

只更新任务的 `assigned_to`，不改变任何订单明细状态和进度。保存成功后，所有已关联明细行同步显示新负责人，状态节点正常可用。

#### 模式 B：选择负责人后直接变更状态

用户选择员工后直接点击某个状态节点，状态变更请求同时携带负责人 ID：

```json
{
  "to_status": "in_progress",
  "order_item_ids": ["..."],
  "assigned_to": "...",
  "reason": ""
}
```

后端在同一个事务中完成：

1. 校验负责人存在且可用；
2. 保存任务负责人；
3. 校验选中的订单明细、状态流转、外协阻塞和权限；
4. 只更新 `order_item_ids` 中的明细状态与进度；
5. 更新任务聚合状态与聚合进度；
6. 提交事务并刷新响应。

任何一步失败都回滚负责人和明细状态，避免出现“负责人已经改了，但状态没有变更”的半完成结果。状态变更成功后沿用现有任务分配通知机制；短信、邮件和飞书仍不在本次范围内。

### 3.4 后端必须校验，前端只负责体验

状态变更服务层增加统一规则：

- 请求带新负责人时，使用请求中的负责人；
- 请求不带新负责人时，使用任务当前已保存负责人；
- 请求和任务都没有负责人时，返回大白话提示“请先选择分配人，再变更任务状态”；
- 显式传空值不能绕过该规则；
- 负责人 ID 必须是真实用户，不能只提交员工表 ID；
- 继续执行现有的任务权限、订单明细归属、状态机、外协阻塞和终态校验。

前端状态节点的禁用只是即时反馈，不能替代后端校验。AI 操作、移动安装页面或其他调用同一状态接口的入口也必须遵守同一后端规则。

### 3.5 已关联明细逐条显示负责人

在订单明细第一行状态信息区域显示：

```text
□ 标识牌   [设计中]   本任务：[设计中]   [分配人：张三]
```

规则如下：

| 场景 | 显示 |
|---|---|
| 已关联且已分配 | `分配人：张三` |
| 已关联但没有负责人 | `分配人：未分配` |
| 未关联明细 | 不显示负责人 |
| 重新派发 | 所有已关联明细显示新负责人 |
| 已完成/已取消明细 | 仍显示负责人，保持原有只读和不可选 |

负责人是任务级字段，因此同一个任务的已关联明细显示同一个当前负责人。本次不新增 `task_order_item_links.assigned_to`，也不宣称支持明细级不同负责人。

### 3.6 选择器与状态按钮的即时状态

定义三个状态：

| 页面状态 | 选择器 | 状态操作 |
|---|---|---|
| 当前已有负责人 | 显示当前负责人 | 可用，除非任务自身不可变更 |
| 当前无负责人且未选择 | 显示“请选择分配人” | 全部禁用 |
| 当前无负责人但已选择新负责人 | 显示待保存人员 | 可点击状态，点击时一并提交负责人和状态 |
| 当前有负责人但选择了另一人未保存 | 显示“待保存”提示 | 点击状态时使用新选择并原子提交 |
| 正在保存/变更 | 保持当前值 | 禁用，防止重复提交 |

“保存分配”按钮只在选择值与当前保存值不同且用户有更新权限时可用。若用户清空选择，状态操作保持禁用；是否清除已有负责人沿用现有编辑权限和接口规则，不允许通过清空后变更状态。

## 4. 实施范围

预计涉及：

- `backend/app/schemas/task.py`
  - 扩展状态变更请求的负责人输入契约；
  - 统一三类任务响应的 `assigned_to_name` 字段声明。
- `backend/app/api/tasks.py`
  - 把负责人参数传递给三类任务状态变更服务；
  - 保持现有权限依赖和接口路径。
- `backend/app/services/task_service.py`
  - 三类任务状态变更共用“负责人必填 + 原子更新”规则；
  - 保持状态、进度、外协和订单阶段逻辑不变。
- `frontend/src/types/api.ts`、`frontend/src/api/tasks.ts`
  - 补齐状态变更请求负责人字段和任务负责人类型。
- `frontend/src/components/tasks/TaskOrderItemLinkCard.vue`
  - 合并任务分配与变更状态区域；
  - 控制无负责人禁用状态；
  - 继续逐条显示已关联明细负责人。
- `frontend/src/views/tasks/DesignTaskDetail.vue`、`ProductionTaskDetail.vue`、`InstallationTaskDetail.vue`
  - 传递任务负责人、员工选项和保存状态；
  - 删除外置独立“任务分配”卡片；
  - 适配带负责人 ID 的状态变更事件。
- 相关后端服务测试、前端任务界面契约测试和回归证据。

不需要修改：

- `task_order_item_links` 表结构；
- 任务明细状态和进度字段；
- 任务看板的进度和隐藏规则；
- 外协任务数据模型；
- 短信、邮件、飞书通知渠道。

## 5. 风险与控制

1. **只做前端禁用，接口仍可绕过**：在任务服务层统一拒绝无负责人的状态变更，并覆盖直接 API 测试。
2. **分配成功但状态失败**：状态点击带新负责人时使用同一事务，任何状态校验失败都回滚负责人。
3. **状态变更误改未勾选明细**：仍以 `order_item_ids` 为唯一明细变更集合，增加参数回归测试。
4. **改派后明细显示不同步**：状态成功或分配保存后重新获取任务，负责人标签只从当前任务响应派生。
5. **三个页面不一致**：把布局、禁用和明细标签放进共享组件，详情页只提供任务类型、员工选项和接口处理。
6. **旧任务关联识别异常**：已关联判断同时覆盖 link 表和 legacy `order_item_id` 兼容路径，未关联明细不显示负责人。
7. **状态操作过于拥挤**：标题右侧使用可换行 flex 布局，窄屏下选择器独占一行，不压缩明细金额和进度信息。

## 6. 非目标

- 不支持一个任务内不同订单明细分别分配给不同员工；
- 不记录每条明细的负责人历史；
- 不因为选择负责人自动推进任务状态；
- 不删除已有的仅保存分配能力；
- 不把分配人显示到未关联明细、项目看板或报价明细中；
- 不修改状态流转顺序、明细进度算法、外协阻塞和订单自动推进规则。
