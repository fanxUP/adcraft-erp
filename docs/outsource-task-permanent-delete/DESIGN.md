# 外协任务永久删除设计

## 风险与目标

- 类型：外协任务不可逆删除与财务数据保全。
- 风险：高；采用 STRICT 模式。永久删除不能靠页面确认框替代后端约束。
- 目标：允许有权限的人员从外协任务回收站永久删除“已取消且没有实际财务痕迹”的任务，同时保留审计记录。
- 非目标：永久删除付款流水、供应商、订单/报价、项目成本或内部任务；批量清理；用删除来消除未核实付款金额。

## 当前行为与设计约束

- 回收站目前只有恢复操作，没有永久删除入口。
- 现有任务删除接口将任务软删除，但同时物理删除关联的 `outsource_payments`；恢复时按仍存在的付款行重算金额。付款行一旦被删，恢复可能无法还原原付款明细和金额口径。
- 财务费用重叠审查通过 `ON DELETE RESTRICT` 外键引用外协任务；不得级联删除审查记录。
- 付款日期核对记录通过 `source_type/source_id` 多态关联，数据库没有外键保护；硬删前必须由服务层检查并保护这些记录。
- 操作日志可保留删除对象 ID 和 JSON 快照，可用于记录永久删除事件；日志不能替代财务流水。
- 旧版软删除日志会记录被清除的付款行数量；日志显示清除过付款的任务属于财务事实不完整，必须保留并人工核实。

因此，永久删除功能的前置条件是先修正软删除：移入回收站不得删除付款行，恢复不得把只有历史已付汇总、但没有付款明细的任务静默改成已付 0。已有回收站数据不自动补造付款明细或付款日期。

## 允许永久删除的规则

只允许删除已在回收站、状态为“已取消”的任务，并且后端在最终事务中重新检查以下条件：

1. `paid_amount` 为 0；任何关联 `outsource_payments` 付款行都阻止硬删。
2. 不存在任何付款日期核对记录，包括已作废的核对历史。
3. 不存在 `finance_cost_overlap_reviews` 关联审查记录。
4. 任务不处于已完成/已结算状态，避免移除已确认的外协成本。
5. 删除对象仍处于软删除状态；不允许从普通任务列表直接调用永久删除。
6. 没有旧版软删除日志表明曾清除该任务的付款行；即使当前汇总为 0，也不能把丢失的历史付款事实误判为无财务痕迹。

未付款余额只在状态为“已取消”时视为不再生效的任务计划金额；确认框仍须展示总额、未付余额及删除影响，并写入审计快照。若业务希望“已取消但仍有未付余额”必须走财务核销，则应在实施前把未付余额也设为阻止条件，并另行定义核销流程。

任何检查不通过时，服务端拒绝删除并返回明确阻止原因；不提供忽略阻止原因的强制删除开关。带有非零历史已付金额的旧记录，即使当前已找不到付款明细，也必须阻止永久删除，不能据此推断为未付款。

## 交互与接口

1. 回收站显示“永久删除”操作，并先展示服务端计算的资格与阻止原因。
2. 对符合条件的记录，确认弹窗显示任务编号、类型、供应商、状态、金额、关联记录数和不可恢复提示；要求输入完整任务编号及删除原因。
3. 前端按钮状态仅作提示。后端独立校验权限、回收站状态、财务条件和关联关系，并在事务中锁定任务后复查。
4. 使用独立的永久删除 API，例如 `DELETE /outsource/tasks/recycle/{task_id}`；不复用现有软删除路由。
5. 单事务内写入永久删除审计日志（操作者、时间、IP、原因、任务编号及最小必要快照），再物理删除任务。审计日志失败则整个事务回滚。
6. 不删除、不级联清理付款、核对、费用审查或其他业务记录；任何遗留引用均应阻止操作并提示人工处理。

## 权限

- 新增独立权限 `outsource_task:permanent_delete`，与 `outsource_task:delete`（软删除/回收站管理）分离。
- 默认只授予系统管理员；其他角色必须在角色管理中显式授权。
- 权限依赖外协中心和任务读取权限，并在权限目录中标记为高风险敏感操作；API 必须服务端校验，不能只隐藏前端按钮。

## 全局影响

- 财务支出台账：硬删非零已付会直接移除历史已付金额或付款流水，因此这类任务一律阻止；本功能不得用于清除“付款日期待核实”提示。
- 外协付款：软删除和恢复保留原付款行；永久删除只接受没有付款行的任务。
- 订单明细、内部设计/制作/安装任务：被删任务不再出现在关联统计中；永久删除审计快照保留原关联信息。相关业务实体本身不删除。
- 成本重复审查、付款日期核对、操作日志：保留原记录，不级联删除；前两类有引用时阻止硬删。
- 供应商历史与外协计划统计：永久删除会移除该任务的历史计划行；确认弹窗和审计快照应明确展示。

## 数据库、恢复与发布

- 预计无需新增业务表或 Alembic 迁移；权限目录/角色种子版本需要更新，操作日志复用现有 JSON 字段。若实现审计快照需要独立表，再单独评估迁移。
- 永久删除本身没有应用内撤销；误删恢复依赖备份恢复或人工重建，因此必须先在生产数据副本演练。
- 现有软删除已经物理删除过的付款明细不能通过新逻辑自动恢复；不得根据 `paid_amount` 合成带日期的付款记录。需要从可靠备份/凭证恢复时，应作为单独财务数据修复流程处理。
- 不对生产数据执行试删。上线前确认最近备份有效、恢复流程可用；上线后只做健康检查和非破坏性页面/API 校验。
